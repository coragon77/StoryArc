# Marks wait for a prompt change that happens anyway

Foreshadowing clues and triggers were never marked done, so the plan asked the model to plant the same clue in every message for hundreds of messages (test chat, 2026-10-19: 0 planted, 0 fired across 6 arcs and about 980 messages). The model now marks them with `:PLANTED` and `:FIRED` markers, the same recognition mechanism as beats. A marked item leaves the plan and the plant check, and with this provider any changed byte of the injection is a full prompt-cache miss, at `IN_PROMPT` and at depth 0 alike. So marks are queued and applied only when the prompt changes anyway, which is the message in which a beat completes, or when the oldest queued mark has waited 20 messages. Until then the item stays visible and a repeated marker for it is ignored. Secrets get no marker, because the recognition line would have to state the secret right before the reply; they are marked by hand in the Arc Manager, where every toggle costs one miss.

## Considered options

- Apply each mark at once: one cache miss per planted clue, several per episode.
- Show each clue for a fixed number of messages: does not know whether the clue was planted.
- A separate LLM check every N messages: an extra call on the generation profile; kept in reserve if markers prove unreliable.

## Amendment 2026-11-26: with the tracker on, a PLANTED mark waits for the extraction to find the clue

The narrator claims clues it never wrote. Of eight PLANTED claims that could still be checked (Amy #42, Paragon #1633, Claim the Sky #100 and #150; the markers survive in the narrator's reasoning, not in the stripped messages), two were clearly in their message, two were borderline, and four were not there at all. All eight had been applied. A planted clue leaves the plan for good, so the player later gets a reveal no clue pointed to (#87).

With the knowledge tracker on, the extraction that reads a claimed message now gets the claims of the messages it reads (`listClaimedClues`, the CLAIMED CLUES section) and answers which of them the messages show (`plantedClues`). A found claim is marked `confirmed` and waits for the flush as before. A claim not found is dropped, and the clue stays in the plan. A claim at a message no update will read again (before the first message a reply update read) is dropped too. Until it is confirmed, a claim counts for neither the 20-message window nor a beat completion's flush, so a failed extraction leaves it queued and unapplied. A re-extraction of an edited or swiped message checks that message's queued claims against the new text again, a confirmed one included; a mark already applied stays, as after a deletion. A repeated marker for a clue whose claim is still unconfirmed moves the claim to the newer message, so dropping the older claim cannot take a later, real plant with it. The extraction only checks claims and never plants a clue nobody claimed: a false "planted" loses the clue for good, while a false "not planted" only means the narrator plants it again. This is unlike beats, which have one recognition path at a time (`beatRecognitionPath`), not two.

With the tracker off nothing checks a claim, and it counts as written, as before. FIRED marks are unchanged. Every applied mark now records its message on the item (`plantedAt`, `firedAt`), so applied marks can be audited; a hand toggle in the Arc Manager removes it.
