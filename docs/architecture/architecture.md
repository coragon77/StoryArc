# Architecture

- **Coverage:** `index.js`, `lib/`, `prompts/`
- **Last Updated:** 2026-11-12

System design for Story Arc. For quick reference, see [CLAUDE.md](../../CLAUDE.md). For file index, see [code-index.md](./code-index.md).

## High-Level Data Flow

```
User clicks "Plan Next Arc"
       |
       v
Context Harvesting  (lib/context/)
  ├── Lorebook: classify World Info entries into constants / arc-summaries / recent
  ├── Character: pull character card fields + user persona
  ├── Chat history: extract recent messages within token budget
  └── Existing arcs: read active/completed arcs from chat_metadata
       |
       v
Arc Generation  (lib/planning/)
  ├── Wizard input: tier (episode / act / saga, from TIER_TABLE) + free-text direction;
  │     in revise mode (re-plan) also the arc being re-planned with edited title/premise
  ├── Phase 1 — Analysis: send harvested context through analyze-context.txt prompt
  │     → LLM produces a prose story-state summary (a re-planned arc is marked
  │       [BEING RE-PLANNED] so its unfulfilled beats are not reported as open threads)
  ├── Questions (wizard only, prepareArc): ask-questions.txt asks 0–5 questions about
  │     the author's intent that the direction leaves open; the answers are given on
  │     the wizard's Questions step and bind Phase 2 like the direction
  │     ({{AUTHOR_ANSWERS_BLOCK}}); none, a failed call or garbage → straight on
  ├── Phase 2 — Arc Outline: send analysis + user direction through generate-arc.txt,
  │     with {{TIER_BLOCK}} (beat kind, count, length band) and, on re-plan,
  │     {{ARC_SO_FAR}} (premise, secrets, fulfilled beats as "already happened")
  │     → LLM returns a JSON arc plan
  ├── Each LLM call: ConnectionManagerRequestService (when a generation profile is
  │     configured) or direct streaming POST to /api/backends/chat-completions/generate,
  │     auto-retried (max 2, linear backoff) on transient errors
  ├── Parse + validate JSON (strip fences, extract object, schema-check; the tier
  │     shapes the beats: scene beats ordered with one active, milestones in the planner's
  │     order and all active, the first open one current (ADR-0010);
  │     estimatedLength clamped to the tier's band)
  ├── Retry once with stricter JSON instruction if parse fails
  ├── Re-plan only: mergeReplan(existing, generated) keeps the situation, replaces the road
  └── Normalize schema, assign defaults, save to chat_metadata.story_arc.arcs
      (re-plan: updateArc on the existing id instead)
       |
       v
Prompt Injection  (lib/injection/)
  ├── On GENERATION_STARTED: read active arcs from storage
  ├── Calculate current phase for each arc (beat ratio × message ratio, take minimum)
  ├── Build TWO arc injections:
  │     story_arc_plan (IN_PROMPT) — token-budgeted plan text, one section per arc
  │       chosen by (tier, focus) — see "Tiers and Focus" below and lib/injection/builder.js:
  │       Episode, normal/spotlight — premise, world facts, the ACTIVE beat's pressure only,
  │                          pacing rules, secrets, foreshadowing, triggers
  │       Act/saga, normal — premise + up to three world facts + the current milestone's
  │                          pressure (the first open one, ADR-0010) under STANDING PRESSURE
  │       Act/saga, spotlight — same section, that pressure under BRING TO A HEAD + one
  │                          trailer sentence, then gated secrets, triggers, foreshadowing;
  │                          ordered first
  │       Paused (any tier) — one line: premise + "pending, not being pursued right now"
  │     story_arc_signals (IN_CHAT, depth 0) — ARC PACING brake for the pacing clock;
  │       continuation guard + confidentiality clause always (whatever autoTrack says);
  │       with autoTrack on the PLANT CHECK, and only while the knowledge tracker is
  │       off the BEAT CHECK listing every active beat of every non-paused arc
  │       (ADR-0008). Placed as the last message before generation (models ignore
  │       it anywhere else)
  ├── Both are set to '' when no arcs are active or the extension is disabled
  ├── Third injection, independent of the arcs — story_arc_knowledge (IN_CHAT, depth 1,
  │     system): the knowledge block, "who knows what" for the characters present and
  │     talked about (lib/knowledge/ledger.js, see "Knowledge Tracker" below); set on
  │     every GENERATION_STARTED, '' while the extension or the knowledge tracker is off
  ├── Fourth injection, set right after the third under the same gate — story_arc_names
  │     (IN_CHAT, depth 1, system): the taken-names block, every name the ledger's
  │     characters use (lib/knowledge/names.js, see "Knowledge Tracker" below)
  └── On CHAT_COMPLETION_PROMPT_READY: stamp each user message in the OUTGOING
        prompt array with "[Arc: message N of ~M]", N derived from that message's
        own chat index. Old positions never change bytes, so the provider's
        prefix cache survives. Stored chat and the UI are untouched.
       |
       v
Beat Recognition and Progress Tracking  (lib/injection/signals.js,
                                        lib/planning/beat-completion.js)
  ├── On MESSAGE_RECEIVED: scan AI message for [ARC_SIGNAL:arcId:itemId:VERB]
  │     (emitted HTML-comment-wrapped; bare form still parsed for old messages);
  │     COMPLETE markers are asked for only while the knowledge tracker is off
  ├── completeBeats (both recognition paths): mark the named beats completed
  │     (active only; at most one per arc per message); stamp arc.lastFulfilledAt
  │     with the fulfilling message's chat index; unlock gated beats whose
  │     unlockAfter prerequisites are all complete; complete the arc when all
  │     non-optional beats are done; record the completion on the beat
  │     (beat.completion) so a rollback can reopen it
  ├── Queue PLANTED (clue) and FIRED (trigger) marks; apply the queue when a beat
  │     completed (in this message, or in the extraction's answer) or the oldest
  │     mark waited MARK_FLUSH_WINDOW (20) messages, so marks cost no miss of their
  │     own when a beat completes, and at most one per 20 messages otherwise
  ├── Strip signal tokens (and their leftover blank lines) from the message
  ├── Scrub leaked plan identifiers (beat/arc ids, all arcs) from the message
  ├── Save updated arc state to chat_metadata, refresh progress UI
  ├── Knowledge tracker on: every N replies, one extraction call (not awaited) reads
  │     the messages since the ledger's last update, records who learned what, and
  │     reports the beats the messages fulfilled, which go through completeBeats.
  │     Deleting, swiping or editing a message, or loading a branch, takes back what
  │     the ledger learned from it (lib/knowledge/ledger.js)
  └── Deleting or swiping a message, or loading a branch that ends before it, reopens
        the beats it completed (reopenCompletionsFrom, both paths); an edit reopens
        them before the re-extraction reads the message again (reopenCompletionsAt,
        tracker on), and puts the arcs back when no answer is applied
       |
       v
Beat Promotion  (lib/injection/signals.js — promoteNextBeats)
  ├── On USER_MESSAGE_RENDERED: for every active episode without an active beat,
  │     promote its first pending beat to active and persist; for every act or
  │     saga, activate every pending milestone (a repair: every open milestone stays
  │     active for recognition; the current one is derived, never promoted)
  └── Between completion and promotion an episode lingers: the plan section carries a
        "develop the consequences" directive instead of a pressure, and no beat
        is offered for recognition. The player always reacts before the model learns
        what comes next; the next user message always ends the linger
       |
       v
UI Display  (lib/ui/)
  ├── Settings panel in ST extension drawer (setup rows only)
  ├── Wand-menu entry + popup (Plan / Manage / progress cards) — the everyday route
  ├── Planning wizard popup (context preview → tier + direction → questions when the
  │     model asked any → generation progress and review);
  │     the same popup in revise mode re-plans an existing arc
  ├── Arc manager popup (list arcs, focus paused/background/normal/spotlight, re-plan, delete)
  ├── Knowledge popup (tracker on; from the Arc Manager, the wand popup and the
  │     drawer): "What changed" (the updates' change items, fix or mark Fine) and
  │     "Cast & facts" (search, sheets, add forms); "Names to check" in both
  └── Progress rows in the drawer and the wand popup (title, tier, phase, beat
        squares, "~N messages to the next phase", the stall or overrule warning
        with Re-plan)
```

## Module Responsibilities

### lib/core/

Shared constants, settings management, and per-chat state initialization.

- `constants.js` — `MODULE_NAME`, `INJECTION_HEADER` (first line of the plan block; doubles as the marker that tells the stamping pass "this is the real chat prompt"), `defaultSettings`, `defaultPerChatSettings`, `ARC_PHASES` (five phases with 0–1 percentage ranges), `PHASE_ORDER`, `PACING_DIRECTIVES` (one directive string per phase), `TIER_TABLE` (episode/act/saga: `label`, `beatKind`, `beatCount`, `lengthBand` — design spec 2026-09-16 §1; read by the generator's tier block, the validator's clamp, the milestone section header and the UI badges, so prompt and validator cannot drift apart), `ARC_FOCUS`, `createDefaultArc()` factory. For the knowledge tracker (ADR-0007): `defaultKnowledgeTrackerSettings` (`{ enabled: false, updateInterval: 1, characterDetails: false, appearance: false }`, nested in `defaultSettings.knowledgeTracker`), `APPEARANCE_KINDS`, `KNOWLEDGE_PROMPT_KEY` (`'story_arc_knowledge'`), `HOLDER_HOW` (the four holder values `witnessed`, `told`, `user`, `plan`, used instead of string literals) and `createEmptyKnowledgeLedger()`, whose JSDoc is the ledger's schema of record
- `settings.js` — `loadSettings()` / `getSettings()` / `isEnabled()` for global extension settings; `ensureChatState()` initializes `chat_metadata.story_arc` on demand and runs `migrateArc()` over every stored arc; `getChatSettings()` returns per-chat settings with defaults merged. `arcTier(arc)` and `arcMessageStart(arc)` state the two fallbacks every reader uses: an arc without a tier is an episode (the migration rule), an arc without `messageStart` counts from chat index 0; tests pin both. `getArcs()` and `getChatSettings()` carry a comment at the `ensureChatState()` call saying that the read may migrate and save. Knowledge tracker: `loadSettings()` merges the stored `knowledgeTracker` group over its defaults key by key (so a stored group missing `updateInterval` gets 1); `getKnowledgeTrackerSettings()` returns that stored group, `isKnowledgeTrackerEnabled()` reads its switch, `isCharacterDetailsEnabled()` is true only while Story Arc, the tracker and `characterDetails` are all on (a group without the key reads as off); `ensureChatState()` creates an empty ledger in a chat that has none (every chat from before the tracker), and `getKnowledgeLedger()` returns `chat_metadata.story_arc.knowledge` after it; `secretHolders(secret)` reads a secret's holder names, `[]` for a secret planned before holders existed
  - **Migration (2026-09-16, ADR-0001).** An arc without `tier` was planned before tiers existed. It becomes `tier: 'episode'` (its beats are ordered scene beats, so no other tier fits); `focus: 'foreground'` → `'normal'`, `'background'` → `'paused'` with `pausedAt = chat.length` at migration. Nothing else on the arc changes. `ensureChatState()` runs on every `getArcs()`, so the migration happens before the first injection is built; `saveMetadata()` is called once when anything migrated. The guard is `arc.tier` being set, not a version number. The old words survive in exactly one place: the episode section's header line still reads `=== FOREGROUNDED: "<title>" ===`, kept byte-for-byte so existing chats' cached prompt prefixes do not change (158358d). Outside `migrateArc()` itself and this note, nothing uses "foreground" any more. "background" came back on 2026-10-25 as a focus value with a different meaning (an act or saga kept off-screen, ADR-0001 amendment); the migration only touches arcs without a tier, so a pre-tier `background` still becomes `paused` and a tiered `background` arc is never migrated (`tests/test-background.js`).

No other module depends on more than `core/`. Core has no circular dependencies.

### lib/context/

Harvests story state from all available ST data sources.

- `harvester.js` — `harvestContext()` gathers every source and returns a `HarvestedContext` object with fields: `character`, `persona`, `lorebook` (split into `constants` / `arcSummaries` / `recent`), `chatHistory`, `existingArcs`, `cast`, `estimatedTokens`. `cast` (issue #44) is the knowledge ledger's characters as `{ name, aliases }`, in ledger order, read through `getKnowledgeLedger()` in `core/settings.js`, while Story Arc and the knowledge tracker are on (`isEnabled()`, `isKnowledgeTrackerEnabled()`); with the tracker off it is `[]` (ADR-0007). Its names and aliases count in `estimatedTokens`. The planner gets it in Phase 2 (`formatCastBlock`, under `generator.js`). `chatHistory` holds story messages only: `selectStoryMessages` drops any message that names an id of a stored arc of any status (`arcInternalIds` from `signals.js`), quotes `INJECTION_HEADER` or holds `ARC_SIGNAL` (2026-10-30). A narrator's OOC analysis that printed a secret beside its id had been read by the planner as story, and the secret came back as a milestone pressure. Other OOC messages stay, because the user's own direction belongs in the planner's input
  - Lorebook: `fetchLorebookEntries()` reads World Info entries, `filterAndSort()` and `categorizeEntries()` classify them by comment/tag into three buckets (all three exported for tests)
  - Character: the private `getCharacterData()` pulls character name, description, personality, scenario; the private `getPersonaData()` reads the active user persona
- `chat-history.js` — extracts recent chat messages up to a token budget; exports `estimateTokens()` (character-count heuristic: chars / 4)

### lib/planning/

Arc generation, validation, storage, and prompt template management.

- `generator.js` — `generateArc(context, userDirection, callbacks, { tier, reviseArc, genre, themeSeeds, analysis, authorAnswers })` runs the two-phase LLM pipeline and stamps `tier`, `direction`, `genre`, `themeSeeds` and `authorAnswers` (each only when non-empty), `messageStart` and `lastFulfilledAt` (= `messageStart`) on the validated arc. The tier travels three ways: `{{TIER_BLOCK}}` in Phase 2 (`buildTierBlock`, below), `validateArcPlan(parsed, { tier })` so the wizard's choice wins over whatever `tier` the model echoed (4246cf1), and the stamp on the result. Phase 1's `formatExistingArcs(arcs, reviseArcId, reviseRulings)` marks the arc being re-planned `[BEING RE-PLANNED]` and lists the rulings passed on `reviseArc` under it as "Overruled by the player:" (`analyze-context.txt` explains the mark: what has happened is established fact, the premise too except where a ruling overrules it; #47); Phase 2's existing-arcs list *omits* that arc — it is presented in the `{{ARC_SO_FAR}}` block (`buildArcSoFar`, below) instead, and listing it under "do not duplicate these" would tell the model not to cover its own ground (e3b81d8). The genre (ADR-0004) travels as `{{GENRE_BLOCK}}` in both phases, rendered by the exported `formatGenreBlock(genre, 'analysis' | 'outline')`: Phase 1 reads the story through it and reports material that leans another way as an imbalance, Phase 2 gets it as `== GENRE (binding) ==` above the creative direction, binding for the register only ("the arc reads as this genre"; 2026-11-09). An empty genre renders no block. The player's themes (`themeSeeds`, ADR-0004 amendment on the themes) travel as `{{THEMES_BLOCK}}` in Phase 2 only, right after the creative direction, rendered by the exported `formatThemesBlock(themeSeeds)`: `== THEMES (colour, not obligations) ==`, colour the arc draws on where the direction and the premise leave room, never an obligation; a theme is never a world fact and never the reason for a pressure, secret or trigger; the one place the themes seed is the plan's `themes` field; the FINAL CHECKLIST carries a matching line. Phase 1 never sees the themes. Empty themes render no block. Genre and theme seeds are set from the wizard after validation, never from the model. **The author's answers (2026-11-09).** A one-paragraph direction left the planner to its overt defaults (a plan for nuanced themes came out with contracts, orders and chaperones; the intent that mattered only came out in a later conversation), so the wizard asks before it plans. `prepareArc(context, userDirection, callbacks, { tier, reviseArc, genre, themeSeeds })` runs Phase 1 and then the question call (`askAuthorQuestions`, progress phase `questions`) and returns `{ analysis, questions }`. `buildAskQuestionsVariables` fills `prompts/ask-questions.txt` with the direction, the tier with its length band, genre, themes, the analysis, the other running arcs by title only (their premises sit behind the Arc Manager's spoiler switch; Phase 1 reads every arc's focus, title and premise and the re-planned arc's rulings, but no secret, trigger or clue, so the question call keeps the analysis), and on a re-plan `buildSeenArcSoFar(reviseArc)` and the arc's earlier `authorAnswers` as already answered. The player reads what the question call writes, so it never gets the full `buildArcSoFar`: `buildSeenArcSoFar` gives only what play has shown (the premise, the completed beats' fulfillments, planted clues, disclosed secrets), never an unrevealed secret, an unfired trigger, an unplanted clue, an open pressure or the escalation. The prompt asks only where an answer would change the plan materially and the direction leaves it open (how pressure works, how dark, whether allies or institutions can step in, the inner conflict, hard lines, how a power or sensitive theme plays), never what the direction answers, never plot, twists or secrets (the author is also the player), and allows zero questions. `parseAuthorQuestions` keeps at most five questions with a non-blank text and at most four non-blank suggestions each; no JSON or a wrong shape gives none. A failed call (caught, logged, a `retry` progress line) gives none too, never a failed generation. `generateArc` takes `options.analysis` and then skips Phase 1 and its progress line; without it, it runs Phase 1 as before. `options.authorAnswers` is cleaned by `answeredAuthorAnswers` (trimmed, blank pairs dropped), rendered as `{{AUTHOR_ANSWERS_BLOCK}}` right after the creative direction (`formatAuthorAnswersBlock`: `== AUTHOR'S ANSWERS (binding, like the direction) ==`, a `Q:` and an `A:` line per pair, and the sentence that an answer wins over genre, themes, the planner's preference and any default in the guidelines; the dilemma line yields with "Unless the author's direction or answers say otherwise,"; empty, no block), checked by a FINAL CHECKLIST line, and set as `authorAnswers` on the arc after `mergeReplan` and before the plan check (which reads them, `AUTHOR_ANSWERS` in `check-plan.txt`). After the merge, because `mergeReplan` spreads `existing`: set before, a re-plan would carry the arc's earlier answers into the check and the store. A new arc gets the field only with answers; a re-plan always gets it, an empty list when every answer was cleared, because `updateArc` merges with `Object.assign` and an absent field would keep the stored answers. `applyPlanRenames` never renames a name that occurs in an answer (the author's words, like the direction, the premise and the rulings; the question is the model's). `validateArcPlan` builds the arc from named fields, so a model echo is dropped. The narrator never sees them. **The cast in Phase 2 (issue #44).** The harvested `cast` travels as `{{CAST_BLOCK}}`, right after `{{GENRE_BLOCK}}`, rendered by the exported `formatCastBlock(cast, 'outline')`: `== CAST (characters already in the story) ==`, one line per character with its aliases, the taken names (`printTakenNames` from `knowledge/names.js`, the derivation of #39, sorted as the narrator's block lists them) and two rules: existing characters are named exactly as listed, everywhere in the plan, holders included; a new character gets none of the taken names as a first name or surname, unless the plan makes them related to the character who has it and says so. The FINAL CHECKLIST line on existing characters' names ends in `{{CAST_CHECKLIST}}`, `formatCastBlock(cast, 'checklist')`, which points it to the cast block. An empty cast renders `''` in both slots, so with the tracker off the outline prompt is byte-identical to the one before. Phase 1 gets no cast, and no call is added for it. Holders spelled as the ledger names them let the extraction link a revealed secret to them. When `reviseArc` is set, the validated plan is passed through `mergeReplan(reviseArc, arc)` (`replan.js`, ADR-0003) *inside* `generateArc`, so the wizard's review step shows the merged arc and Regenerate re-merges. Phase 3 is the plan check (2026-10-30, ADR-0006): `runPlanCheck(arc, story, revealableSecretIds, callbacks)` runs on the validated arc, on re-plan after the merge, so it sees every secret with its `disclosed` state and the ids the plan will be stored with. `buildPlanCheckVariables` fills `prompts/check-plan.txt` with the premise (on a re-plan the proposed premise, `proposedPremise`, since the road was planned around it; the check never rewrites the premise, only a rename changes a name in it) the direction and the rulings passed on the re-plan arc (`{{RULINGS}}`, `(none)` without; all passed as public, so carrying them out is never a give-away; #47), every secret by id with phase and disclosure and, indented under it, the planted clues that point at it (`  Planted clue: …`), the unfired triggers, and the pressures and the fulfillments (`{{FULFILLMENTS}}`, the `intention`) of open beats (`isBeatOpen`: neither completed nor skipped); a completed or skipped beat's fulfillment is never passed, because a re-plan keeps it and a completed one has already been recognised as written; the arc's world facts by index (`{{WORLD_FACTS}}`, `- [0] …`, `(none)` without; an arc stored before world facts reads as having none); a re-plan also gets the Phase 1 analysis and the last 10 harvested messages (`PLAN_CHECK_RECENT_MESSAGES`). The model answers `{ revealed, rewrites: [{ kind, id, text }], links: [{ trigger, secret }] }`, and the exported pure `applyPlanCheck(arc, answer, revealableSecretIds)` applies it to a copy: rewrites only the `action` of unfired triggers and the `pressure` and `intention` of open beats (a trigger rewrite that echoes the `IF … →` line is cut to the action), sets `disclosed` only for secrets of the arc being re-planned, and for those the `revealed` list decides both ways: a secret it leaves out goes back to `disclosed: false` (2026-10-31; a re-plan made while a leaked message was in the chat kept stating the leak after the user regenerated that message). On a re-plan the old `disclosed` mark is not shown to the check, so it judges from the story alone. A secret marked done by hand in the Arc Manager can therefore be un-marked by a re-plan, and fills a trigger's `secret` link only when it is empty or unknown. Unknown ids, empty texts and wrong shapes are ignored. **Fulfillment rewrites (2026-11-04, ADR-0006 amendment).** The check's task 3 finds every fulfillment that is a tally of many scenes ("has completed her first patrols") or a chain of separate events joined by "and", and rewrites it as the one on-screen moment at which the development shows; it answers each as a rewrite with `kind: "fulfillment"`. Recognition judges a message or two at a time (ADR-0008), and a sum over scenes never shows in one: a tally stayed open for 439 messages in the Paragon chat. `applyPlanCheck` applies such a rewrite only to a beat not yet completed; a fulfillment rewrite for an unknown or closed (completed or skipped) beat, or with an empty text, is ignored and logged, since it leaves a beat that may never be recognised. **Process milestones (2026-11-12, ADR-0006 amendment).** For an act or saga (`TIER_TABLE[arc.tier].beatKind` is `milestone`), `buildPlanCheckVariables` fills `{{PROCESS_MILESTONE_RULE}}` ahead of step 3's "leave alone" clause (empty for an episode), so step 3 also rewrites the fulfillment of a process milestone that the first scene of its pressure would already meet into the moment the process has taken hold; `buildTierBlock` gives the outline the same rule for acts and sagas. A one-off event keeps the event, an episode's scene beats are not touched. **Authority the setting does not grant (2026-11-09, ADR-0009).** Step 2 also rewrites a pressure or trigger action in which someone forces a character through a contract, clause, paperwork, an order, a disciplinary threat or a chain of command that a person in their place would not hold in a setting like this one, into lever and cost. Whether a power is real is judged by the setting (an officer commands soldiers, an employer does not own an employee's free time, a volunteer body cannot compel); the direction or the story can grant more, the premise never. Two wordings failed first: counting the premise let a contract-clause arc pass untouched twice, because its premise named the clauses; resting on the direction alone rewrote a garrison's legitimate orders twice when the direction was one line, because a fresh plan's check gets no story messages. The current wording rewrote the contract arc twice and left both military arcs alone (2026-11-09). **World facts (2026-11-09, ADR-0009).** Step 2 also rewrites a world fact that says how to narrate into a statement of fact, or drops it with an empty `text`, answering with `kind: "worldFact"` and the fact's index as `id`. `applyPlanCheck` applies these in `applyWorldFactRewrites`: a text replaces the fact, an explicit blank text drops it, a missing or non-string text and an unknown index are ignored with a warning (an id written as `"[1]"` is read as 1); indexes refer to the list as given to the check, so a drop never shifts another rewrite. An arc stored without a `worldFacts` key gets none added. **Secret rewrites (2026-11-09, ADR-0003 amendment).** Step 2 also rewrites a secret that is not revealed when someone in it forces a character through a power they would not hold in the setting, by the same lever-and-cost rule as a pressure, for a contradiction with the cast, or for a register the author's direction or answers rule out (the register rule covers unrevealed secrets, 2026-11-09), and only for that: the rewrite keeps what the secret is (the same hidden fact, the same people behind it, the same cause) and must still explain every planted clue listed under it; a revealed or disclosed secret is never rewritten. It answers with `kind: "secret"` and the secret's id. `applyPlanCheck` settles the disclosure first, from the `revealed` list, so a secret that the same answer marks revealed, or that is already disclosed, gets no rewrite. On a re-plan a secret counts as revealed when it is `disclosed` or a knowledge-ledger fact links to it by `{ arcId, secretId }` (the extraction never sets the flag): `generateArc` reads the ledger once (`secretIdsRevealedOnScreen`) and works on a copy of the re-planned arc with those secrets marked disclosed (`markSecretsRevealedOnScreen`), so the arc-so-far block lists them as established, the merge keeps them, and `applyPlanCheck` counts them as listed (`onScreenSecretIds`). A check that fails, throws or answers without a `revealed` list keeps every earlier secret as stored and adds the plan's new ones (`keepEarlierSecrets`, logged): the add-only re-plan, since nothing says which secret came out. The list judges `earlierSecrets`, the re-planned arc's secrets as stored before the re-plan: the story block ends with "== SECRETS BEFORE THIS RE-PLAN ==" listing them by id in their old wording, and step 1 names only those. An earlier secret the list names comes back as it was stored, `disclosed: true`, in place of what the planner wrote under its id, or appended when the plan dropped it; its id stays, so clues, triggers and ledger facts point at it again. A secret that came out on screen but was never marked disclosed is so never rewritten (2026-11-09). No call is added. Every other rewrite replaces `content` directly, on a re-plan too: an unrevealed secret is road (ADR-0003 amendment, later 2026-11-09, which removed the proposals and the player's keep-or-take choice). A rewrite identical to the stored text (trimmed), an empty one and one for an unknown id are dropped. No call is added. The clues come from the exported `plantedCluesOfSecret(arc, secretId)`: a foreshadowing entry's `target` is free text (the outline asks for `secret:<id>` or `beat:<id>`, and nothing else links a clue to a secret), so an entry with `planted: true` points at the secret when its target, trimmed and without a `secret:` prefix in any case, starts with the id: the leading token, up to the first whitespace, `(`, `,`, `;` or `- ` (`secret:voss_betrayal (his deal)` and `secret:voss_betrayal - the deal` both match; a hyphen inside an id stays part of it). A `beat:` target points at no secret, nor does a target in prose unless its first word is an id. Only planted clues are listed, the ones the player has seen: a new plan lists none, and a re-plan lists the planted clues the merge kept. **The cast and renames (issue #49, ADR-0006 amendment).** `runPlanCheck(arc, story, revealableSecretIds, names, callbacks)` gets `names = { cast, replanPremise, replanTitle }` from `generateArc`: the harvested `cast`, and on a re-plan `reviseArc.premise` and `reviseArc.title`, the premise and title the wizard passed in (`''` otherwise). `buildPlanCheckVariables(arc, story, cast)` fills `{{NAMES_BLOCK}}`, right before the answer key of `check-plan.txt`, with `formatPlanCheckNamesBlock`: `== NAMES ==`, the cast with aliases (`formatCastLines`, the outline's cast block lists it the same way), the taken names (`printTakenNames`), the plan's own `characters` field (generated, and read by nothing before this), and the RENAMES task with its answer key `"renames": [{ "from", "to" }]`: for each character the plan names, decide cast member or new character; a cast member named differently is renamed to the cast's name; a new character with a taken first name or surname, not made related to the character who has it, is renamed to a full name with no taken name; a name that extends a cast name by one more ("Julian Vance" for "Vance") is left unless the plan makes clear it is someone else; a character the direction names is never renamed; one pair per form the plan uses for the character. The task carries its own answer key, so the fixed part of the template does not change, and with an empty cast (tracker off) the block is `''` and the check prompt is byte-identical to the one before. `applyPlanCheck(arc, answer, revealableSecretIds, names)` applies the renames after the rewrites, in `applyPlanRenames`: a missing or wrongly shaped `renames` renames nothing, a malformed item (no string `from` or `to`, `from` equal to `to`, a second pair for the same `from`) is ignored with a warning. Code guards what the check may rename and drops a pair with a warning when `from` is a cast name or alias (folded comparison); `from` occurs in the direction or in `replanPremise`; on a re-plan, `from` occurs in `replanTitle`, so the title, the player's alone (ADR-0003), is never renamed, while a new plan's generated title may be; `from` occurs in a ruling's quote or a bare pick's `chose` (the merged arc's `rulings`), the player's words; `to` is not a cast name or alias and uses a taken name (`usesTakenName`: any name word, or part of a hyphenated one, in `listTakenNames`); `from` contains a single-word cast record's name as a whole name and `to` is not that name ("Julian Vance" → "Julian Marsh" against the record "Vance" is dropped, "Priya Patel" → "Priya" against "Priya" is kept; the Street act's "Julian Vance" was the record "Vance"); `from` does not occur in the plan. The kept pairs replace in one pass per text, longest `from` first in the alternation, so "Julian Hale" wins over "Hale" and a new name is never renamed again. A match is a whole name (`wholeNamePattern`): case-sensitive, not preceded or followed by a letter, digit, hyphen or apostrophe, except that a possessive `'s` or `’s` after the name still matches ("Hale's"), so "Vance" never matches inside "Vance-Chen", "Vancester" or "O'Vance". `renamePlanTexts` reaches the title, `premise`, `proposedPremise` (a re-plan's proposal, so the proposal the player sees in step 3 carries the new name), themes, tone, directives, anti-patterns, world facts, escalation and characters; every secret's content and holders, kept secrets included; every foreshadowing clue and target; the pressure, `intention` and flexibility of beats not completed; the condition and action of unfired triggers. The direction and the genre are never touched, and the arc given is not mutated. Whether an error is retried is decided by the exported `isRetryableError(detail)`, which matches `502|503|504|timeout|gateway|ETIMEDOUT|empty response` against `err.message` plus `err.cause?.message`. `empty response` is in that list because reasoning models (glm-5.2:thinking) sometimes emit only reasoning deltas and no content, which the routes below turn into `Empty response from API` — a per-call accident worth retrying. Auth, quota and model errors are deliberately not retryable: they fail identically every time and retrying only costs the user minutes. The pacing block, the continuation guard and the confidentiality clause are emitted regardless of `autoTrack`; only the BEAT CHECK and the PLANT CHECK are gated on it, and the BEAT CHECK on the knowledge tracker being off as well. The in-chat block is appended to the existing injection rather than added as a second one because the Claude converter counts system messages toward the depth, so each extra low-depth message pushes the breakpoint one real message further back.
- `stamping.js` — **how the exact counter survives the cache.** The model still needs "how far into this arc are we" on every generation, and one counter line anywhere is exactly the shape that breaks the prefix. The fix is to give every message its own counter: `buildStamp(arc, chatIndex)` returns `[Arc: message N of ~M]` where `N = chatIndex - arc.messageStart + 1` and `M = arc.estimatedLength` — a pure function of the index and fixed arc metadata, so message 67 reads "message 67 of ~80" this turn and every later turn. Old positions keep their bytes, only the appended tail is new, and the newest message carries the current number. `stampPromptMessages()` prepends the stamps on `CHAT_COMPLETION_PROMPT_READY`, mutating ST's outgoing messages array in place; stored chat (`chat[i].mes`) and the rendered UI are never touched. Details that matter:
  - **Only user messages are stamped** — half the tokens for the same pacing signal, and stamping the model's own past replies invites it to imitate the format and write `[Arc: message …]` into its prose. The cost is that the newest stamp lags on generations that follow an assistant message (Continue, or generating without typing): the model then reads the last *user* message's number, which can be a few behind. Accepted deliberately; the phase brake, not the exact count, is what enforces pacing.
  - **`focus` changes count as a lifecycle change.** The stamp comes from the pacing clock (`clock.js`), and `focus` defaults to `normal` for every new arc, so pausing or spotlighting an arc in the Arc Manager can hand every historical position a different arc's numbering. Same one-time cache miss as activating or deleting an arc, but a user hits this one far more often.
  - **Prompt entries are matched to chat indices by content suffix, not by position.** ST filters `is_system` messages out of `coreChat` (`public/script.js:4496`), `doChatInject` splices entries in, and other extensions add their own, so positions do not line up. An entry that matches nothing is skipped *without* consuming a chat index, so a foreign entry cannot shift every later number. If a regex script rewrote message text for the prompt, nothing matches and nothing is stamped — a no-op, never a wrong count.
  - **Arc lifecycle changes cost one cache miss.** Activating, completing or deleting an arc, or re-estimating its length, changes historical stamps. That is a few times per arc, and accepted.
  - **Other extensions' `generateRaw` calls fire the same event** (`public/script.js:4037`). The pass runs only on prompts containing `INJECTION_HEADER`, which only the real chat prompt carries.
  - **The plan section shows one beat and no ids.** The episode section carries a `CURRENT PRESSURE:` block holding the active beat's `pressure` text (falling back to `intention` for arcs planned before the field existed). Pending and locked beats are omitted entirely — no ids, no intentions, no teaser. Beat ids appear nowhere in the plan text at all. The old `CURRENT BEATS` list with `(NOW)`/`(upcoming)` markers turned the plan into a visible task list: live testing burned 7 of 10 non-optional beats in ~8 exchanges on an arc planned for 40 messages.
  - **Linger.** When an arc has no active beat (the gap between a completion and the next user message), the pressure block is replaced by a directive to develop consequences and introduce no new major developments.
  - `buildSignalDirective` always emits the continuation guard (never restart the scene, even when the last message is not the user's — RP presets like Celia wrap "the latest turn" at fixed depths, which mislabels the anchor when the user generates without input) and the confidentiality clause declaring the plan invisible scaffolding whose internals must not appear in any journal/summary/state-tracking block the preset requests. Both must survive linger, so neither is gated on having an active beat, and neither depends on `autoTrack` (until 2026-11-04 `autoTrack` off dropped the whole directive, guard and clause included). `autoTrack` switches automatic recognition only, and the knowledge tracker decides where beats are recognised (ADR-0008):

    | `autoTrack` | Knowledge tracker | In the signal directive | Beats recognised by |
    |---|---|---|---|
    | off | either | guard + clause | not recognised; only the Arc Manager's hand toggle completes them (the extraction lists no developments) |
    | on | off | guard + clause, BEAT CHECK, PLANT CHECK | the narrator's `COMPLETE` marker (`processSignalResults`) |
    | on | on | guard + clause, PLANT CHECK | the knowledge extraction (`fulfilled`, see "Beat Completion") |

    Both are settings, not per-message values, so the block stays byte-identical from message to message within a phase. With the tracker on the narrator never sees a fulfillment: the BEAT CHECK printed every active beat's `intention` into the prompt, and the narrator read it as a goal despite "do not steer the scene toward them" (Paragon chat, 2026-11-04: the model quoted a milestone's fulfillment as one of the "standing pressures" it was pursuing, and 7 of the prompt's 10 beat-check lines came from arcs in background focus). The BEAT CHECK block and its marker lines are gated: they appear only while a beat is active, and each line is phrased as recognition of the past (`If the story has already brought this about — "<intention>" — output exactly: …`) with an explicit "these are not instructions, do not steer toward them". Earlier phrasings were read as objectives; a bare `:COMPLETE` token was read as status and forced the active beat into every reply
- `pacing.js` — `calculatePhase(arc)` computes beat-completion ratio and message-count ratio against `estimatedLength`, takes the minimum to get a conservative phase; `getPacingDirective(phase)` returns the directive string; `selectNonOptionalBeats(beats)` is the beat filter that phase, progress card and arc completion count; `shouldShowSecret(revealPhase, phase)` is the secret gate shared by the episode section and the spotlit milestone section (moved here from the episode section in 77dbf33 so both gate identically); `phaseBoundaryMessage(arc, phase)` returns the arc-relative message number where the phase ends — it does not read `chat.length`, which is what makes it safe to put in the prompt; `messagesUntilNextPhase(arc, phase)` turns the same boundary into a countdown for the progress card's "~N msgs to next phase" line, and is UI-only now. Both return `0` — not `NaN` — when the boundary cannot be computed, which is the case for arcs planned before `estimatedLength` and `messageStart` existed (e1bc69a)
- **Clue and trigger marks (2026-10-19).** Before this, nothing ever set `planted`, `fired` or `disclosed`: a 980-message chat showed 0 of each across 6 arcs, so every clue was sent as "TO PLANT" in every message and the model kept planting it. `buildSignalDirective` now adds a `PLANT CHECK:` block with one recognition line per unplanted clue (`:PLANTED`) and unfired trigger (`:FIRED`, quoting the trigger's action) of every arc whose section shows them (`showsPlanLists`: episodes not paused, acts and sagas in spotlight — the dispatch in `builder.js`). Secrets get no line, because it would have to state the secret right before the reply; they are marked by hand in the Arc Manager. Marks are **queued** in `chat_metadata.story_arc.pendingMarks`, not applied: a marked item leaves the plan and the plant check, and any changed byte is a full cache miss (rule above). `flushPendingMarks(messageIndex, promptChangesAnyway)` runs on every received message and applies the queue when a beat completed in that message (the prompt changes anyway) or when the oldest mark has waited `MARK_FLUSH_WINDOW` = 20 messages. With the knowledge tracker on no beat completes inside the reply, so `onMessageReceived` passes `false` and only the window applies there; the extraction's apply calls `flushPendingMarks(messageIndex, true)` itself after it completed a beat (`completeFulfilledBeats` in `ledger.js`), so ADR-0005's rule holds on both paths. Until then the item stays visible and a repeated marker for it is ignored (the queue is deduplicated). A queued mark dies with its reply (2026-10-31): `index.js` listens to `MESSAGE_DELETED` (ST passes the new chat length; regenerating the last reply deletes it first) and `MESSAGE_SWIPED` (the swiped message's index), and `dropPendingMarksFrom(firstGoneIndex)` drops every mark with `at >= firstGoneIndex`, then saves. A new swipe queues its own marks through `MESSAGE_RECEIVED`. Deleting a message in the middle shifts later indices and leaves their marks queued, as before. Before this a mark from a swiped-away reply closed its trigger later anyway (Paragon chat). Any number of items may be marked per message; the one-beat-per-arc rule applies to beats only.
- `signals.js` — `parseSignals(text)` finds all `[ARC_SIGNAL:arcId:itemId:COMPLETE|PLANTED|FIRED]` tokens (the verb is returned as `verb`) anywhere in the message, bare or HTML-comment-wrapped (the directive asks for the comment form — ST's renderer hides it completely, even mid-stream; verified against `messageFormatting`: a custom tag leaves an empty `<p>`, an open/close tag leaks its inner text, a comment leaves nothing); `processSignalResults(signals, activeArcs, messageIndex)` queues the PLANTED and FIRED marks and hands every `COMPLETE` marker to `completeBeats` (`planning/beat-completion.js`) as `{ arcId, beatId, at: messageIndex }`, `at` being the index `MESSAGE_RECEIVED` delivered, not `chat.length - 1` (see Gotchas; 23649df, 9c3e980). Until 2026-11-04 the completion rules lived here; they moved so the knowledge extraction applies the same ones (see "Beat Completion"). It deliberately does **not** promote the next beat; `promoteNextBeats(arcs)` does that on `USER_MESSAGE_RENDERED`: for an episode it activates the first pending beat when none is active; for an act or saga it activates *every* pending milestone at once — validation already stores milestones `active`, so this only repairs an arc that arrived with pending ones (a re-plan merge, an old build) (77dbf33). Recording stays liberal in one direction on purpose: a completion signal is never refused for being too fast, because the signal arrives *after* the scene was written and refusing it would make the tracker disagree with the visible story. The brake is what the model can see, not what the bookkeeping accepts; `stripSignalsFromMessage()` removes tokens from both `chat[]` and the rendered DOM and trims the blank lines the marker leaves at message start; `scrubArcInternals(messageIndex, arcs)` mechanically removes leaked beat/arc ids from the saved message after marker parsing — the confidentiality clause steers the model, only the scrub guarantees it (RP presets with state-tracking blocks, e.g. Celia's `[Main-line]`, otherwise persist beat ids and next-beat agendas into history, where they steer later generations). Called with *all* arcs, not just active — past arcs' ids linger in journal recaps. Only underscore-containing ids are scrubbed; a plain-word id is indistinguishable from prose and harmless. The id list comes from the exported `arcInternalIds(arcs)` — arc ids plus beat, secret, clue and trigger ids; secret ids since 2026-10-30, after a narrator's OOC analysis printed one beside the secret's content — and the harvester uses the same list to keep such messages out of the planner's input

### lib/knowledge/

The knowledge tracker's whole process (ADR-0007), one file under the house rule "one process, one file", plus the message ids it shares with the beat completions and the taken-names derivation it shares with the reused-name flag and the planner. See "Knowledge Tracker" below for the ledger, the block and the events.

- `ledger.js` — six sections, in the order the process runs, each helper right after its first caller (AGENTS.md "One Process, One File"). Every ledger operation changes the stored ledger **in place** and returns whether it changed; callers save only then. The three update functions (`updateKnowledgeAfterReply`, `updateKnowledgeAfterSwipe`, `updateKnowledgeAfterEdit`) return a `KnowledgeUpdateResult`, `{ ledgerChanged, beatsChanged, flaggedCharacters? }` (`NOTHING_CHANGED` when they did nothing): `index.js` refreshes the status line on the first, the progress display on the second, and shows a notice per character in the third ("The reused-name flag" under "Knowledge Tracker"). `beatsChanged` is also true when the update stored a ruling, so the card shows it even when no beat changed.
  1. **Update after a reply** — `updateKnowledgeAfterReply(replyIndex)`, see "Knowledge Tracker"; then `completeFulfilledBeats(fulfilled, messageIndex)`, which runs after the apply, so the covered messages carry their message ids when `completeBeats` records the completions, and flushes the queued marks (`flushPendingMarks(messageIndex, true)`) when a beat completed; then `storeRulings(rulings)` (see "Rulings" in "Knowledge Tracker"), also after the apply and before the save; then the helpers `repliesSince` and `latestExchangeStart`.
  2. **Extraction** — `extractKnowledge(ledger, chatMessages, fromIndex, personaName)` loads `prompts/extract-knowledge.txt`, fills it from `buildKnowledgeExtractionVariables(...)` (`{{PERSONA}}`, `{{CHARACTERS}}` with aliases, `{{FACTS}}` by id with holders or "public", `{{SECRETS}}` by ref with planned holders, `{{CONTEXT_MESSAGE}}`, the latest message before `fromIndex` that is not hidden, with its index, or `(none)` (`latestShownMessageBefore`, #46), `{{MESSAGES}}` from `fromIndex` on, each with its index; hidden `is_system` messages left out), sends it through the generator's `callLlm`, and returns the parsed answer or `null` on a failed call or an unreadable answer. `listShownSecrets(arcs)` lists the active arcs' secrets the current phase shows (`shouldShowSecret`, the SECRETS block's gate), disclosed ones included, each under a `ref` unique in the call (`id`, then `id_2`, … because secret ids are unique only within an arc). `parseKnowledgeExtractionAnswer(text)` takes the answer whole or not at all: unreadable JSON, a missing key or one wrongly typed item gives `null`; a missing `revealedSecrets` or `retracted` reads as `[]`, each retracted item needs a `factId` and an integer `at`, and each revealed item needs its `secretId`, its heard `text`, `heardBy` and an integer `at`. `resolveRevealedSecrets` turns each revealed ref back into its arc, secret id and planned holders, keeps the answer's heard `text` and `at`, and drops refs the input did not list. The secret's own `content` goes into the extraction's input only, never into the resolved item. Beats (2026-11-04, ADR-0008): with the chat's `autoTrack` on, `listRecognisableBeats(arcs)` lists, per active arc that is not paused and has an active beat, its active beats under the id `<first 8 characters of the arc id>:<beat id>` (the marker's arc id) and its completed beats' fulfillments under `done`, without ids; with `autoTrack` off the list is empty. `buildKnowledgeExtractionVariables` renders it as `{{DEVELOPMENTS}}`, one `Arc "<title>":` block per arc. `parseKnowledgeExtractionAnswer` reads the answer's `fulfilled: [{ developmentId, at }]` as the one exception to all or nothing: a missing list or one of the wrong type reads as `[]`, and an unreadable item is dropped, so a broken beat report never costs the knowledge update. `resolveFulfilledDevelopments(fulfilled, developments, fromIndex, lastReadIndex)` turns each item into `{ arcId, beatId, at }` for `completeBeats`, and drops an id the input did not list as an active beat and an `at` outside the messages the call read; `lastReadIndex` is taken before the call, so a message sent during it is never a fulfilling one. Rulings (2026-11-04, #40; ADR-0008 amendment): `listArcPlans(arcs)` lists every active arc that is not paused, whether or not it has an active beat and whatever `autoTrack` says, with its short arc id, title, premise and the `pressure` of every beat not completed (a beat without a pressure adds none); `buildKnowledgeExtractionVariables` renders it as `{{PLANS}}`. The answer's `rulings: [{ arcs, quote, chose?, at }]` is read as tolerantly as `fulfilled`; a `chose` that is absent, null or blank is none, one that is not a string drops the item. `resolveRulings(rulings, arcPlans, chatMessages, fromIndex, lastReadIndex)` drops, with a warning, an `at` outside the read messages, a message there that is hidden or not the player's, a quote not in that message (`findQuoteInText`: ignoring case, whitespace collapsed; it returns the span as it stands in the message, so the stored text is the player's own) a `chose` found neither in the context message nor in a narrator message (not the player's, not hidden) among the read messages (`findOptionInMessages`, same comparison), and a ruling with no listed arc id left; it returns `{ arcIds, text, chose?, at }` with full arc ids and the option as found.
  3. **Apply an extraction answer** — `applyExtractionAnswer(ledger, answer, fromIndex, messageIndex)` covers the messages `fromIndex…messageIndex`. New characters first (ids `c<n>`), then the learned items: a known fact id adds holders; a text joins the fact with the same text (`findFactWithSameText`: equal ignoring case, runs of whitespace and a trailing full stop; facts in the ledger and those created earlier in the same answer) and creates a fact (`f<n>`) only for new text; names match case-insensitively against names and aliases, and unknown names and fact ids are ignored. The teller (`toldBy`) of a `told` item becomes a `witnessed` holder of the fact at the same `at`, unless they hold it already: the prompt leaves out characters who already know, and without this a talked-about teller printed "Does not know" next to "Has told only Ellie". An item's `at` outside `fromIndex…messageIndex` falls back to `messageIndex` (`atInsideCoveredMessages`), so a regeneration, a delete or the next edit of that message always takes it back. A revealed secret creates or extends the fact linked to it (`fact.secret = { arcId, secretId }`), worded with the heard `text` (a later reveal adds holders and keeps the first wording), with the characters who heard it as `witnessed` holders and its planned holders as `plan` holders, all at the reveal's own `at`. Then the retracted ids: a known fact without a user-entered holder moves to `retractedFacts` with the correction's `at` (see "Knowledge Tracker"). `present` replaces the scene; the scene it replaces goes into `sceneHistory` (`keepSceneInHistory`: only a scene from an earlier message, never the empty one before the first update; the newest `KNOWLEDGE_SCENE_HISTORY_CAP` = 10 are kept), and `lastUpdatedAt` becomes `messageIndex`. Helpers: `findCharacterId`, `nextLedgerId(prefix, entries)` (one above the highest number in use; exported for the popup), `findCharacterIds` (names to unique ids), `findFactWithSameText` with `normalisedFactText`, `addHolderUnlessHeld`. Given the chat as a fifth argument (both update paths pass it), `assignCoveredMessageIds` gives the covered messages a message id, and every holder entry at a covered index (in retracted facts too), a retraction, the scene and `lastUpdatedAt` get that id as `messageId` / `lastUpdatedMessageId`.
  4. **Roll back after a delete, a swipe, an edit or a branch load** — `rollBackKnowledgeFrom(firstGoneIndex)` first calls `followMessagesById(ledger, chat)` (entries with a message id, retractions and retracted facts' holders included, move to their message's new index or go with it; a retraction whose correcting message is gone gives its fact back; `messageIdOf`, `latestMessageWithId`), then `dropKnowledgeFrom(ledger, firstGoneIndex)`, the index rule for entries without one: holder entries with `at >= N` go, a fact left without holders goes, `at: null` entries stay; a scene from a dropped message goes back to the latest scene in `sceneHistory` before message N, and becomes `{ at: null, present: [] }` only when there is none (a ledger stored before the history has none); history entries at N or later go; and `lastUpdatedAt` goes back to `N - 1` (`null` for N = 0). It only rolls back data. The prompts are rebuilt by `onMessageDeleted` in `index.js`, which calls `injectStoryArcPrompts()` (plan, signal and knowledge injections) after its drops and rollbacks: a regenerate fires GENERATION_STARTED, where the prompts are first built, while the old reply is still in the chat, and deletes it only afterwards. Without the rebuild the new reply was told what the replaced one taught (2026-11-01), lacked the pressure of a beat the deletion reopened, and had its phase counted one message too far (2026-11-04). ST awaits each MESSAGE_DELETED listener before it assembles the prompt, so the rebuild runs inside the handler. Same pattern as `dropPendingMarksFrom` for queued marks. `keepOnlyHolders(ledger, isKept)` is the one holder-dropping loop, shared with `dropKnowledgeLearnedAt`; it first puts back every retracted fact whose retraction `isKept` rejects, and takes the rejected holder entries out of the facts that stay retracted too (a retraction left without holders goes), so an edit of the message a retracted fact came from and a later rollback of the correction do not bring the fact back with holders from the old text; `reachesMessage(storedIndex, messageIndex)` is the "not null and at or past message N" check. Then `updateKnowledgeAfterSwipe(messageIndex)` with the private `reextractKnowledgeOfMessage` (which completes the beats its answer reports, like the update after a reply), and `updateKnowledgeAfterEdit(messageIndex)` with the private `dropKnowledgeLearnedAt`; with `autoTrack` on, the edit first reopens the beats completed at that message (`reopenCompletionsAt`), so the re-extraction judges the edited text against an open beat; see "Knowledge Tracker".
  5. **Inject the knowledge block** — `listStoryArcPrompts()` (`injection/narrator-prompts.js`) lists `story_arc_knowledge` and then `story_arc_names` (`buildTakenNamesBlock` from `names.js`), and `injectStoryArcPrompts()` (index.js) sets them every time: the blocks while Story Arc and the tracker are on, `''` otherwise, so no stale block lingers. (`injectKnowledgeBlock()` did this until #83, 2026-11-12.)
  6. **Build the knowledge block** — `buildKnowledgeBlock(ledger, messages)` returns the block text or `''`; `KNOWLEDGE_LIST_CAP` = 5. Format and rules under "Knowledge Tracker" below. `characterName(ledger, characterId)` is exported for the Knowledge popup.
- `message-ids.js` — Story Arc's own stable id on a chat message (`MESSAGE_ID_KEY` = `'story_arc_message_id'` in `extra`), in its own file since 2026-11-04 because the ledger and the beat completions (`planning/beat-completion.js`) both name their message by it. `assignCoveredMessageIds(chatMessages, fromIndex, lastIndex)` gives every message an update read an id unless it has one (hidden messages none); `messageIdOf(chatMessage)` reads it. Only the extraction gives ids; `beat-completion.js` only reads them.
- `names.js` — the taken names (issue #39): `buildTakenNamesBlock(ledger)` for the injection, `printTakenNames(ledger)` (the sorted printed list that block and the planner's cast block share, #44), and the derivation underneath, `listTakenNames(ledger)`, `nameWords(name)` and `foldName(name)`, exported for the reused-name flag (#35, which also uses `listCharactersWithNames(ledger, names, exceptCharacterId)` for its notice) and the planner with its plan check (#36). Pure, imports nothing; its own file because those callers sit outside the ledger and the generator cannot import `ledger.js` without a cycle. See "The taken-names block" under "Knowledge Tracker".

## Phase System

Five phases, each with a 0–1 percentage range applied to both beat-completion ratio and message-count ratio. The current phase is whichever of the two ratios is lower (conservative — do not rush ahead).

| Phase | Range | Pacing Directive |
|-------|-------|-----------------|
| Setup | 0–20% | Plant seeds. Build atmosphere. No revelations. No confrontations. |
| Development | 20–50% | Tensions grow. Complications deepen. Hints become patterns. |
| Escalation | 50–75% | Stakes rise sharply. Confrontations can begin. Secrets start surfacing. |
| Climax | 75–90% | Major beats resolve. Secrets revealed. Decisive moments. |
| Resolution | 90–100% | Aftermath. Emotional processing. Seeds for the next arc. |

## Signal Protocol

When `autoTrack` is enabled, a dedicated injection (`story_arc_signals`, IN_CHAT depth 0 — the last message the model sees before generating) instructs the AI to emit markers: `PLANTED` and `FIRED` for clues and triggers (the PLANT CHECK), and, only while the knowledge tracker is off, `COMPLETE` for beats (the BEAT CHECK):

```
<!-- [ARC_SIGNAL:<arcId-prefix>:<beatId>:COMPLETE] -->
```

With the tracker on, beats are recognised by the knowledge extraction instead, and the narrator never sees a fulfillment (ADR-0008; see "Beat Completion"). The marker parsing below runs on every reply whatever the switches, so a `COMPLETE` marker the narrator writes without being asked is still applied to an active beat.

The HTML-comment wrapper makes the marker invisible in ST's renderer even while it streams in; the bare form (without the wrapper) is still parsed for messages written before the change. Only the first 8 characters of the arc UUID are used in the signal to keep it compact. The model is told to put the marker on the **first** line of its reply, not the last — end-of-message markers get eaten whenever the response hits the token cap. On `MESSAGE_RECEIVED`, `parseSignals()` scans the whole message, `processSignalResults()` resolves the full arc by prefix match (for a `COMPLETE` marker through `completeBeats`), `stripSignalsFromMessage()` removes the tokens (and their leftover blank lines) before the user sees them, and `scrubArcInternals()` deletes any beat/arc ids the model leaked elsewhere in the message — journals and state-tracking blocks from RP presets otherwise carry plan internals (spoilers, next-beat agendas) into saved history.

Directive placement is the load-bearing detail (27c3d17): with the directive in the system prompt (or even one message back from the end), GLM 5.2 reasoned about beats in its chain-of-thought and still never emitted a marker. Depth 0 produced compliance. Emission remains stochastic per message — acceptable over a 40-message arc, since beats only need to complete eventually.

## Beat Completion

A beat completes when the story is recognised to have fulfilled it (2026-11-04, ADR-0008). There are two recognition paths, chosen by the knowledge tracker's switch (`autoTrack` off turns both off; see the table under `buildSignalDirective`):

| | Tracker off | Tracker on |
|---|---|---|
| Who recognises | the narrator, in the reply it writes | the knowledge extraction, after the reply |
| What it sees | the BEAT CHECK: each active beat's `intention` in the narration prompt | `{{DEVELOPMENTS}}` in `extract-knowledge.txt`: each active beat's `intention` by id `<arc8>:<beatId>`, the arc's completed beats under `done` |
| What it reports | `<!-- [ARC_SIGNAL:<arc8>:<beatId>:COMPLETE] -->` on the reply's first line | `fulfilled: [{ developmentId, at }]` (task 6, FULFILLED: only what happens on screen, OOC lines fulfil nothing, when in doubt leave it out) |
| Caller | `processSignalResults` (`signals.js`), `at` = the reply's index | `completeFulfilledBeats` (`ledger.js`), `at` = the message the answer names, inside the messages the call read |
| When | in `onMessageReceived`, before the next generation | a few seconds after the reply, or up to `updateInterval` replies later; also after a swipe switch or an edit (the single-message re-extraction) |

Both paths call `completeBeats(completions, arcs)` in `lib/planning/beat-completion.js`, so the rules are the same:

- the arc must be found and `active`, the beat must exist and be `active`; a pending, locked or unknown beat is a hallucinated id or a stale report and is ignored (logged);
- the completions are applied in the order of their messages (`inOrderOfMessages`, earliest `at` first, stable), so a later milestone's completion never skips an earlier one the same answer reports fulfilled earlier;
- one completion per arc per message (`at`), within one message the first in the list wins; independent arcs may each advance in the same message;
- `lastFulfilledAt` becomes `at`, unless a later completion set it already (an edited earlier message completed again); locked beats whose prerequisites are now all completed become pending (`completeBeat` in `arc-edit.js`, the Arc Manager's toggle uses the same function); an arc with no open non-optional beat left completes (`isBeatOpen`: neither completed nor skipped);
- in an act or saga every earlier open milestone becomes `skipped` at the same message (`skipEarlierMilestones`, ADR-0010): the story moved past it. A skipped milestone is not active, so it leaves recognition and cannot be completed any more; a second claim for it in the same answer is ignored. Completing the last milestone with earlier ones open skips them and completes the arc. The Arc Manager's hand completion skips the same way and records only that, `completion: { byHand: true, skipped }`, which no rollback reopens; setting a completed milestone back by hand gives back what its completion skipped. A skipped milestone is given back only when no other completion that still stands lists it as skipped (`restoreSkippedMilestones`), so each standing completion keeps owning its skips. Episodes never skip;
- no promotion: the next scene beat waits for the next user message (`promoteNextBeats`).

**Fulfillments are one on-screen moment.** The extraction reads only the messages since its last update, usually one user message and one reply. A fulfillment that is a tally of many scenes ("has completed her first patrols") or a chain of separate events joined by "and" never shows in such a window; the narrator did not recognise one either (`rookie_beats_and_sidekick_drills` stayed active for 439 messages in the Paragon chat with the whole chat in context). The generator asks for one moment (`generate-arc.txt`, `buildTierBlock`, `detail-pass.txt`) and the plan check rewrites tallies and chains (see `generator.js` above). Existing arcs get one-moment fulfillments when they are re-planned; there is no migration. Marking beats complete by hand is not a recognition path; the Arc Manager's toggle stays an override.

**The completion record.** A completion with an `at` stores `beat.completion = { at, messageId?, unlocked, skipped, arcCompleted, lastFulfilledBefore }` (`completionRecord`): the message by index and, when it carries one, by Story Arc message id (the id the knowledge ledger uses, `lib/knowledge/message-ids.js`), and what reopening the beat has to undo. The id is only read, never given: the ledger relies on only the messages an update read carrying one (`followMessagesById`). With the tracker on, the extraction gave the message its id before its completions are applied. With the tracker off, or for a hidden message, the record names its message by index only.

**Rollback.** Before 2026-11-04 a completed beat was never reopened: a swiped-away reply that completed a beat kept it completed. Now:

| Event | Call | What happens |
|---|---|---|
| `MESSAGE_DELETED(newChatLength)` (also the last reply before a regeneration) | `reopenCompletionsFrom(newChatLength)` in `index.js`, then `updateProgress()` and a save when it changed anything | a record with a message id follows its message: it moves to the message's new index while the message is in the chat, and is reopened when the message is gone; then every record at `newChatLength` or later is reopened |
| `MESSAGE_SWIPED(mesId)` | `reopenCompletionsFrom(mesId)`, before the knowledge rollback (which strips the swiped message's id) | the swiped message's completions are reopened. ST awaits the handler before it generates a new swipe, so the new reply's prompt shows the reopened beat and may complete it again. Switching to an existing swipe re-extracts it (tracker on); its markers were stripped when it arrived, so the in-prompt path does not complete its beats again |
| `MESSAGE_EDITED(id)` | `reopenCompletionsAt(id)` inside `updateKnowledgeAfterEdit`, tracker and `autoTrack` on only | the completions at exactly that message are reopened, matched by message id when the message and the record carry one, else by index; the re-extraction completes them again if the edited text still fulfils them. Without an applied answer (a failed call, the chat or the message changed meanwhile) the arcs are put back exactly as they were before the reopen (a `structuredClone` taken right before it), unless they changed during the call: then they stay (2026-11-11; completing the beats again instead left a promoted beat pending, and offering them as open without reopening re-implemented the reopen badly) |
| `CHAT_CHANGED` | `reopenCompletionsFrom(chat.length)` before the ledger rollback | ST copies the chat metadata whole when it branches; a branch that ends before a completing message reopens its beat |

Next to each call, the arcs' rulings follow their message by the same rules (#45): `removeRulingsFrom` on delete and chat change, `removeRulingsAt` in `updateKnowledgeAfterEdit` (tracker on, whatever `autoTrack` says; only the rulings whose quote is gone from the edited text), none on a swipe; see "Rulings" in "Knowledge Tracker".

Delete, swipe and branch load reopen completions with the tracker off too. Reopening a beat (`reopenCompletion`) undoes what its completion did: the beat is `active` again; in an episode a later beat promoted meanwhile goes back to `pending` (one scene beat is active at a time); a beat it unlocked that is still `pending` is `locked` again, so an unlocked scene beat promoted meanwhile ends up locked too; a milestone it skipped that is still `skipped` is `active` again unless another standing completion's record lists it too (one set by hand since stays as set); an arc it completed is `active` again. Several completions of one arc are reopened latest first. Then `restoreLastFulfilledAt` sets the arc's `lastFulfilledAt` to the latest remaining recorded completion or to the earliest reopened record's `lastFulfilledBefore`, whichever is later; that value covers what has no record (`messageStart`, a completion by hand or from before the records), and a record without it (an arc from before `lastFulfilledAt`) falls back to `messageStart`. A completion without a record is never touched. The reopen functions are synchronous and do not save; the caller saves when they return true.

**Limits.** A record without a message id has only the index rule: a deletion in the middle of the chat before the completing message leaves `at` one off, and deleting the completing message itself in the middle of the chat does not reopen the beat. With the tracker off, an edit reopens nothing (nothing would complete the beat again). An unreadable extraction answer loses both the knowledge update and the completions for that window; the next update reads the same messages again. A user message sent while the extraction runs is built with the beat still active, so its pressure stays one message longer. The extraction judges messages it did not write and does not see the plan, so it may recognise a single-event beat more strictly than the narrator did. An arc that is never re-planned keeps its old tally and chain fulfillments, which the extraction will not recognise.

## Pacing Enforcement

Prompt-side pacing ("do not advance for N more messages") was demonstrably ignored, so the brakes are mechanical and sit on what the model can *see*:

1. **Information hiding** — the plan text shows one beat, as a pressure, with no id. A model cannot race toward objectives it was never given.
2. **Pressure/fulfillment split** — the plan shows the beat as weather (`pressure`, no completion state). The fulfillment condition (`intention`) reaches the narrator only through the BEAT CHECK, phrased as recognition of the past, and only while the knowledge tracker is off; with it on, only the extraction sees it (ADR-0008). An outcome-phrased beat is a solvable, and models are trained to solve visible goals in one scene and then parrot the solution into dialogue. The recognition phrasing was not enough: the narrator still read beat-check fulfillments as goals (Paragon chat, 2026-11-04).
3. **Active-only, one per arc per message** — the backstop in `completeBeats` against one eager scene burning several beats.
4. **Promotion on the next user turn** — after a completion the arc is left with no active beat until `USER_MESSAGE_RENDERED`. The AI's own aftermath prose and empty-input continues cannot chain into the next objective; the player reacts to a development before the model learns what follows.

Promotion is reactive, not clocked. A message-budget hold was considered and rejected: scenes must react to the roleplay, not to a round counter, and a clock detaches the plan from an unforeseen story direction. The accepted consequence is that an arc "planned for 40 messages" can finish sooner if the model keeps fulfilling beats and the player plays along — `estimatedLength` feeds only the advisory phase wording, and the real pace is set by the player's turns.

## Tiers and Focus

Multiple arcs can be active simultaneously. Tier owns an arc's shape, focus owns its prominence (ADR-0001, `CONTEXT.md`). The tier is chosen in the wizard at generation and only grown by re-plan (episode → act → saga, never smaller); the focus is set by hand in the Arc Manager at any time.

### Injection matrix — what `buildArcSection(arc)` picks

`builder.js` looks at focus first, then tier (`arc.tier || 'episode'`, so an arc without a tier is an episode):

| | Episode | Act / Saga |
|---|---|---|
| `paused` | `paused.js`: one line under `=== PAUSED:` — premise + "pending, not being pursued right now". No beat check line; clock frozen | same one line; no beat check |
| `background` | not offered (ADR-0001 amendment); re-plan never shrinks an act or saga into an episode (ADR-0003 amendment) | `background.js`: `=== BACKGROUND:` title + "Runs off-screen…" sentence. No premise, pressures or lists; milestones stay recognisable (beat check or extraction); clock runs |
| `normal` | `episode.js`: full section (world facts, `CURRENT PRESSURE` of the one active beat, pacing rules, gated secrets, triggers, foreshadowing). Pacing-clock candidate | `milestone.js`: `=== ACT:`/`SAGA:` header, premise, up to three world facts, the current milestone's pressure under `STANDING PRESSURE (…)` (ADR-0010). No secrets, triggers or foreshadowing, no brake, no clock, no phase line |
| `spotlight` | `spotlight.js` → the same full section, byte-identical; the arc **is** the pacing clock and is ordered first | `spotlight.js` → the milestone section with the current milestone's pressure under `BRING TO A HEAD:` + one trailer sentence, then gated secrets, triggers, foreshadowing; ordered first so budget trimming never drops it. No milestone is named as a target (ADR-0002) |

Section order (`sectionRank`): spotlight first, then normal episodes, then everything else (normal acts and sagas, background, paused) — storage order within each group. The in-chat block is the same for every tier: `ARC PACING` names only the pacing clock; the recognition set (the BEAT CHECK with the tracker off, the extraction's `{{DEVELOPMENTS}}` with it on) is every `active` beat of every non-paused arc, which for an act or saga means every open milestone, not only the current one. The phase (`calculatePhase`) feeds the brake boundary, secret gating and the progress card on an episode (the stamps do not depend on it); on an act or saga it feeds secret gating (spotlight only) and the progress card (phase label and the "~N msgs to next phase" line) only — `calculatePhase` itself is tier-blind.

### Milestones — order, the current one, and skipping

An arc is one plot thread (ADR-0010, the player's ruling of 2026-11-09, which replaced the unordered milestones of the 2026-09-16 design). Its milestones run in the planner's order. `validateArcPlan` stores every milestone `active` with `unlockAfter: []`, so recognition can fire for any open one in any message from the first one on; `promoteNextBeats` keeps that invariant after a re-plan merge. The narrator gets only the **current** milestone's pressure: `currentMilestone(arc)` in `settings.js`, the first open one (`isBeatOpen`) after the last completed one in stored order. An open milestone before a completed one is **passed** (a rollback, an edit or a hand change can leave one): never current, its pressure never printed, but still active and so still recognisable. With no open milestone after the last completed one there is no current one and no pressure block. "Current" is derived, not stored, so arcs stored before the rule (every milestone active) need no migration, and the next milestone presses as soon as the current one closes; there is no promotion gap as for scene beats. When the story fulfils a later milestone first, it completes and every earlier open one becomes `skipped` (see "Beat Completion"); the next open one after it is current. A skipped milestone counts like a completed one for the phase (`calculatePhase`), the Arc Manager's "every milestone done" note and arc completion; the extraction's ruling check (`listArcPlans`) leaves its pressure out. The cap of one completion per arc per message still holds. A milestone is never shown to the model as its fulfillment (7ed5b1e, issue #13): the milestone and spotlight sections print only `pressure`, and print no pressure block for a current milestone without one rather than substituting its intention or the next milestone's pressure, and `validateArcPlan` rejects an act or saga whose milestone lacks a `pressure` — one error per beat naming its id, through the same errors path the wizard already shows with Regenerate. The `pressure || intention` fallback inherited from pre-2026-08-29 episodes was removed here because it could print a past-tense fulfillment as a standing pressure, which under `BRING TO A HEAD` is exactly the named target ADR-0002 forbids. The episode fallback stays. The generator's tier block tells the model that a milestone's fulfillment names the on-screen moment at which the story shows it has reached a *state*, not a specific scene, a tally of scenes or a chain of events, so it can be recognised whatever route the story took and from the one or two messages the extraction reads (2026-11-04).

### Pause — the clock freezes and shifts

`pauseArc(id)` writes `focus: 'paused'` and `pausedAt = chat.length` (an already paused arc keeps its original freeze point, so the span it sat out is never shortened). `resumeArc(id, focus)` on a paused arc adds `chat.length - pausedAt` to `messageStart`, to `lastFulfilledAt` and to `replannedAt` (when present) and clears `pausedAt`, so the stamp number and the phase continue where they stopped: paused at chat length 100 on "message 12 of ~20", resumed at 115, the next user message still stamps "message 12" (pinned by `tests/test-clock.js`). On an arc with `pausedAt == null` it only writes `focus` — the Arc Manager routes every normal ↔ spotlight change through it too (b7bde8a). Shifting `messageStart` re-numbers every historical stamp: one prefix-cache miss, the same class as any focus change.

### Spotlight — the world moves, nothing is named

Spotlighting an episode changes nothing in its section; it makes that episode the pacing clock and orders it first. Spotlighting an act or saga moves its current milestone's pressure into the main block under `BRING TO A HEAD:` with the trailer "Let this pressure intensify over the coming scenes, and let the world act on its own interests." (one pressure since ADR-0010). The obvious wording — "choose one of these and steer toward it" — is the goal instruction the 2026-08-29 pacing work found to be poison, so no milestone is ever named (ADR-0002). If live play shows spotlight is too soft, the next step is a tempo phrase ("within the next few scenes"), not a target; the trailer is a standalone sentence rather than a header parenthetical so that phrase is a one-line change (fcc104f).

## Re-plan

Re-plan regenerates the unfulfilled part of an active arc from the story's current state, keeping its identity, its secrets and its fulfilled beats (ADR-0003, spec §3). Entry points: the Arc Manager's Re-plan button (closes the manager, then `showWizard(arcId)` — nested ST popups stack badly) and the stall nudge on the progress card (`showWizard(arcId)` directly from the drawer; from the wand popup after it has closed, #72).

Neither input is mutated. Pinned by `tests/test-replan.js` (e3b81d8, b864ac1).

## Stall Nudge

A stall is the measurable sign of divergence: an arc going roughly three times its expected per-beat length without a fulfillment (GLOSSARY "Stall"). For an act or saga that is its current milestone not moving: the current one changes only through a completion, its own or a later one's that skips it (ADR-0010), and every completion sets `lastFulfilledAt`, so the rule needed no change. `isStalled(arc, chatLength)` in `progress.js`, for every tier (#41, 2026-11-04): not while paused or in background focus, `chat.length - max(messageStart, lastFulfilledAt, replannedAt, reactivatedAt) > 3 × estimatedLength / nonOptionalBeatCount`; an act's or saga's non-optional beats are its milestones. An arc without a non-optional beat or without `estimatedLength` never stalls. `lastFulfilledAt` is the chat index of the fulfilling message, so after N further messages the difference is N + 1: a 20-message episode with six non-optional beats nudges at N = 10 and not at N = 9 (pinned by `tests/test-stall.js`). A missing or `0` `lastFulfilledAt` counts from `messageStart` (`Math.max`), so a migrated episode is not nudged the moment it loads. An act of length 90 with four milestones, last fulfilled at 2225, is not stalled at chat length 2292 and stalled at 2293 (67.5 allowed). `applyReplan` stamps `replannedAt`, so a freshly re-planned arc shows no nudge; it is a field of its own because the rollback below sets `lastFulfilledAt` back before the re-plan, and the stamp cannot be moved by it. A chat shortened by deletions below the stamp counts negative: nothing lights until it grows past it again. Pausing does not count: resume shifts `lastFulfilledAt` by the paused span, and `replannedAt` by the part of the pause after the stamp, so a re-plan applied during the pause counts from the resume (`replannedAt + chat.length − max(pausedAt, replannedAt)`: re-planned at 1200, paused since 1000, resumed at 1300 gives 1300; re-planned at 900 gives 1200). A background arc's clock runs, so an arc brought back to normal focus may light at once. `completeBeats` sets it, and reopening a completion sets it back (`restoreLastFulfilledAt`), so a swiped-away fulfillment no longer resets the stall count.

**Arc capabilities for the Arc Manager (2026-11-05, #69).** Three functions the redesigned Arc Manager calls; tests in `tests/test-clock.js`, `tests/test-stall.js`, `tests/test-beat-completion.js`, `tests/test-arc-edit.js`.
- *Reactivate* (`reactivateArc(arcId)` in `clock.js`): a completed or abandoned arc becomes `active` in `normal` focus, whatever focus it ended in, so it never takes the spotlight from the arc holding it; an arc that ended while paused resumes through `resumeArc`, so its clock shifts by the paused span. It stamps `reactivatedAt = chat.length`, a third start of the stall count next to `lastFulfilledAt` and `replannedAt` (same reason as `replannedAt`: `lastFulfilledAt` keeps its one meaning), shifted on resume by the same rule as `replannedAt`. The beats are not touched: a completed arc comes back with its beats completed, for the player to re-plan or set back by hand. An active arc is left as it is. Since #71 (2026-11-06) it also sets `messageStart = chat.length`: the phase count, the phase brake and the stamps start over, where before a long-ended arc came back straight into resolution (found in the mockup).
- *Done by hand counts for pacing* (`setBeatStatusByHand(arcId, beatId, status)` in `beat-completion.js`, the Arc Manager's status toggle). ## Knowledge Tracker

Story Arc keeps a knowledge ledger per chat: which character knows which fact, and how they learned it (ADR-0007, spec issue #2). A short block close to the bottom of the prompt tells the narrator what everyone knows and what the characters in the scene, and the characters the scene talks about, know. It never says what a character does not know. It exists because a rule against omniscience names no fact and loses to the scene; a concrete "Gabriel has told only Ellie" leaves the narrator no reason to invent an off-screen phone call. The process lives in `lib/knowledge/ledger.js`.

**Rulings (2026-11-04, #40, ADR-0008 amendment).** The extraction also gets the plans of the active, non-paused arcs (`== PLANS OF THE STORY ARCS ==`: short arc id, title, premise, open pressures, no genre, no ids on pressures) and task 7, OVERRULED: an out-of-character line of the player that says the story must differ from a listed premise or pressure is reported with the arc ids, the exact quote and the player's message index. Scene-level requests and new direction that contradict nothing listed are not rulings. A checked ruling (`resolveRulings`) is stored by `storeRulings` on each arc it names, after the ledger apply and before the save, in the update after a reply and in the re-extractions after a swipe switch and an edit. A ruling whose text and chosen option (`chose`, both compared like a quote) match an open ruling of the arc is skipped, so two "Option one" picks against different option sets are two rulings, and so is one the arc holds already from the same message with the same text. The update log records `answer.rulings` (resolved) and `rulingsStored`, never the text. Only while the tracker is on; rulings do not follow `autoTrack`. A ruling follows its message like a completion record (2026-11-04, #45; `removeRulingsFrom`, `removeRulingsAt` in `beat-completion.js`): open and answered rulings go when their message is deleted (by message id when the ruling has one, and a ruling whose message is still in the chat moves to its new index; otherwise by the index rule), when a branch is loaded that ends before it, and when the message is edited so that the ruling's quote is no longer in its text, before the edit's re-extraction reads it again: `removeRulingsAt(messageIndex, isStillStated)` takes the quote check from `ledger.js` (`findQuoteInText` on the edited text; `beat-completion.js` cannot import `ledger.js` without a cycle). A ruling whose quote is still found stays as it is, with its `answeredAt`, `chose` and `at`, so a typo fixed elsewhere in the message neither reopens an answered ruling nor loses it, and the re-extraction's repeat check skips it (review fix, 2026-11-04); one the player edited out is gone, and a changed quote the re-extraction reports is stored as a new open ruling. The edit removal runs only where the edit re-extracts (tracker on, message read), whatever `autoTrack` says. A swipe removes no ruling: it replaces the narrator's reply, not the player's message before it. The progress card refreshes after a removal.

**A ruling given as a bare pick (2026-11-04, #46).** The narrator offers options out of character and the player answers in the next exchange with a bare pick ("Option one"); at the default update interval the two arrive in two windows. The extraction therefore also gets the context message, `== MESSAGE BEFORE THE NEW MESSAGES ==`: the latest message before its window that is not hidden, with its index, labelled as already read; nothing may be reported from it except as the options a ruling picks from. A ruling item may carry `chose`, the picked option copied exactly from the narrator's message. The `quote` must still be the player's text inside the window; the `chose` must be found in the context message or in a narrator message inside the window before the pick's message (`findOptionInMessages`: the options always come before the pick, so a later reply, even the one being swiped, never counts), else the ruling is dropped with a warning. The stored ruling keeps `chose` as found. It costs one more message of tokens per extraction and no call. The re-extraction of an edited message reads the message before it as its context message too.

**Optional, off by default.** `extension_settings.story_arc.knowledgeTracker = { enabled: false, updateInterval: 1, characterDetails: false, appearance: false }` (`characterDetails`: see "Character details", "The switch"; `appearance`: see "Appearance"). While the switch (or Story Arc itself) is off there is no extraction call, the knowledge block and the taken-names block are `''`, the SECRETS lines carry no holders, and the Knowledge buttons are not shown, so the injection is byte-for-byte what it was before the tracker, the beat check included (pinned by `tests/test-knowledge-secrets.js` and `tests/test-knowledge-inject.js`). Rollbacks still run while it is off (below), so knowledge from text that is gone does not come back when it is switched on.

**The ledger** lives at `chat_metadata.story_arc.knowledge`, next to the arcs, so branches, exports and backups carry it (a side file was rejected in ADR-0007). Shape of record: `createEmptyKnowledgeLedger()` in `constants.js`.

```javascript
knowledge: {
    characters: [{ id, name, aliases: [name],              // ids c1, c2, …
                   nameClash?: { names: [name], at, messageId? },   // only on a record flagged
                                                          // for a taken name (below)
                   details?: { gender?, age?, role?, relation?, status?: [{ value, at, messageId? }] } }],
                                                          // character details (below): one history per
                                                          // kind, oldest first; absent kind = unknown
    facts: [{
        id, text,                                         // ids f1, f2, …
        public: boolean,                                  // known to everyone; never printed
        secret?: { arcId, secretId },                     // only on a fact an arc's secret became when revealed
        holders: [{ characterId,
                    how: 'witnessed' | 'told' | 'user' | 'plan',     // HOLDER_HOW
                    toldBy: characterId | null,           // for how 'told'
                    at: messageIndex | null,              // null = entered by the user, survives every rollback
                    messageId? }],                        // the message's Story Arc stamp (below)
    }],
    scene: { at: messageIndex | null, messageId?, present: [characterId] },   // from the last extraction
    sceneHistory: [{ at: messageIndex, messageId?, present: [characterId] }], // earlier scenes, oldest first,
                                                          // newest 10; missing in older ledgers = empty
    retractedFacts: [{ at: messageIndex, messageId?, fact }], // facts an OOC correction at `at` took back, whole;
                                                          // missing until the first retraction = empty
    lastUpdatedAt: messageIndex | null,                   // last message the ledger covers
    lastUpdatedMessageId?,                                // that message's stamp
    reviewedMarks?: [itemKey],                            // change items the player reviewed (below)
    pendingReextractions?: [{ messageId, tries, textHash, offeredBeats }], // edited messages whose re-extraction call
                                                          // failed, retried after reply updates (Rollback)
    updateLog: [record],                                  // newest 20, oldest first; missing until the
                                                          // first record = empty (below)
}
```

The ledger stores only who knows, and the block states only who knows (issue #21). Holder entries record the message, not the swipe: a swipe takes the message's knowledge back and the shown text is extracted again. The extraction writes `witnessed`, `told` and (for a revealed secret's planned holders) `plan`; the popup writes `user` (the values are `HOLDER_HOW` in `constants.js`). A public fact is a flag on the fact, not a holder value. The teller of a `told` item is a `witnessed` holder too (whoever tells a fact knows it). So is the actor: the extraction prompt has a character who did, caused or planned what a fact describes listed among its holders (`witnessed`), even when absent. Only for the deed as they did it: a routine act they would not remember does not count, and what others found out about them is a fact they do not hold (2026-11-01: Diana became a holder of "Vera knows Diana from her signature on Lucas's file", and the block told the narrator she knew it). In the 2026-11-01 live check the player told Amy that Mara rewrote her diagnostic logs; Mara was left out, and the block printed "MARA (talked about, not present)" with "Does not know" for her own deed. The prompt also asks for fact text that states the fact itself, not who else knows it (a live fact ended "…, and nobody else knows except Ellie."). In the second live check one answer wrote "Mara from the night shift rewrote Amy's diagnostic logs." twice, as the actor's own item and as the item of those Steve told; two facts with one text printed both "Knows" and "Does not know" for Mara. Applying the answer now joins learned items with the same text into one fact, and the prompt asks for a ledger fact's id over new text when the same knowledge is meant and for each fact once. The same check got 9 facts from one reply, mostly sensations ("Amy can feel the vibration of Steve's phone in her throat like a heartbeat"); the prompt now records only knowledge a character could act on or wrongly reveal (secrets, plans, identities, who did what, private information, things told in confidence), not small talk, sensations, descriptions, moods or what anyone in the scene can plainly see. One fact holds one piece of knowledge (issue #23): the extraction once joined "Ellie Masters is sitting on over a million dollars and intends to bring Vera Lin onto Lucky Strike's payroll" into one fact; Vera later learned only the second half and could not become its holder. The prompt now puts knowledge that different characters can learn at different times into separate facts. Every `at` the extraction writes lies inside the messages its call covered.

**Extraction after a reply.** `onMessageReceived` calls `updateKnowledgeAfterReply(replyIndex)` after signal processing, so the extraction reads the reply without its markers, and does not await it: ST awaits its listeners, and the extraction must not hold up the next generation. A prompt built while it runs uses the ledger as it is. The update runs when at least `updateInterval` AI replies (hidden messages not counted) arrived since `lastUpdatedAt`, and reads every message from `lastUpdatedAt + 1` to the reply. A ledger never updated (`lastUpdatedAt: null`) reads only the latest exchange, the reply and the user message before it: a long chat's history is not backfilled. One extraction at a time (`knowledgeUpdateRunning`); a reply arriving meanwhile starts none, and the next update covers its messages. When the answer is back it is dropped if the chat changed (`chat_metadata.story_arc` is another object), the reply's text changed (a swipe) or `lastUpdatedAt` moved (a rollback); otherwise it is applied to the ledger re-read after the call, so popup edits made during the call survive. A failed call or an unreadable answer changes nothing but the update log and leaves `lastUpdatedAt`, so the next update reads the missed messages again. An applied update then retries one edited message whose re-extraction call failed (`retryPendingReextraction`, see the edit row under "Rollback"). The call goes through the arc generation connection profile (`callLlm`, the plan check's transport), so it can run on a cheaper model than the chat.

**Beat recognition (2026-11-04, ADR-0008; ADR-0007 amendment).** With the chat's `autoTrack` on, the same call also recognises beats; no call is added. Its input gets `== DEVELOPMENTS OF THE STORY ARCS ==` (`listRecognisableBeats`: the active beats of every active arc that is not paused, by id, and each arc's completed beats under `done` as context that is never reported), and its answer a `fulfilled` list (task 6). After the answer is applied to the ledger, `completeFulfilledBeats` hands the resolved items to `completeBeats` and flushes the queued marks when a beat completed. The narration prompt then carries no BEAT CHECK. The rules, the completion record and the rollback are under "Beat Completion"; the single-message re-extraction after a swipe switch or an edit completes beats the same way. With `autoTrack` off the developments list is empty, so nothing is reported.

**Out-of-character corrections retract facts** (issue #18). The extraction can take knowledge back, not only add it. Live case, test chat 2121–2129: a character stated a yearly stipend the narrator had made up, the extraction recorded it for two characters, the player objected out of character ("There was never anything on the page regarding financial compensation…"), the narrator admitted "I invented that detail on the spot", and the fact kept reaching the narrator through the block. The prompt now says that out-of-character lines (marked OOC, in square brackets, or the narrator stepping out of the story) teach characters nothing and are corrections; when one calls a ledger fact wrong, invented or not canon, the answer lists it under `retracted: [{ factId, at }]`, `at` being the message of the correction (inside the covered messages, like every `at`). A correction that states the right version is no fact until a later in-story message shows a character learning it. `parseKnowledgeExtractionAnswer` reads a missing `retracted` as `[]`; a non-list or an item without `factId` or integer `at` rejects the answer. Applying the answer handles retractions last (the correction is the later word): the fact leaves `facts` with all its holders and goes to `retractedFacts` as `{ at, fact }`. A fact with any user-entered holder stays (a hand correction wins), and an unknown id changes nothing. The rollback is the normal drop path: `keepOnlyHolders` judges each retraction with the same predicate as the holder entries, so deleting, swiping, regenerating or editing the correcting message (and loading a branch that ends before it) puts the fact back, with only its holders from before the rollback point; a fact entered meanwhile under its id gives the returning fact a fresh id (`nextLedgerId`).

**New names of a known character (issue #60, part 1).** In the Paragon chat the ledger held nine pairs of records for one person each (Anvil next to Kendra Osei, Switchback next to Mateo Reyes, …): when a known character turned up under a name the ledger did not have, task 2 could only add a new record. The prompt now has NEW NAMES after task 2, and the answer a `newNames` list, `[{ character, name }]`: a character from the ledger, by any of its names, and the new name the messages give them (a codename, a first name, a nickname). The prompt asks for an item only when the text makes plain both names belong to one person (an unmasking, an introduction under both names, a character who knows them using it, a ledger fact saying who goes by it), never as a guess; a secret identity the characters in the scene do not know still counts once the text has shown it, because the story may keep two names but the ledger keeps one character. The task is not part of the character details switch: duplicates split knowledge whether details are on or not. `parseKnowledgeExtractionAnswer` reads the list as strictly as `retracted`: missing reads as empty (answers from before the list stay valid), not a list or an item without a non-blank `character` and `name` rejects the whole answer. `applyExtractionAnswer` applies the new names **first**, before the new characters, so everything else in the same answer finds the record under the new name: a new character listed under it is not added (task 2's rule that a name the ledger has creates nothing), and `present`, a learned holder or teller, a revealed secret's hearers and a details item that use it resolve to the record. Each item adds the trimmed name to the end of the record's `aliases`. A name another record already has as its name, alias or display name (ignoring case, `findCharacterId`) is refused, so names stay unique across records; a name the record has already changes nothing; a `character` no record has is ignored. The `update` and `reextract` records count the three outcomes (`newNamesAdded`, `newNamesRefused`, `newNamesUnknown`; a no-op counts nowhere). An added alias does not roll back: rollback never removes records the extraction created, nor a name it gave an unnamed relative, so a record's names stay as they are when the message that taught them is swiped, edited or deleted. The player can still change aliases in the Knowledge popup.

**Shared name words point at nobody (issue #62).** In the Paragon ledger (2026-11-05) Arthur Sterling had the alias "Sterling" next to Julian Sterling, Marcus Chen "Marcus" next to Marcus Bishop, Malcolm Cross "Cross" next to Agent Cross: every "Julian Sterling" in a reply made Arthur talked about, and an answer naming "Sterling" resolved to Arthur. The aliases came in while the word was still unique, so only a rule at reading time catches the later arrival. `listNameWordCarriers(characters)` maps every name word of the named records (the words `listTakenNames` derives from one record's name and aliases, folded with `foldName`, hyphen parts included, unnamed relatives carrying none) to the ids of the records carrying it. `isSharedNameWord(name, characterId, carriers)` is true for a name that is a single whitespace-free word with exactly one `nameWords` word, carried by a record other than `characterId`; "Mr. Sterling" has two words and is never shared (a bare `nameWords` count would drop the title and call it one word). Reading: `findCharacterId`, and so every list of an extraction answer that resolves names (`findCharacterIds`, tellers, relations, `wasUnnamed`, newNames' `character`), returns null for a shared word, even for the record whose own name it is (a record named "Vance" next to Brody Vance is found only by its id-based paths, the popup); `isNamedInText` skips a shared name or alias, with the carriers map built once per `buildKnowledgeBlock`. `findCharacterId` builds it only when a name matched. Adding: a newNames item that is a shared word for its record is counted in `newNamesRefused` (no new log field), checked after "the record has the name already" (a no-op, compared against the record's own names, since `findCharacterId` no longer finds a shared word); the new characters' `trimmedAliases` drops shared words, for named, renamed and unnamed new records alike, while the new character's own name is left to the reused-name flag (a new character named just "Sterling" is now added and flagged instead of being taken for Arthur). The popup's hand alias edit is not guarded. The NEW NAMES task says a bare first name or surname another ledger character shares is not a new name, a title with the surname ("Mrs. Osei") is.

**Message ids (issue #19).** Applying an answer gives every message the call read Story Arc's own message id, `message.extra.story_arc_message_id` (a `uuidv4`; a message that carries one keeps it), and each holder entry, the scene and `lastUpdatedAt` store it as `messageId` / `lastUpdatedMessageId` next to the index. The message id is Story Arc protocol data on the message, the same exception GOALS.md makes for scrubbing plan internals; `saveMetadata` saves the whole chat, so it persists with the messages. Ids are never borrowed from other extensions. Only messages an update read carry a message id: a swipe removes it from the shown swipe and from every swipe's `swipe_info[i].extra`, and the extraction that reads the swipe gives it a new one. ST's `syncMesToSwipe` copies `extra` into the swipe it swipes away from, and a branch from a chosen swipe (`createBranch` → `getBranchChatSnapshot` → `syncSwipeToMes`) brings that swipe's `extra` back without a `MESSAGE_SWIPED`; without the cleanup, a swipe whose knowledge an earlier swipe took back would count as read in the branch and never be read again.

Deleting a message in the middle of the chat is handled by the message ids (above). Entries without a message id, learned before #19, still go by index, so a deletion in the middle among them shifts later indices uncorrected, the limitation the pending marks keep. Message ids and ledger reach disk in the same chat save, so one is not saved without the other. Live check of a middle deletion is pending (issue #19).

**Update log (issue #26).** In the Paragon chat the updates for replies 2165, 2167 and 2169 wrote their scene but no facts, although four replays of the same extraction all returned facts; the only trace was the browser console, gone after a reload. So the ledger keeps its own short history in `updateLog`, saved with the chat: the newest `KNOWLEDGE_UPDATE_LOG_CAP` = 20 records, oldest first (`recordKnowledgeUpdate`). Nothing reads it but the reviewed marks, through the change items of its records (below) — not the block, not the extraction prompt. No timestamps; indices and message ids place each record. Records (shape at `createEmptyKnowledgeLedger`):

- `{ kind: 'update' | 'reextract', from, to, messageId, answer: { present, newCharacters, learned, retracted, revealedSecrets, fulfilled }, factsCreated, holdersAdded, factsRetracted, beatsCompleted, detailsSet, detailsChanged, restatementsIgnored, detailsLocked, newNamesAdded, newNamesRefused, newNamesUnknown }` — an applied answer: the messages read, the message id of `to` (`null` when it has none), the lengths of the answer's lists (`fulfilled` after resolving), and what the apply did (fact ids created and retracted, holder entries added, the teller's entry included, the number of beats completed, the character details set for an unknown kind, changed with an on-screen event, ignored as restatements, and skipped because the player locked the kind in the Knowledge popup, issue #54, and the new names added as aliases, refused because another record has them, and ignored for a character the ledger does not have, issue #60). Beats go in as counts only, never their ids or texts: the plan is spoiler-protected; details too, never their values. An update whose answer learned nothing is an `update` with zero counts.
- `{ kind: 'skipped', from, to, reason }` — a call whose answer was not applied: `'no answer'` (the call failed or the answer was unreadable), `'chat changed'` (the reply's or message's text changed), `'ledger moved'` (a rollback or update moved `lastUpdatedAt` during the call). Saved, unlike before. A skip by the tracker switch, the update interval or an update already running is not recorded, nor is a skip when another chat was loaded during the call (the record would land in that chat).
- `{ kind: 'rollback', from: firstGoneIndex, factsDropped, holdersDropped, factsRestored, detailsDropped }` — written by `dropKnowledgeFrom` when the rollback changed anything. In `rollBackKnowledgeFrom` it also counts what `followMessagesById` took back with deleted messages. The edit's `dropKnowledgeLearnedAt` writes none; the re-extraction after it writes its `reextract` record.

What a step did is found by object identity (`knowledgeHoldings` before and after, `holdingsChange`), so a restored fact that took a fresh id is reported under that id.

**Change items and reviewed marks (issue #67, for the "What changed" view of #65).** An `update` or `reextract` record written since then carries `items` next to its counts (`createdChangeItems`, by object identity against `knowledgeHoldings` taken before the apply): `characters` (ids of new records; the unnamed relative the story named is not one), `holders` (`{ factId, characterId, messageId? }`, in the facts or in a fact the same answer retracted), `details` (`{ characterId, kind, messageId? }`, one per character and kind, the newer entry's message id when one answer set and changed a kind; no value), `names` (`{ characterId, name }`: a name or alias a record the ledger had gained, a `newNames` alias or the name of a named relative) and `scene` (who is present when that set changed, else `null`). The facts retracted are the record's `factsRetracted`. The re-extraction writes its record after it put back the scene of an older message, so it lists no scene it left alone. Older records have no `items` and stay valid: they list no change items and are never reconstructed. `listChangeItems(record)` (exported for the popup's view) gives each item its **item key**, `<recordId>:<item kind>:<ids>` (`u6:holder:f2:c1`, `u6:detail:c2:gender`, `u6:scene:c1:c3` with who is present), stable across reloads. Every `update` and `reextract` record written since the #70 review carries a **record id** (`recordId`, `u1`, `u2`, …: one more than the highest number in the log, `nextUpdateRecordId`; the log drops only its oldest records, so no id comes twice). The record id keeps two re-extractions of one message apart and stops a fact id reused after a delete (`nextLedgerId` takes the highest id plus one) from inheriting the old fact's mark. A record with items but no record id (written between #67 and the review) keeps `<messageId>:<record kind>` as its prefix (`m6:update:holder:f2:c1`, `#<to>` for a missing message id). The ledger stores the player's **reviewed marks** as `reviewedMarks: [itemKey]`, missing until the first mark. `markChangeItemReviewed` and `unmarkChangeItemReviewed` in `knowledge-popup.js` are pure edits like the other hand edits (`{ ledger, error }`; marking refuses a key no record of the log lists), saved through `saveLedgerEdit`, which copies `reviewedMarks` onto the stored ledger, so a mark is undoable like any hand edit (#68). A rollback drops the marks of the items it removed (`dropReviewedMarksOfGoneItems`, at the end of `dropKnowledgeFrom` and `dropKnowledgeLearnedAt`, so deletion, branch load, swipe and edit all do it): the keys of the items in the ledger are taken before the rollback (`presentChangeItemKeys`, in `knowledgeHoldings`, so `rollBackKnowledgeFrom` covers `followMessagesById` too) and after, and a mark goes when its item was there before and is not after. A holder or detail item is there while the entry with its message id is (a later or earlier entry of the same character and kind does not keep it), a retraction while its fact is retracted, a scene while the scene or the scene history holds the scene of the record's message with the same characters present, a character and a name while the record has them. An item gone before the rollback keeps its mark: a scene that left the ten-scene history while its record is still among the log's 20, a holder removed by hand. A mark no record of the log lists any more (its record left the cap) goes at the next rollback. Marks live in `ledger.js` only as far as the rollback needs them; the edits stay with the popup.

**The knowledge block** — `story_arc_knowledge`, in-chat at depth 1, system role, listed by `listStoryArcPrompts()` and set by `injectStoryArcPrompts()` (called by `onGenerationStarted` and `onMessageDeleted`) next to the plan and signal injections. Depth 1 sits right above the newest message; this placement took a hand-written card from 3 of 3 leaking replies to 0 of 3 in the 2026-11-01 experiment (spec issue #2, Further Notes). `buildKnowledgeBlock(ledger, chat)` covers:

- **present** — the characters in `scene.present` from the last extraction;
- **talked about** — characters whose name or an alias appears as a whole word (case-insensitive, Unicode-aware) in the story text of the latest user message or the latest reply, hidden messages skipped, minus those present; a name or alias that is a shared name word (issue #62, `isSharedNameWord`) does not count. Story text is the message with every tagged element (`<tag>…</tag>`, nested ones included) taken out (`withoutTaggedElements`, issue #22): presets append status blocks such as `<svt>…</svt>` and `<trk>…</trk>` to every reply, and at message 2133 of the Paragon chat three bystanders got a talked-about section only because a `<bg>` line named them. HTML formatting tags in the story text (`<i>Steve</i>`) are taken out too. The extraction input keeps the tags.

```
[WHO KNOWS WHAT — characters in this scene and characters being talked about. Each character knows only their own list, what everyone knows, and what happened in front of them on-screen. A private fact reaches nobody off-screen: not through rumors, teammates, news reports, logs, records or their own deduction. A character not listed here knows only what everyone knows, plus any secret the SECRETS section names them for.]

EVERYONE KNOWS
- Steve's team won the Best Live Demo award

STEVE (present)
- Knows: Steve is quitting next month (shared only with Amy)
- Knows: The demo ran on a scripted fallback (shared only with Lena and Amy)

AMY (present)
- Knows (told by Steve): Steve is quitting next month (shared only with Steve)
- Knows: The demo ran on a scripted fallback (shared only with Lena and Steve)

LENA (talked about, not present)
- Knows: The demo ran on a scripted fallback (shared only with Steve and Amy)
```

`EVERYONE KNOWS` lists the public facts as `- <fact>`, newest first by their newest holder entry (facts without holders after the dated ones, in ledger order), at most `KNOWLEDGE_LIST_CAP` lines; it is printed only when there are public facts, right after the header. Per character: `- Knows: <fact>` (or `- Knows (told by <name>): <fact>`), followed by ` (shared only with <names>)` listing the fact's other holders in holder order, or ` (known only to them)` when the character is its only holder; and, for a character talked about only, `- Has told only <names>: <fact>` from the `toldBy` entries. Each list holds at most `KNOWLEDGE_LIST_CAP` = 5 lines, newest first; an entry made by the user counts as newest, so a correction reaches the narrator first. A character with no lines gets no section; with no public fact and no section the block is `''`. A `plan` holder entry never prints a line of its own but is named in "shared only with" (owner ruling D22: otherwise the line says the character alone knows it, and the header's last sentence points planned holders to the SECRETS block), and a fact held only through the plan is printed nowhere: a secret's text stays in the SECRETS block, which gates it by phase. Once a secret is revealed on-screen it is a fact with `witnessed` holders and is printed like any other; its planned holders get no line for it.

There are no "Does not know" lines (issue #21, owner ruling D20 a, D18 a). Until 2026-11-01 each covered character got `- Does not know: <fact>` for a fact another covered character held. Every such line printed the private fact's full text: in the Paragon party scene at message 2169 the block was ~4,600 tokens in 11 sections, 48 of its 68 lines were "Does not know" lines, and the two private Jumbotron facts appeared 24 times. The narrator gave one of them to a background character who was listed as not knowing it, laundered as "My team leader said …". Naming a secret once per bystander puts it in front of the model ("white bear"), and a character without a list had no limit at all. Now a private fact's text appears only in its holders' sections, the header says what a character may draw on (own list, public facts, what happened in front of them) and that rumor and hearsay carry nothing new, and the public facts are printed so bystanders have material they may use. The extraction prompt records as public what a crowd watched happen and what was broadcast or reported.

**The Has met line (2026-11-08, ADR-0007 amendment).** At Paragon message 3027 (since regenerated) Levi called Sofia Vega "the mouth-scar female". He had never seen her: her rebar lip scar was only in the lorebook's cast entry, which the narrator gets every turn, and the block tracked what characters know, not whom they have seen. So the ledger keeps `meetings`, `[{ at, messageId?, present }]`, oldest first, one per message: `recordMeeting` in `applyExtractionAnswer` records every scene with two or more present, from the `present` list the extraction already returns, with no prompt change and no extra call. A meeting at the same message is replaced. An edit drops the edited message's meeting first (`dropKnowledgeLearnedAt`), unlike the scene, because no later update replaces a meeting: a failed re-extraction would otherwise keep one the edited text no longer has. The re-extraction records it again if it still holds. A ledger without `meetings` gets its scene history and its scene as its first meetings on its next apply. One with nothing to record stays without the key, so old ledgers and tests see no change until a meeting happens. `meetings` is not capped, unlike `sceneHistory` (it holds about one entry per update). Rollback follows the scene history: `dropKnowledgeFrom` drops the meetings at `firstGoneIndex` or later, and `followMessagesById` moves them by message id and drops those whose message is gone. Merge and delete re-point them in `withCharacterReferencesChanged` (`knowledge-popup.js`), and a meeting left with fewer than two characters goes. `saveLedgerEdit` stores them, and undo snapshots the whole ledger. A covered character who has met anyone gets `- Has met: <names>` after the details line and before the knowledge lines, every name in the order of first meeting, uncapped. A character with only that line still gets a section. The line does not follow the character details switch. Only a block that prints such a line carries the header sentence "A character knows the face, looks and voice only of someone they have met: a name on their Has met line, or someone the story put in front of them on-screen. Hearing a name is not meeting." The on-screen clause is deliberate, because meetings start with the tracker (in the Paragon chat the first apply fills only the ten scenes in the history) and an acquaintance from before then must stay possible. Limits: `present` is the scene at the end of the messages an update reads, so a character who comes and goes within one update is never recorded as met. Every meeting is kept, not only the first of a pair, so deleting the message where two characters first met keeps them met as long as a later meeting has them both. Meetings appear in neither the update log nor the change items: the scene item already lists who is present per update. The Knowledge popup does not show or edit them yet.

**The taken-names block** (issue #39, spec #34) — `story_arc_names` (`NAMES_PROMPT_KEY`), in-chat at depth 1, system role, listed by `listStoryArcPrompts()` right after the knowledge block, under the same gate: Story Arc on and the tracker on, `''` otherwise and `''` when the ledger has no character. It works without any active arc. ST joins the extension prompts of one position, depth and role in the sorted order of their keys, so it lands right after `story_arc_knowledge`, in the same system message. It tells the narrator every first name, surname and codename the story already uses, because Summaryception compacts long chats and the narrator then reuses names it cannot see (Julian Vance and Julian Sterling). One header sentence with the rule, then the names on one line:

```
[NAMES ALREADY IN THIS STORY — first names, surnames and codenames of characters who have appeared. A new character gets none of these names, as a first name, as a surname or as part of a double or hyphenated surname: adding a second surname does not make a taken name new. Only a relative of the character who has a name may share it, and only when the story says how they are related. Characters already in the story keep their names.]
Aegis, Bishop, Chen, Marcus, Sterling, Vance
```

**Double surnames (2026-11-11).** The first header said only "unless the new character is related". In the Paragon chat, after the block went live (message 2739), the narrator dodged it by adding a second surname to a taken one: Vance-Horton, Vance-Garrick, Vance-Geller, Vance-Grier, Lin-Bauer, Santos-Cruz, Okafor-Ross. Hyphenated surnames rose from 5% of new ledger records before the block to 13% after, and reuse of a taken name word did not drop (17% to 25%). The block prints only the parts of a hyphenated surname, so the compound was never on the list, and a double surname reads as a family tie. The header now names the double surname and asks the story to say how a relative is related; the planner's rule, its checklist line and the plan check's rename rule say the same.

The derivation is code in `lib/knowledge/names.js`, no LLM call, and reads only the ledger: every character's name and each of its aliases. `nameWords(name)` splits a name at whitespace and removes enclosing punctuation; it drops words without a letter, lowercase particles (`de`, `van`, `al-`; a capitalised `Van` or `Al` stays) and leading articles (`The`), and drops leading titles while more than one word is left, so the last word always stays. A name or alias of several words with no capitalised word is a description, not a name ("the night-shift tech", seen live in the Amy test chat 2026-11-04, put "the", "at" and "box" on the list) and gives no words; a single lowercase word ("zoe") still counts. Since #83 (2026-11-12; the view showed `07, 904, A, K, with` on the Amy chat's list): in a name of several words with a capital, only the capitalised words are name words ("Woman with Umbrella" loses "with"; a capital after a hyphen or an apostrophe counts, "al-Rashid", "d'Artagnan"); a single letter is an initial, never a name ("Mara K." gives Mara); and `listTakenNames` puts a hyphen piece through the same letter and single-letter tests ("HH-904" gives HH, "ID #07-A" gives ID). A lowercase "the …" description is deliberately not dropped when it has capitals: codename aliases such as "the Vanguard" stay names. The extraction lists a character without a name under a lowercase "the …" description (NEW CHARACTERS in `extract-knowledge.txt`), which gives no words; Title Case labels stored before ("Unknown Caller", "Waiter #4") stay until renamed. A title is a word ending in a period or a word of `TITLE_WORDS` (honorifics, ranks, offices and kinship words such as Mr, Dr, Judge, Commissioner, Señora, Staff, Sergeant, Corporal, Rear Admiral, Principal, Coach, Nurse, Uncle, Auntie; never a common given name such as Don). No word is classified as a first name or a surname. `listTakenNames(ledger)` returns a `Map` from the folded form (`foldName`: lowercase, diacritics removed, locale-independent) to the spelling of the first record in ledger order that has it; a hyphenated word is in it whole and by each part. `buildTakenNamesBlock(ledger)` prints only the parts, sorted by the folded form in code-unit order. **Byte stability:** the text depends only on the set of names, so the order of the records, the facts, the holders and the scene never change it; a new character, a rename or an alias with a new word does. The reused-name flag (#35) and the planner with its plan check (#36) reuse `listTakenNames` and `foldName`; the module is its own file because the generator cannot import `ledger.js` without a cycle. A character added or renamed in the Knowledge popup counts from the next generation on. The extraction prompt and the ledger's shape are unchanged.

**Secrets and holders.** The planner names each secret's holders (`generate-arc.txt`, `normalizeSecretHolders` in validation, `[]` for arcs planned before). A re-plan keeps the holders of kept secrets. While the tracker is on the SECRETS block appends ` (known only to: …)` to a secret with holders (`holderSuffix` in `builder.js`). The extraction sees the shown secrets with their planned holders and reports a secret that comes out plainly on-screen under `revealedSecrets`, with what the characters heard (`text`, one sentence) and the message it came out in (`at`); applying the answer turns that sentence into a ledger fact linked to the secret. The secret's own `content` never goes into a fact and so never into the knowledge block: it may hold parts that have not come out yet (owner ruling D10 a, 2026-11-01). The secret's own `disclosed` state in the arc stays with the plan check and the Arc Manager.

**The Knowledge popup** (`lib/ui/knowledge-popup.js`, rebuilt in #70 from the approved mockup of #65), reachable while the tracker is on from the Arc Manager header, the wand popup and the drawer's status line. It is a correction desk: it opens on what the last updates changed and puts each fix on the line that shows the mistake. Names and aliases are unique across characters, ignoring case, because the block and the extraction find characters by any of them. Hand edits are `how: 'user'`, `at: null`: no regeneration, swipe or deletion removes them. The popup is the correction path for an extraction that recorded a leak as a fact. Spoilers: facts are shown openly; only a holder entry from an arc plan (`how: 'plan'`) reads "Planned holder" until the player reveals it (per popup session).

- **Frame.** A wide, large ST popup without its own buttons and with `allowVerticalScrolling: false`: the root `#story-arc-knowledge` fills the popup body, the tab panels scroll (the Map panel holds still, its sheet scrolls), the heading (ledger size, last update, who is in the scene), the tabs, the search field (sticky) and the status bar stay put. The status bar holds the last message ("Saved: …", "Undone: …", a refusal), the Undo button while the session has an undoable edit, the key hints for the focused control, and Close. Styling is `lib/css/knowledge.css`, every rule scoped to the root, only ST theme variables and `color-mix()` of them (no own accent), ST's `menu_button` / `text_pole`, real `<button>`, `<details>`, `<input>`, `<select>`, a visible focus ring.
- **What changed.** `listChangeLines(ledger, withDetails)` reads the update log newest first. Each record with `items` (#67) is a group, its heading the message range and its counts; its change items (`listChangeItems`) become lines: a new character, a detail set (the value looked up in the character's history by the item's message id, with a note when the player locked it or the story changed it later), a new fact with the holders it was learned by, holders added to an older fact ("learned"), a retraction, a new name, the scene. The holder items of one fact make one line; a line covers several items and is reviewed when every item carries a reviewed mark. Each line has its fixes (holder chip → Move to… / Remove / Open; Edit, Add holder, Not true, Delete… on a fact; Still true on a retraction, also on a fact line whose fact was retracted; Edit on a detail; Same person as… and Delete… on a new character; "Not their name" on a new alias, and on the name the story gave an unnamed relative) and "Fine", which marks its items reviewed; reviewed lines fold away (Show N reviewed per group, "Show reviewed lines" for all), "All fine" marks a group. A fix made on a line also marks that line reviewed in the same undo step and keeps it in view with the fix stated (a moved holder shows struck through, an arrow, the new holder). The tab shows how many lines are open. Without `withDetails` the detail lines are left out. Records without `items` (older ones, skips, rollbacks) are "Earlier updates", one count line each; their "Open in Cast & facts" shows only the facts the record stored (`factsCreated`, `factsRetracted`, as they are now), never a reconstruction by message number, with a button for a message search of the same range (decision 2026-11-06); an update that stored no fact but changed holders or details offers that message search directly.
- **Cast & facts.** One search field: characters by name or alias (whole name, start, start of a word, anywhere; an alias after a name), the latest facts of a clear best match, facts by all typed words (newest first, the words marked), retracted facts; `#2927` or `#2926–2927` is a message search, labelled so, of everything dated there. Before anything is typed: add buttons, "Changed by you" this session, who is in the scene, the retracted facts and everyone A–Z behind folds (rows drawn only when the fold opens: 105 characters, 500 facts, no per-row hidden select anywhere). No match offers to add the text as a character (with a note when its name words are taken), an unnamed relative (`<name>'s <kinship>`) or a fact. A row opens the sheet in place, with Back to where it came from (results, a previous sheet, a What changed line). The character sheet: names and aliases (Save names clears a name check), the details with where each came from and its lock state (Edit / Set, Lock, Unlock or Clear; `withDetails` only), what they know with a filter (Move to…, Remove, open the fact), Same person as… and Delete…. The facts an arc plan gives the character (`how: 'plan'`) fold into one "N planned facts" line with Show (the spoiler is that this character will learn it); hidden plan entries count neither in "knows N facts" nor in a fact's "also known to N others". The fact sheet: text and public flag, holders (Move to…, Remove, open), Add holder, Not true, Delete…. Add forms for a character, an unnamed relative and a fact (with holders).
- **Map (#77).** A third tab draws the cast for seeing and finding, not for editing. `layoutCastMap(context)` puts every character on a ring: the scene in the centre, then who learned a fact in the last `MAP_RECENT_WINDOW` (100) messages before `lastUpdatedAt`, then who learned one earlier, then who knows none; an unnamed relative without facts of its own takes its anchor's ring (recent or earlier) so it sits by that record. Facts from an arc plan (`how: 'plan'`) count for neither the ring nor the dot size, so the map gives no plan away. Within a ring the records sort by name family (`listMapFamilies`: the surname when another record has it, else the most shared name word, from `listTakenNames` per record; a short record whose name words all sit in a longer one, Raj in Raj Barrows, joins that family; an unnamed relative joins its anchor's), and neighbours of one family get a quiet band behind them. Each `relation` detail is one curve per pair with its kinship word near the record that carries it; the selected character also gets dashed links to every record sharing a name word. The layout is in ring units and deterministic (plain string sort, the id last); `buildMapScene` projects it onto the measured pane (`view.map.pane`, zoom 1 fits the cast, pan) and places labels greedily by priority (only for dots inside the pane; the selection, filter matches and a merge's two halves always; then the focused node, the selection's relatives and name sharers, the scene, who knows most): beside the dot away from the centre, above or below it, then inward (never half a row off, where a label could be read as a neighbour's); a label that would cover a label, a dot, a name-to-check flag or a ring title stays hidden; the bar says how many names in view are hidden and shows on hover and focus. Text widths are estimated from the length (no canvas), so Node and the browser place the same labels; on the Paragon ledger 95 of 105 are named at fit zoom in a 1440 × 900 window, 78 at 1024 × 900. `mapRenderState` keeps the render context and the layout while the ledger's lists are the same objects (every edit and undo replaces them), so pan, zoom, the filter and a resize only project and place labels; the filter also dims relation lines and words unless one end matches, and the two kinship words of one pair stack. One `<button>` per character, nothing inside it; a name to check is a triangle and a dashed ring on the dot. Selecting opens the same character sheet as Cast & facts beside the map (the focus stays on the node, so the arrows go on, and the status bar shows the sheet's keys N, D, F, which work from the node too; where the sheet replaces the map it takes the focus) (the `sheet` editor area, so every edit, merge and undo works unchanged); below a container width of 1080 px the sheet takes the map's place and "Back to the map" (or Esc) returns to it as it was. A drop of one node onto another, or M on a node, arrows to another and Enter, calls `startMapMerge(view, fromId, toId)`: it opens the dropped character's sheet with the merge editor aimed at the other; nothing is merged until `merge-go` saves through `saveLedgerEdit`. Wheel, pointer and the stage's ResizeObserver are bound natively on the popup root (the wheel must prevent scrolling); the observer draws at once so no frame shows the old size, and it is disconnected when the tab or the popup closes. Pan and zoom redraw only the stage (svg and nodes), never the sheet, so no typed text is lost. Keys: arrows go to the nearest node that way (panning it into view), Enter opens, M picks up, Esc cancels, `+ − 0` zoom, `/` the map's filter (Enter opens the best match, ↓ goes to it).
- **Editors.** One editor container, opened in place under the line, the name check or the sheet row (`view.editors` per area: a line key, `clash:<id>`, `sheet`, `fs`, `add`). A typeahead picker over the cast replaces every select: suggestions first (named in the fact, sharing a name, in the scene, changed by you, recently in the story), arrows choose, Enter picks. Merge and delete state their consequence before the confirm: the merge preview lists what moves and what stays, and its refusal comes from calling `mergeCharacters` on the unchanged ledger; the delete preview reads `deleteCharacter`'s `removed`, and its refusal (an unnamed relative depends on the record) offers to open that relative. - **View state and redraw.** Typed text lives in the view's drafts (by field), so a redraw loses nothing; after an edit the heading, the tab count, the open panel and the status bar are redrawn, the search field stays as typed, and the focus returns to the control it was on (`data-fk`) or to the next sensible one: `focusAfter` is a list of focus targets, fixed selectors or an attribute with its exact value (`findFocusTarget`), compared rather than put into a selector, so a line key or a name with a comma or a quote cannot break the redraw. Typing in the search redraws only the results, in a picker only its options. Clicks, typing and keys are delegated on the document under `.storyArcKnowledge`; the `toggle` of the `<details>` is bound once on the popup root in the capture phase.
- **Keys.** `/` search; in results ↑ ↓ Home End, Enter opens, typing goes back to the field; in a sheet's lists ↑ ↓, Enter opens, M moves, Del removes; on a character sheet N names, D details, F facts; on a What changed line ↑ ↓ and F for Fine; Ctrl+Enter saves a text area, Enter a one-line field; Ctrl+Z undoes. **Character details in the popup (issue #54, spec #50).** A character's sheet lists each detail kind with its value and where it came from ("From the story, message #12", "Locked by you" with what the story says, or "unknown"); a result row sums the known details up. Each kind has its own editor (Edit or Set): a text field for gender, age and role, a kinship word plus the cast picker for the relation, and a select of unknown / alive / dead for the status. "Save and lock" calls `saveCharacterDetails(ledger, characterId, typedDetails, shownDetails)` with that one kind, so saving one detail locks no other; `shownDetails` is the value the editor showed, and a field counts as changed only when it differs from that value (`isSameDetailValue` from `ledger.js`, the extraction's comparison: letter case aside, a relation by kinship word and other character), never from the ledger's current value: an extraction or a rollback that changed a detail while the popup was open is not undone or written back, and retyping "female" as "Female" changes nothing (saving the value as shown locks it instead, `lockCharacterDetail`). A field changed to a value writes a player entry `{ value, at: null, by: 'user' }` at the end of the kind's history, in place of an earlier player entry (the story's entries stay before it); the kind is then **locked** (`isDetailLocked` in `ledger.js`: the history holds a `by: 'user'` entry). Unlock (or Clear, when the story never set the kind) saves the kind emptied, which removes the player entry; the extraction's entries under it count again, and a kind with none left leaves `details` (a record with no kind left loses `details`). Emptying a kind only the story set changes nothing: story entries go only with their messages. A relation needs both the kinship word and another character of the ledger; a status is alive or dead; a relation that would give an unnamed relative the display name of another record is refused, as in `addUnnamedRelative`. `applyExtractionAnswer` skips an item for a locked kind before any other rule, and the `update` and `reextract` records count those skips (`detailsLocked`, below). A player entry has `at: null`, so no rollback reaches it. The save goes through `saveLedgerEdit` like every popup edit.

**Merge into… (issue #60).** One person recorded twice (Anvil next to Kendra Osei, seen in the Paragon chat 2026-11-05) is joined in the popup. "Same person as…" on a character sheet, a name check or a new-character line opens the merge editor: the cast picker (suggesting the records that share a name word; a name check with one other record skips it), then the consequence, the merge button and "Keep … instead" to swap which record stays (#70). The chosen record stays: `mergeCharacters(ledger, mainId, otherId)` returns `{ ledger, error }` like the other edits. The other record's name and aliases become aliases of the main record (`cleanAliasList`, minus the main name, ignoring case); names stay unique across records, so a name a third record has refuses the merge (`findNameConflict` on the ledger without the other record). The main record keeps its name; an unnamed main record takes the other's name instead, the way the story naming a relative does. Every reference to the other record moves to the main one: holder entries' `characterId` and `toldBy`, on facts and on retracted facts' facts, `scene.present` and each `sceneHistory[].present` (one id per scene), and the relation entries' `of` on other records. A fact with two holder entries for the merged character keeps one: an entry without a message (`at: null`, the player's) first, else the earliest `at`, the main record's on a tie; an entry the other record told the main one reads as witnessed (`toldBy: null`), since the person knew it. Details merge per kind, one record's history winning whole: a kind only one of the two records has locked (`isDetailLocked`, an entry `by: 'user'`) keeps that record's history, so merging Anvil with the player's age into Kendra Osei with an extracted age keeps the player's; any other kind (locked on neither or on both) keeps the main record's, or the other's where the main record has none. A relation entry between the two records would relate the record to itself and is dropped first, so it locks nothing and the other's relation can fill the kind. A merge that leaves an unnamed record without name and relation, or two unnamed relatives with one display name ("Anvil's mother" and "Kendra Osei's mother"), is refused: merge those two first. Every moved entry keeps `at` and `messageId`, so `dropKnowledgeFrom` and `followMessagesById` roll it back as before. The other record's `nameClash` goes with it; the main record's goes when no other record has any of its flagged names (`listCharactersWithNames`). The taken names and the reused-name flag then see the names as aliases of one character. No log record is written: the update log records extraction and rollback, not hand edits.

**Move, delete, restore, lock (issue #66).** Four more pure edits for the redesigned popup (#65), each `{ ledger, error }` and never changing its input; the rebuilt popup (#70) offers them as Move to…, Delete…, Still true and Lock. `moveFactHolder(ledger, factId, fromId, toId)` gives every holder entry of `fromId` on the fact to `toId`, keeping `how`, `toldBy`, `at` and `messageId`, so `dropKnowledgeFrom` drops a moved entry with its message as before; when `toId` already holds the fact, the moved entries go and `toId`'s own stays. Other holders' `toldBy: fromId` is not re-pointed (a move of the listener does not change who told whom); a moved entry told by `toId` itself reads as witnessed, as in a merge. Refused for a move to the same character, to a character not in the ledger, or from one who does not hold the fact. `deleteCharacter(ledger, characterId)` removes the record and every reference, walking the same places as a merge (`withCharacterReferencesChanged`, shared by both): holder entries on facts and retracted facts, `toldBy` (the entry reads as witnessed, `toldBy: null`), `scene.present`, each `sceneHistory[].present`, and other records' relation entries to them (a kind left empty goes, `details` left empty goes). A fact that had holders and has none left goes with the character, unless it is public; a fact that had no holder before stays. A retracted fact left without holders goes, as in `keepOnlyHolders`. Refused, naming the relative, while an unnamed record has any relation entry to the character: it is called after them. On success the result also carries `removed: { facts, retractedFacts, holderEntries, relations }` (the facts and retracted facts that went, as `{ id, text }`, the count of the character's entries on facts that stay, and each relation entry of another record to them that went, as `{ characterId, kind }`; a player's relation goes too), so the popup can state the consequence before confirming by calling it on the unchanged ledger first. `restoreRetractedFact(ledger, factId)` ("still true") takes the later retraction of that fact id out of `retractedFacts` and puts a copy of its fact back at the end of `facts`, holders as they were, under a free id (`nextLedgerId`) when a fact took its id meanwhile; the restored fact has no player entry, so a later extraction may retract it again. `lockCharacterDetail(ledger, characterId, kind)` appends a player entry `{ value, at: null, by: 'user' }` with the kind's current value (a relation's `{ kind, of }` copied), which locks the kind (`isDetailLocked`) and outlives a rollback of the story's entry; refused for a kind outside `DETAIL_KINDS`, one the story has not set, and one already locked. `saveLedgerEdit` stores all four, scenes and retracted facts included.

**Not true and unnamed again (#70 review).** `retractFact(ledger, factId)` retracts a fact by hand, as an out-of-character correction would: the fact goes into `retractedFacts` whole as `{ at: null, fact }`, the player's own retraction, which no rollback takes back (`keepOnlyHolders` keeps an `at: null` retraction; its holders still go with their messages, and with none left the retraction goes); `restoreRetractedFact` ("Still true") puts it back. `unnameCharacter(ledger, characterId)` makes a relative the story named unnamed again: the name and the reused-name flag go, id, aliases, details and relation stay; refused for a record without a relation and when another record already has the display name it would get.

**Undo (issue #68).** Every hand edit of the popup passes `saveLedgerEdit`, so the undo records there, not per edit function; an edit added later is undoable without extra wiring. `showKnowledgePopup` starts a session (`startKnowledgeUndoSession`) and ends it on close (`endKnowledgeUndoSession`); outside a session `saveLedgerEdit` records nothing. The stack is `createUndoStack({ read, write, changedMessage })`, generic over a stored state and a way to read and write it, since #71 in `lib/ui/undo-stack.js`, the Arc Manager being its second caller. An entry holds `JSON.stringify` of the stored ledger before and after the edit; an edit that changed nothing is not recorded. `undoLedgerEdit()` (the status bar's Undo button and Ctrl+Z; the button's title and the status message name the edit by the label `saveLedgerEdit` got, kept per session in the view's `undoLabels`) restores the newest entry only while the stored ledger still serializes to the entry's "after"; otherwise it shows "The ledger changed since this edit (an update ran); undo is no longer possible." and drops the stack. The serialized comparison is the change check because the extraction and the rollback write into the stored ledger object in place (`getKnowledgeLedger()` then field writes), while a chat switch or a new ledger replaces it: an identity check misses the first, and a version counter would have to be bumped at every write site in `ledger.js`. The restore clears the stored object's keys and assigns the snapshot's in order, keeping the object (as `saveLedgerEdit` does) and the exact serialization, so a second undo's check still matches.

**Status line.** The settings drawer shows at which message the ledger was last updated (`updateKnowledgeStatus()`), so the player sees whether it is behind. While any record carries `nameClash`, the line appends "N new names to check" and an "Open Knowledge" button (`.story-arc-knowledge-names-btn`, bound in `setupSettingsPanelEvents`) that opens the Knowledge popup, with or without arcs.

**The reused-name flag** (issue #43, spec #35). Detection is a step of `applyExtractionAnswer`, so it runs on every path that applies an answer: the update after a reply and the re-extraction after a swipe switch or an edit. Before the new characters are added it takes `listTakenNames(ledger)`; `listSharedNames` compares each character it adds (its name and aliases, same derivation, folded) with that map, so characters added by the same answer are not compared with each other and clashes already in the ledger are never flagged. A shared name sets `nameClash: { names, at, messageId? }` on the new record: the shared names in the spelling the taken-names block prints (a hyphenated surname shares its parts, never the whole word), the last message the answer covered, and its message id. The field is absent on every other record, so older ledgers need no migration. A character the ledger already has is not added and so not checked; characters added in the Knowledge popup are never flagged. Character records are never rolled back, and neither is the flag. The update functions' `KnowledgeUpdateResult` carries `flaggedCharacters: [{ id, name }]` only when an apply flagged one (`withFlaggedCharacters`). `index.js` shows one toastr notice per flagged character ("New character Julian Stern shares a name with Solomon Stern. Check it in the Knowledge popup."), looking up who has the shared names now with `listCharactersWithNames` from `names.js`; the status line keeps the count in view. Naming an unnamed relative (`wasUnnamed` in the answer) skips the check on purpose: the relative is an existing record, not a new character, and a relative sharing the other character's surname (Kendra Osei's mother becoming Abena Osei) is what the rule allows, not a reuse. Saving a flagged character's rename or aliases in the popup (`renameCharacter`, `setCharacterAliases`) removes `nameClash`. Detection runs only when a record is added, so a cleared flag never comes back. No LLM call is added; the extraction prompt, the narration prompt and the update log's records are unchanged. **"Names to check"** (#48) sits at the top of the Knowledge popup, before and outside the spoiler groups, because a name is never a spoiler: `buildKnowledgeContent(ledger, chatMessages)` lists each flagged record with its name, each stored shared name with the characters who have it now (`listCharactersWithNames`, looked up when the section is built; a stored name no other record has any more is left out, and with none left the row says the clash is gone and offers only "Not a clash", since the glossary avoids "flag" in player-facing text), and the message it was named in, at its current index found by `nameClash.messageId` while that message is still in the chat, else `nameClash.at`. A one-line hint says to rename here first, then edit the chat text. The row's Rename button opens the same name and aliases editor as the Characters row; "Keep the name" calls `keepCharacterName`, which removes `nameClash` and nothing else. The flagged row inside the Characters group carries a "name to check" chip. The section shows names and message numbers only, never a fact. Every popup edit calls `updateKnowledgeStatus()`, so the status line's count drops at once.

**Character details (2026-11-05, issue #51, spec #50, ADR-0007 amendment).** In the Paragon chat the narrator put Kendra Osei's mother, established as an office cleaner on double shifts, on a night shift at Highland Hospital to free Kendra for a Friday night: once Summaryception has compacted the history, the narrator cannot see what the story set and invents it again. So each character record may carry `details`, one history list per kind of `DETAIL_KINDS` (`gender`, `age`, `role`, `relation`, `status`, in `constants.js`), oldest first; the current value is the last entry. An extraction entry is `{ value, at, messageId? }`. `gender`, `age` and `role` are short text as the story states it (`age` may be vague, "twenty-something"; `role` is the job or place in the world plus where it puts the character, "cleaner, double shifts, Oakland"); `relation` is `{ kind, of }`, a kinship word and the other cast member's id; `status` is `alive` or `dead` (`DETAIL_STATUS_VALUES`). An absent kind is unknown; older records have no `details` and need no migration. The popup's character saves spread the record, so they keep `details`.

**The switch (2026-11-05).** Character details have their own switch, `knowledgeTracker.characterDetails`, off by default like the tracker; `isCharacterDetailsEnabled()` in `settings.js` is true only while Story Arc, the tracker and the switch are all on. The builders take it as a parameter (`withDetails`), read once by their callers: `extractKnowledge`, `injectKnowledgeBlock` and the Knowledge popup's two renders. Unnamed relatives belong to character details and are off with them. While it is off the narrator and the extraction get what they got before details existed, and the extraction prompt is byte for byte the one from before them: its details and unnamed-relative parts are template placeholders (`{{CHARACTERS_DETAILS_NOTE}}` in the characters header, `{{UNNAMED_RELATIVES_TASK}}` after task 2, `{{NEW_CHARACTERS_SCHEMA}}` for the answer's `newCharacters` list, `{{DETAILS_TASK}}` before "Answer with ONLY", `{{DETAILS_SCHEMA}}` after the rulings list; their texts are constants in `ledger.js`). The characters list prints no details and no "(unnamed)" mark; `extractKnowledge` returns the answer with `details: []` and only the named new characters, without `wasUnnamed` (`withoutUnnamedRelatives`), so no nameless record is created and none is named; and the knowledge block prints no details line, no "dead" in a heading and no details header sentence. Nameless records already in the ledger keep their display names, which need the relation. Rollbacks of detail entries still run while it is off, like the tracker's own. The Knowledge popup hides the details summary, the details editor and the "New unnamed relative" form. Pinned by `tests/test-knowledge-details-switch.js`: with the switch off, a ledger holding details gives the same block and the same extraction prompt as the same ledger without them. While it is on, everything below holds unchanged.

- **Extraction input.** `buildKnowledgeExtractionVariables` prints each character's known details after its names, labelled by kind: `- Ama Osei (also: Ama) — gender: female; role: cleaner, double shifts, Oakland; relation: Kendra Osei's mother; status: alive` (`characterDetailTexts`, which the planner's cast (`harvestCast`) uses too, each value from `currentDetailText`; a relation reads "<other>'s <kinship>"). A record without details prints the line it printed before. The labels let the extraction see which kinds are known.
- **Task 8, DETAILS.** For a ledger character, a detail is reported when the ledger does not know that kind yet and the new messages state it, or when the new messages show it changing on screen (a transfer, a new job, a death, a dead character seen alive again); a new character from task 2 may carry details in the same list. Only what the text states, never a guess from a name, a look, a trope or likelihood; a known detail is not reported again unless it changes; a different value merely stated, with no such event, is not a change and is not reported (issue #52); out-of-character lines set no detail. Item: `{ character, kind, value, of?, change?, at }`, `value` always a string (the kinship word for a relation, `alive` / `dead` for a status), `of` the other character's name, for a relation only, `change` the on-screen event in one short sentence, only for an item that replaces a known detail.
- **Parsing.** `parseKnowledgeExtractionAnswer` reads a missing `details` as `[]`; a non-list, or an item without a character name, with a kind outside `DETAIL_KINDS`, a value that is neither a non-blank string nor a finite number, a non-integer `at`, a status other than alive or dead (compared in lower case), a relation without `of`, or a `change` that is neither a string nor null, rejects the whole answer, like a malformed `retracted` item. A detail is canon once recorded, so a half-understood item must not reach the ledger. A number (an age given as `17`) is stored as its string form; a blank or null `change` reads as none.
- **Apply.** `applyExtractionAnswer` records the details after the retractions and before the message-id pass, so new characters of the same answer can carry them and every entry gets its message's id like a holder entry. An item for a kind the player locked in the Knowledge popup is skipped before every other rule, even with `change` (issue #54; see "Character details in the popup"). An item for an unknown kind is recorded (a detail set). For a known kind (issue #52) the same value again, letter case aside (a relation by kinship word and the other character's id; `isSameDetailValue`), changes nothing; a different value is appended to the kind's history only when the item carries `change` (a detail changed: the old entry stays, the new one is current), and without `change` it is ignored as a restatement, the code-level guard behind the prompt rule. Items are applied in order, so of two items for one kind in one answer without `change` the first wins. `status` follows the same rule both ways: a death and a dead character back alive both need `change`. Being alive is never a first statement: an `alive` item for a character with no status yet is dropped without a count, so a status starts with a death (live check 2026-11-05 in the Amy chat: the extraction marked nearly every character `alive` though no text said so; the prompt now asks for `alive` only for a listed dead character shown alive again). The entry does not store the `change` sentence. A relation to someone outside the cast, or to the character itself, and an unknown character are ignored. `at` outside the covered messages falls back to the last of them, like every `at`. The apply counts what it did into its optional `detailCounts` argument (`detailsSet`, `detailsChanged`, `restatementsIgnored`, `detailsLocked`), which the update after a reply and the re-extraction pass on to their update-log record. Unnamed relatives: see "Unnamed relatives" below.
- **Rollback (issue #53).** Detail entries roll back with the text that set them, by the same predicates as holder entries (`keepOnlyDetailEntries`, called next to `keepOnlyHolders` in each of the three steps): `followMessagesById` keeps an entry with a message id at its message's new index and drops it with a deleted message; the index rule of `dropKnowledgeFrom` drops entries without one from the first gone index; the edit's `dropKnowledgeLearnedAt` drops only the entries set at the edited message, so its re-extraction finds those kinds as they were before the message. A kind is a history, so dropping its newest entry restores the previous value (the rollback of "nurse, Highland Hospital" gives back "cleaner, double shifts"); dropping its only entry makes it unknown, and the kind leaves `details` (a record with no kind left loses `details`, the shape it had before details existed). Entries with `at: null` survive every rollback. The character record itself is never rolled back. The `rollback` log record counts the detail entries dropped (`detailsDropped`).
- **The block.** For each present or talked-about character, `buildKnowledgeBlock` prints `- Details: female; 40s; cleaner, double shifts, Oakland; Kendra Osei's mother` right under the heading (`detailsLineForCharacter`: known kinds in `DETAIL_KINDS` order, status left out), and a dead character's heading reads `AMA OSEI (dead, talked about, not present)`; `alive` prints nothing. A character with a detail to print and no knowledge line still gets a section. When the block prints any detail, the header gains one sentence before its closing bracket: "A character keeps the details listed for them; a detail changes only when the story shows it changing." With no detail to print the block is byte for byte what it was before (pinned by the unchanged header constants in `tests/test-knowledge-block.js` and `tests/test-knowledge-inject.js`); with the tracker off both keys stay `''` whatever the ledger holds.

**Appearance (2026-11-11, design `docs/plans/2026-11-11-character-appearance-design.md`, ADR-0007 amendment).** StoryImage, the sibling extension that reads the ledger, kept looks from the newest messages only; in the Paragon chat Priya Mehta's description sat at #140, #520, #770 and #2825, her stored look came out like Ellie's, and the image model mixed them up. So a character's `details` may also hold the six `APPEARANCE_KINDS` (`constants.js`): `ethnicity`, `skin`, `hair`, `eyes`, `build` (height and body) and `features` (scars, tattoos, freckles, birthmarks, piercings, glasses, a beard, in one list), each a history of plain-word strings in the same entry shapes as the other kinds. They are kept apart from `DETAIL_KINDS`, so `characterDetailTexts` (and with it the planner's cast, `harvestCast`) and `detailsLineForCharacter` never see them. Rollback (`keepOnlyDetailEntries`, `detailEntriesOf`), the merge (`mergeDetails`) and the change items already go over every kind a record holds and needed no change. StoryImage reads `details.<kind>` with its own `detailAt` (the last entry at or before a message, by array order).

- **The switch.** `knowledgeTracker.appearance`, off by default; `isAppearanceEnabled()` in `settings.js` is true only while `isCharacterDetailsEnabled()` is and the switch is on. The drawer's "Appearance" checkbox (`#story-arc-knowledge-appearance`) sits under "Character details"; `applyTrackerDisabled` disables it while the tracker or character details are off. Off, the extraction prompt and the block are byte for byte what character details give (pinned in `tests/test-knowledge-details-switch.js`), `extractKnowledge` drops appearance items from the answer's `details` without a count, and the popup shows no appearance rows, no "What changed" lines of appearance kinds and no search. Stored appearance stays and still rolls back.
- **Extraction input.** `buildKnowledgeExtractionVariables` takes a ninth parameter, `withAppearance` (default false, effective only with `withDetails`). A character's known appearance kinds (`characterAppearanceTexts`, `kind: value` in `APPEARANCE_KINDS` order) are added to its line only when the new messages name it: `isNamedInText` with `listNameWordCarriers` on the new messages (hidden ones left out) each through `withoutTaggedElements`, because a preset's status block names characters who are not in the scene. Measured on the Paragon ledger (148 characters, a ~2.4k-token characters list): printing every look would add ~1.3k to ~2.5k tokens per reply.
- **Extraction task.** The appearance text lives in three placeholders inside the `DETAILS_TASK` and `DETAILS_SCHEMA` constants of `ledger.js`, not in `extract-knowledge.txt`: `{{APPEARANCE_KINDS_NOTE}}` (the six kinds with an example each, at the end of the "kind" bullet), `{{APPEARANCE_TASK}}` (after the task's rules: lasting looks only, never clothing, the day's jewellery, makeup or passing states; ethnicity only when named; `features` as one whole list; values without the kind's own word; a fuller description of a known appearance kind is reported without `change`, named as the exception to the task's "not reported again"; appearance goes into DETAILS, never LEARNED) and `{{APPEARANCE_SCHEMA_KINDS}}` (the kind field of the schema). `fillTemplate` runs one pass, so the builder fills them into the constants with `replaceAll` before returning.
- **Parsing.** `parseKnowledgeExtractionAnswer` accepts a kind from `DETAIL_KINDS` or `APPEARANCE_KINDS` whatever the switch; any other kind still rejects the answer.
- **Refinement.** A look is told piece by piece, and the restatement rule would freeze the first, vaguest description. In the apply, after locked, set, same and `change`, a different value without `change` for an appearance kind is appended when `isAppearanceRefinement(kind, current, value)` holds: words (lower-case runs of letters and digits, a hyphen splits them), the kind's own words left out of both sides (`APPEARANCE_KIND_WORDS`: hair; eye, eyes; skin), the new set larger and holding every old word, and no negation word (no, not, without, never, nor, longer: `APPEARANCE_NEGATION_WORDS`) the stored value lacks, so "freckles" → "no freckles" is no refinement. "dark hair" → "dark glossy curls, about shoulder length" refines; "dark" → "black" and "dark glossy curls" → "dark curls" are restatements; "dark" → "dark blonde" refines too, a known gap. Counted as `detailsRefined` in the `update` and `reextract` records. The other kinds never refine.
- **The block.** `buildKnowledgeBlock(ledger, messages, withDetails, withAppearance)`; a **present** character with a known appearance kind gets `- Appearance: Indian; skin warm brown; hair dark glossy curls; eyes warm brown; build petite, five-two; features freckles` right after its details line (`appearanceLineForCharacter`, ethnicity unlabelled). A talked-about character never gets it, for the reason the Has met line exists. The line alone gives a section and counts as a printed detail for the header sentence. `injectKnowledgeBlock` passes `isAppearanceEnabled()`.
- **Popup.** With appearance on, the character sheet's Details section gets an "Appearance" sub-heading after the detail rows, its six kinds as `buildDetailRow` rows (text fields; Edit / Set, Lock, Unlock / Clear as for the other kinds), and the search button on the sub-heading's line. The merge preview and the message search go over the appearance kinds too (`shownDetailKinds`); `saveCharacterDetails` and `lockCharacterDetail` accept them; `KIND_LABELS` has their labels; the result row's summary (`detailsSummary`) leaves them out. `buildKnowledgeContent` and `listChangeLines` take `withAppearance` as an extra parameter, default false.

**The appearance search (2026-11-11, Part B of the design).** Existing chats get nothing from the forward extraction, and in a long chat almost every message is hidden (Paragon: 3,258 of 3,294, hidden by the summary extension), the introductions among them. So a character's sheet offers "Find details" (until 2026-11-11 "Find appearance", before that "Search the chat"). Since 2026-11-11 it also finds gender, age and role (`SEARCHED_KINDS`; design note "Gender, age and role"). The button sits beside the Details heading whenever character details are on. Each finding is listed under the rows it would change (`buildFindingsList`: gender, age and role under Details, the looks under Appearance). With appearance off, `searchAppearance(…, withAppearance = false)` sends no appearance passages and offers only gender, age and role. The process is `lib/knowledge/appearance-search.js`:

- `findNamingPassages(chatMessages, names, sentPassages, maxChars)` (added with gender, age and role): the newest passages that name the character, describing or not, in the unit of the appearance passages (`listNamingPassages`, which `findAppearancePassages` also walks), a text the appearance passages already hold left out, newest first until the next would pass `maxChars` (4000), returned oldest first. `searchAppearance` sends them only while one of gender, age and role is not locked, merged with the appearance passages by message index. No age pattern and no introduction search (Stefan's minimal version).

- `findAppearancePassages(chatMessages, names, otherNames, maxChars)` reads every message, hidden ones included, through `withoutTaggedElements` (a tracker's clothing lines and a plot director's `<details>` speculation are not story), splits it into sentences (also on `;` and `•`), and keeps a sentence that names the person (or the pronoun sentence right after one) with a lasting-feature word or a height and a describing word next to it, nobody else named closer to the feature; ownership by "'s" or by the first named person, the longer name winning where two start at one place ("Kendra's mother" over "Kendra"). A sentence is in at most one passage: a pronoun sentence taken along with the naming one before it is not a passage of its own, so the cap and the budget count distinct text. Names match with a straight or a curly apostrophe alike. Ethnicity is its own feature group through a small fixed pattern (`X-American` style compounds, descent, heritage, ethnicity, "born in", a list of about thirty demonyms), only in the sentence that names the person. At most three of the newest passages per feature, within `maxChars` (6000) counted as the `[#at] text` lines, returned oldest first. Modelled on StoryImage's `findDescriptions`; StoryArc cannot import from a sibling extension. On Paragon: Priya 13 passages, 3.4 KB, ~175 ms, the four introductions among them; Ellie 17, about half noise.
- `findDefinitions(definitionTexts, lorebookEntries, names, otherNames)` (added 2026-11-11, design note "The definitions"): the texts written before the story that name the character, each `{ label, source, text }`. The persona description (`power_user.persona_description`, read by `readDefinitionTexts`; `getContext()` has no `persona` field) when the persona's name is one of the character's names, labelled `persona`; the card description of a card character of this chat (the one character or the group's members, never another chat's card of the same name), labelled `card`; a persona or card named by the first name alone, or the other way round, counts as the character, and its name then names them in lorebook text too; each capped at 3,000 characters, `{{user}}` (in lorebook text too) and a card's `{{char}}` (in a chat with one card also in the persona and in lorebook text and keys) replaced by function replacers, line breaks as " / ". Lorebook entries written during the story (arc summaries, memory books) also count as older than every message; accepted, since the chat they summarise wins over them. Then lorebook text from `fetchLorebookEntries` (the books ST scans for the chat), labelled `lore 1`, `lore 2`, …: an entry whose keys or comment name the character, up to 1,500 characters, goes whole (their sheet); from every other entry that names them, the sentences `findAppearancePassages` keeps; whole sheets first, within 3,000 characters, an entry that does not fit skipped for a later one that does. Without a name there is none.
- `searchAppearance(ledger, characterId, chatMessages, personaName)` takes the names from the ledger (the character's display name and aliases minus shared name words, and for an unnamed relative "<any name or alias of the other character>'s <kinship>" as `isNamedInText` does; every other character's names plus the persona), makes no call when there is neither a definition nor a passage, and otherwise fills `prompts/find-appearance.txt` (the display name, aliases, the known appearance, the definitions as `[label] text` lines, the passages) and sends it through `callLlm` (the arc generation profile). The prompt says the definitions are older than every passage: a passage wins on a disagreement, a definition fills what no passage states. The answer `{ details: [{ kind, value, sources }] }` (the older key `appearance` still reads; a numeric value such as an age reads as its digits) keeps one item per kind; `sources` lists every text the value uses, message indexes and sent definitions' labels (folded: "[Lore 2]" reads as "lore 2"); a single `at` instead reads as one source. A source that was not sent is left out; an item with an unknown kind, no sent source left or an empty value is dropped, not the whole answer, because the player reviews every finding. A finding's `sources` are the definitions' sources ("persona", "card", "lorebook: <book> / <entry>") in the order sent, then the message indexes, oldest first; its `at` is the newest message among them, or null for definitions only (Stefan's ruling 2026-11-11: a value with any chat part rolls back with its newest message); its passage is every text used, joined with " … ". It returns `{ findings, sourceCount }` (definitions plus passages) or `{ error }`.
- `listOfferedFindings(character, findings)`: a kind is offered unless locked, when the ledger does not know it, when the finding is newer than the current entry and differs, or when it refines the current value whatever its age (the Priya case: a vague "dark" the forward extraction set at #3295, the fuller "dark glossy curls" at #2825). A definition, a finding with `at: null` or a current record entry (`at: null, by: 'record'`), counts as older than every message (-1); a current record entry accepted over story entries counts as the newest of them, so their older values are not offered back; any other current entry without a message counts as newer than every finding. Accept checks every message among a finding's sources against the text the search read (`sourceTexts`, `findSourceMessageRefusal`).
- **Acceptance.** A finding turns the detail row it would change into the proposal (`buildProposalRow`, ruled 2026-11-11 from the mockup's layout B): the current value struck through or "unknown", an arrow, the found value; one source line ("Found in 10 messages, newest #3293, 4 hidden", `describeFindingSources`) with Show sources, which opens a chip per source (a hidden message marked) and the three newest message passages of the finding's `passages` (one per source, from `parseAppearanceAnswer`; a persona or card text shows only when no message does, as it can run to thousands of characters), the names the search finds them by (`listSearchNames`) marked with `namesPattern`; Accept and Skip in place of the row's fixes. Each section (Details, Appearance) says under its head what the last search found (`buildSearchResult`, from `view.appearanceSearches`: the kinds searched and found): the proposals left, or "Nothing new", naming the kinds the sheet already records. The findings are kept in the view per character, each with its source message's text at the time of the search (`sourceText`). Accept refuses a source message no longer in the chat or whose text changed since (`findSourceMessageRefusal`: an index shift after a deletion shows as a changed text), then checks the edit (`findAppearanceFindingRefusal`: an appearance kind, a character in the ledger, a value, not locked, and still offered by `listOfferedFindings` on the current ledger, so a finding a newer reply overtook is refused), and drops the line on every refusal; only then it gives the source message a Story Arc message id with `giveMessageId` (`message-ids.js`; hidden or not, an existing id kept) and saves `acceptAppearanceFinding(ledger, characterId, finding, messageId)` through `saveLedgerEdit`, so Undo covers it and `saveMetadata` saves the chat with the id. The entry is a story entry `{ value, at, messageId }`, appended even when older than the entry before it: a kind's history is in the order recorded and its last entry is current (ruled 2026-11-11). It rolls back with its source message like any story entry. A finding with a message among its sources is checked and stored at its newest message (`at`), as above. A finding from definitions only (`at: null`) skips `findSourceMessageRefusal` and `giveMessageId` and is stored as a record entry `{ value, at: null, by: 'record', source }`, its sources joined with " and ": it survives every rollback, locks nothing, and the sheet shows "From the <source>" (an update line it overtook: "Changed later, from the <source>"). Skip drops the proposal without an edit. Accept all (a primary button: in the head of a section with two or more findings, or one for the sheet when both sections have two or more, so the view keeps one primary) runs both refusals on every finding of its scope first, drops the refused ones (each refusal under its own section and appended to the status), gives the rest their message ids and saves them as one edit (`acceptAppearanceFindings`, chaining `acceptAppearanceFinding`), so one Undo takes them back together. Neither Accept nor Skip comes back with Undo as a proposal: undoing an Accept restores the ledger, not the view's findings.
- **A search id is not a read.** Before the search, only messages an update read carried a Story Arc message id, and two places relied on it: the edit of a hidden message (`isHiddenAndUnread`) and the fallback of `followMessagesById` when the last-read message is gone. When `giveMessageId` creates an id, it also sets `extra.story_arc_message_id_by_search` (`SEARCH_ID_KEY`, read by `isIdFromSearch` in `message-ids.js`); a message that already had an id gets no marker. `showsUpdateRead` in `ledger.js` answers both questions: a message shows an update's read when it has a read-text hash, or a message id the search did not create, or (read before #19) a holder entry at its index. That is the rule from before the search minus search-created ids, so a hidden message only the search gave an id makes no call when edited and keeps the entry, and every message an update read keeps its old behaviour. The marker never needs clearing: an update that reads the message later records its read-text hash, which counts first. `latestReadMessage` (which replaced `latestMessageWithId`) walks back from the end of the chat for the newest message that has an id and shows a read, so an accepted finding on an unread message cannot carry `lastUpdatedAt` past messages no update has read. A first version tested ledger entries instead of the marker; sizing on the Paragon chat (2026-11-11, read-only) found 595 hidden messages an update had read that taught nothing and had no read-text hash, whose rewrites that version would no longer have re-extracted.

**Unnamed relatives (issue #55, spec #50).** A recurring relative the story has not named ("Kendra Osei's mother", the case that started spec #50) is a cast member of its own: a record with `name: ''` and a relation. `characterDisplayName(ledger, character)` in `ledger.js` gives every printed name: a named record's name, else "<other character's name>'s <kinship>" from the current relation entry. The other character is printed by its own name only (a nameless one as "unnamed character <id>"), so two unnamed records related to each other never loop; a nameless record without a relation reads "unnamed character <id>". `characterName` returns the display name, so the knowledge block (headings, "Knows" and "Has told" lines, details lines), the extraction input (the characters list marks the record "(unnamed)", the facts list's holders), the popup (rows, relation and holder selects, fact holders, the name-conflict message) and the `flaggedCharacters` result all print it. The update log stores counts only and prints no name, so it needed no change. `findCharacterId` matches a record by its display name or an alias, ignoring case, so the extraction finds an unnamed relative by the display name; `isNamedInText` looks for the display name too, and for an unnamed relative also "<any name or alias of the other character>'s <kinship>" ("Kendra's mother" as well as "Kendra Osei's mother"), whole word, ignoring case, a straight or curly apostrophe alike; a relative is "talked about" only when the text uses such a phrase, not for "my mom".
- **Extraction.** Task 2 of `prompts/extract-knowledge.txt` lets a new character be an unnamed relative: `{ "name": "", "aliases": [], "relation": "mother", "of": "Kendra Osei" }`, called by its display name in the rest of the answer. When the new messages name one, the answer lists it under `newCharacters` with the new name and `"wasUnnamed": "Kendra Osei's mother"`, and uses the new name in the rest of the answer. `parseKnowledgeExtractionAnswer` reads a new character with an absent, null or blank name as `{ name: '', aliases, relation: { kind, of } }` and rejects one without `relation` and `of`; `wasUnnamed`, absent, null or blank, is none, and any other non-string rejects the answer.
- **Apply.** `applyExtractionAnswer` adds the named new characters first, then the unnamed relatives, so a relative may relate to a character the same answer adds. An unnamed relative is created only when `of` is in the cast and no record has its display name yet; its relation is stored as a record entry `{ value: { kind, of }, at: null, by: 'record' }`. That relation is the record's identity, so, like the record, it never rolls back (`at: null`); it is not `by: 'user'`, so it locks nothing and a later `change` can still change it. A detail history thus holds three entry shapes: a story entry `{ value, at: messageIndex, messageId? }` from the extraction, which rolls back with its message; a record entry `{ value, at: null, by: 'record' }`, the relation an unnamed relative was created with or (with `source`) an appearance finding the player accepted from the persona, card or lorebook, which survives every rollback and locks nothing; and a player entry `{ value, at: null, by: 'user' }` from the Knowledge popup ("Save and lock"), which survives every rollback and locks its kind. The popup's "Save" (2026-11-11) writes a record entry with `source: 'player'` instead (`isPlayerRecordEntry`): unlocked, shown as "Set by you"; the player's own value is one entry, locked or not, so either save, Lock and an emptied field replace or remove it. Only `by: 'user'` locks (`isDetailLocked`). A named new character with `wasUnnamed` that finds an unnamed record by that display name names it: the record keeps its id and details and gains the new aliases. Without such a record the character is added as usual.
- **Taken names exception.** `listTakenNames` skips every record without a name, aliases included: "Kendra Osei's mother" must not take "Kendra" or "Osei". So an unnamed relative never gets `nameClash` (`listSharedNames` finds nothing) and never shows under "Names to check". Naming an unnamed relative, by the extraction or in the popup, sets no `nameClash` either: a relative sharing the other character's surname is the exception the taken-names block itself makes. From then on the name counts as taken. `harvestCast` leaves nameless records out of the planner's cast: they have no name for a plan to use or avoid.
- **Popup.** Under the Characters group, "New unnamed relative" takes a kinship word and the character they relate to (`addUnnamedRelative(ledger, { id, kind, of })`): the relation is a player entry `{ value: { kind, of }, at: null, by: 'user' }`, so it is locked and survives every rollback; a second record with the same display name is refused, here and when `saveCharacterDetails` changes a nameless record's relation. The row's name editor shows "No name yet"; saving it with a name names the relative (`renameCharacter`, id and details kept), saving it empty keeps the record unnamed. `saveCharacterDetails` refuses to empty the only relation of an unnamed relative.

| Integration | API | Purpose |
|------------|-----|---------|
| World Info | `getSortedEntries()` from `/scripts/world-info.js` | Read the chat/persona/character/global entries ST itself scans |
| Chat messages | `chat` import from `/script.js` | Read history + signal scanning |
| Prompt injection | `setExtensionPrompt()` ×4 from `listStoryArcPrompts()` (`story_arc_plan` IN_PROMPT, `story_arc_knowledge` and `story_arc_names` IN_CHAT depth 1, `story_arc_signals` IN_CHAT depth 0, all system role) | Inject arc guidance + knowledge and taken-names blocks + signal directive |
| Prompt registry | `extension_prompts` (script.js), read at `CHAT_COMPLETION_PROMPT_READY` | The record of the last send (`saveLastSent`) |
| Outgoing prompt | in-place mutation of `eventData.chat` on `CHAT_COMPLETION_PROMPT_READY` | Stamp per-message arc counters (see `stamping.js`) |
| LLM calls | `ConnectionManagerRequestService.sendRequest()` (profile set) or direct `fetch()` to `/api/backends/chat-completions/generate` (fallback) | Run multi-phase generation (not `generateRaw()` — see Gotchas, a14ae32) |
| Per-chat persistence | `chat_metadata` + `saveMetadata()` | Store arc plans |
| Global settings | `extension_settings` + `saveSettingsDebounced()` | Store config |
| Events | `eventSource.on(event_types.*)` | React to chat lifecycle |
| UI popups | `Popup` class from `/scripts/popup.js` | Wizard, arc manager and wand popup |
| Wand menu | append to `#extensionsMenu` | "Story Arc" quick-access entry next to the chat bar (f4a0503) |

Key events used:

| Event | Handler |
|-------|---------|
| `GENERATION_STARTED` | Build and inject arc guidance (or clear it when no arcs / disabled); set the knowledge block (`''` while the tracker is off) |
| `MESSAGE_RECEIVED` | Parse signals, complete beats named by `COMPLETE` markers, flush queued marks, scrub leaked ids, refresh progress; then start the knowledge update (not awaited), which with the tracker on also completes the beats it reports and refreshes progress when it did |
| `USER_MESSAGE_RENDERED` | Promote the next beat in arcs left without an active one |
| `MESSAGE_DELETED` | Drop queued marks and reopen completions from the new chat length on; ledger knowledge and completion records follow their messages by message id (index rule for those without one) |
| `MESSAGE_SWIPED` | Drop queued marks, reopen completions and drop ledger knowledge from the swiped message on; re-extract a switched-to existing swipe |
| `MESSAGE_EDITED`, `MESSAGE_UPDATED` | When the text differs from the one read: reopen the beats completed at the edited message (`autoTrack` on) and re-extract its knowledge (tracker on) |
| `CHAT_CHANGED` | Re-initialize per-chat state, reopen completions past the chat's end, refresh UI, drop ledger knowledge past the chat's end, refresh the knowledge status line |

`MESSAGE_RECEIVED` fires only for AI messages; user messages fire `USER_MESSAGE_RENDERED` (the same event Story Mode counts rounds on). The split is what makes the promotion gap a *user* turn rather than any turn.

**Emission order matters here.** `Generate()` emits `GENERATION_STARTED` at its top (`public/script.js:4299`) and only calls `sendMessageAsUser()` — which emits `MESSAGE_SENT` and then `USER_MESSAGE_RENDERED` — about 150 lines later (`:4453`, emitting at `:5912`/`:5919`). The injection for the message the user just typed is therefore built *before* promotion runs, so a freshly promoted beat's pressure first reaches the model on the generation after that. The resulting sequence, per completed beat:

1. AI message completes a beat; the arc is left with no active beat.
2. The player types a reaction. Its generation still sees the linger directive → the AI writes one consequences/breather message with no beat check.
3. The player types again. This generation carries the newly promoted beat's pressure.

One AI message of breathing room per beat, which is the intent. With the knowledge tracker on, step 1 is the extraction's answer instead, a few seconds after the reply (or up to `updateInterval` replies later); promotion still waits for the first user message after the completion is applied, and a user message sent while the extraction runs is built with the beat still active. This cannot be shortened by choosing a different event: every user-message event fires after `GENERATION_STARTED` inside the same `Generate()` call. Promoting in `onGenerationStarted` instead would restore exactly the chaining the design removes, because empty-input continues also go through `Generate()`.

## Gotchas

- **Arc generation deliberately does not go through `generateRaw()`.** It adds fields (`include_reasoning`, `reasoning_effort`, `type`, `stop`, `logit_bias`, …) that make some providers answer 502. The profile route goes through `ConnectionManagerRequestService` (a controlled payload via `ChatCompletionService.processRequest`, not the `generateRaw` path); the no-profile fallback `callBackendDirectly()` sends the minimal body SillyTavern-MemoryBooks uses — `messages`, `model`, `temperature`, `max_tokens`, `chat_completion_source`, plus `custom_url` when set. Pinned by a14ae32, e65449d.
- **`maxTokens: undefined` is how the profile preset's response length wins.** `ChatCompletionService.createRequestData` deletes undefined payload keys *before* `presetToGeneratePayload` merges the preset, so an undefined `max_tokens` lets the preset's value through. Passing a number would override the preset on every call. Pinned by e65449d.
- **The signal directive must never live inside the budget-trimmed plan text.** The trim slices from the tail, the directive was the last section — so on any plan larger than the budget the model never saw the signal protocol at all. This was the primary reason tracking never worked. It now injects separately (`story_arc_signals`). Pinned by 27c3d17.
- **The signal directive only works at IN_CHAT depth 0.** In the system prompt or even one message from the end, GLM 5.2 demonstrably reasoned about the beats in its chain-of-thought and still skipped the marker; as the final message before generation it complied. Marker goes on the reply's *first* line — end-of-message markers are eaten by response-token-cap truncation. Pinned by 27c3d17.
- **Beat progression needs explicit promotion.** Completing a beat does not make the next one `active` by itself; without a promotion step the arc has no active beat after the first completion, the directive lists no markers, and tracking silently dies. Promotion now lives in `promoteNextBeats` on `USER_MESSAGE_RENDERED` — deliberately one user turn later than the completion, never in `completeBeats`. Pinned by 27c3d17 (the step) and this change (its placement).
- **A visible plan is a task list.** Listing pending beats with ids and intentions made GLM 5.2 drive at them: 7 of 10 non-optional beats in ~8 exchanges on a 40-message arc, with beat intentions parroted into dialogue. The plan text now shows one beat, as a pressure, without ids. This is the primary pacing brake; the prompt-side "do not advance for N more messages" rule was ignored every time.
- **Never refuse a completion for being too fast.** The signal arrives after the scene is already on screen, so refusing it makes the tracker disagree with the visible story and re-arms the same marker instruction next message — a loop. Bookkeeping stays liberal; the pace is controlled by what the model is shown, not by what the recorder accepts.
- **Do not migrate stored arcs to add `pressure`.** Arcs planned before 2026-08-29 have beats without the field; `buildEpisodeSection` (`builder.js`) falls back to `intention` and they keep working. A live arc in the owner's test chat depends on this.
- **`setExtensionPrompt` takes `(key, value, position, depth, scan, role, filter)`.** The original call passed seven positional args (an extra `0` before `scan`), shifting `role` into `scan` and the role constant into `filter` — it only worked because everything coerced to the intended values. Pinned by 27c3d17.
- **`generateQuietPrompt()` is not the alternative.** It routes through the full chat pipeline, which re-enters Story Arc's own `GENERATION_STARTED` / `MESSAGE_RECEIVED` handlers while a plan is being generated. Tried in 8787fea, reverted in a700465.
- **Non-streaming requests time out on large prompts.** The arc prompt arrives as one 24K+ char message and exceeds nano-gpt's ~38s non-streaming ceiling; normal chat escapes this only because its prompt is spread over many small messages. The request therefore sets `stream: true` and reassembles the SSE `data:` events, stopping at `[DONE]`. Pinned by a257d92.
- **The model name must come from `getChatCompletionModel(oai_settings)`.** `oai_settings.openai_model` is only correct for the OpenAI source — nanogpt keeps its model in `oai_settings.nanogpt_model`, so reading the field directly sent "gpt-5" to a backend that does not serve it. Pinned by ca2dfb8.
- **A 200 OK can still be an error.** Some backends return `{ error: … }` in a 200 body, and errors also turn up inside individual SSE chunks. Both paths throw instead of handing the body to the arc JSON parser, which otherwise reports it as a parse failure. Pinned by 3a14aa3.
- **The settings drawer needs ST's exact markup.** The header div must carry `inline-drawer-toggle` — ST binds its click handler to that class, not to `inline-drawer-header` — and without it the drawer silently never opens. Pinned by 1310dc7. Leave the styling to ST too: wrapper padding and a header border misalign the panel in the drawer list (a09887b).
- **Assistant-last histories make RP presets restart the scene.** Celia injects `<latest_turn_start>`/`<latest_turn_end>` wrappers at fixed IN_CHAT depths 1/0; when the user generates without typing (a normal way to advance the story), the wrappers label the model's *own last reply* as "the latest turn to answer", and GLM re-answered the last user message from scratch — three parallel takes of the same scene. The signal directive's continuation guard counters this at depth 0. Pinned by 8dbfdb1.
- **Every popup must unbind its click namespace when it resolves.** The handlers are delegated on `document`, so they outlive the popup's DOM. The wizard's `click.storyArcWizard` stayed bound after the wizard closed, and one click in the arc manager then fired both modules' `.story-arc-spoiler-toggle` handlers — the spoiler toggled twice and looked like nothing happened. The manager leaked the same way in reverse. Each popup now calls `$(document).off('click.<namespace>')` after `await popupPromise`. Pinned by 7945e3a; `wand-menu.js` follows the same pattern for `click.storyArcWandPopup`, and needs it more than the others because the popup is reopened in a loop.
- **`MESSAGE_RECEIVED`'s index is not always `chat.length - 1`.** `/sys at=N` emits the event with the index of the inserted message (`public/scripts/slash-commands.js:6006`); every other emission site (`script.js:6691,6716,6738,6781`, `group-chats.js:300`) does use the last index. `processSignalResults` therefore takes `messageIndex` from the handler instead of re-deriving it, so `lastFulfilledAt` points at the message that actually carried the marker. Pinned by 9c3e980.
- **Stored arcs are never re-validated.** The tier band clamp (episode 8–20) and the milestone rules apply at generation only; an existing episode with `estimatedLength: 40` keeps it, and re-plan replaces `estimatedLength` from the fresh generation. Reading the clamp as "no arc can have 40" is wrong for every arc planned before 2026-09-16 (77dbf33).
- **Never re-list the re-planned arc in Phase 2's existing arcs.** It sits in the `ARC SO FAR` block; the existing-arcs list carries "do not duplicate these", so listing it there too tells the model not to cover the arc's own ground. Phase 1 gets the `[BEING RE-PLANNED]` mark instead (e3b81d8).
- **Prompt clauses steer; only post-processing guarantees.** GLM pastes beat ids and next-beat agendas into Celia's `[Main-line]`/journal blocks even when told not to; because those blocks re-enter the prompt as history, the model ends up pacing the arc off its own agenda instead of the pacing rules. `scrubArcInternals` deletes the ids mechanically after every AI message — the confidentiality clause reduces the leakage, the scrub makes the identifiers unable to persist.

## Design Principles

1. **Context-first** — arc quality is bounded by context quality. Lorebook classification, chat trimming, and character harvesting are all weighted toward signal over noise.
2. **Narrative-first schema** — beats express *intention*, not script. Secrets, foreshadowing, and triggers give the AI creative latitude while keeping the arc on track.
3. **Conservative pacing** — phase advancement requires both beat completion and message count to exceed the threshold. The AI is explicitly told not to rush.
4. **Non-destructive** — read-only access to lorebook, chat history, and character data. Only `chat_metadata.story_arc` is written.
5. **Lean** — no bundler, no library, no file storage beyond `chat_metadata`. One module per responsibility. No features outside the core loop: harvest → plan → inject → track. One exception, by decision (ADR-0007): the optional knowledge tracker keeps the one kind of memory the plan's secrets need, who knows what; Story Arc still does not summarize or manage lorebooks.
6. **Graceful degradation** — any single context source (lorebook, chat, character) is sufficient for generation. Empty sources produce placeholder text rather than errors.
