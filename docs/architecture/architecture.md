# Architecture

- **Coverage:** `index.js`, `lib/`, `prompts/`
- **Last Updated:** 2026-11-04

System design for Story Arc. For quick reference, see [CLAUDE.md](../../CLAUDE.md). For file index, see [code-index.md](./code-index.md).

## High-Level Data Flow

```
User clicks "Plan Next Arc"
       |
       v
Context Harvesting  (lib/context/)
  ├── Lorebook: classify World Info entries into constants / arc-summaries / recent
  ├── Character: pull character card fields + user persona
  ├── Chat history: extract recent messages within token budget
  └── Existing arcs: read active/completed arcs from chat_metadata
       |
       v
Arc Generation  (lib/planning/)
  ├── Wizard input: tier (episode / act / saga, from TIER_TABLE) + free-text direction;
  │     in revise mode (re-plan) also the arc being re-planned with edited title/premise
  ├── Phase 1 — Analysis: send harvested context through analyze-context.txt prompt
  │     → LLM produces a prose story-state summary (a re-planned arc is marked
  │       [BEING RE-PLANNED] so its unfulfilled beats are not reported as open threads)
  ├── Phase 2 — Arc Outline: send analysis + user direction through generate-arc.txt,
  │     with {{TIER_BLOCK}} (beat kind, count, length band) and, on re-plan,
  │     {{ARC_SO_FAR}} (premise, secrets, fulfilled beats as "already happened")
  │     → LLM returns a JSON arc plan
  ├── Each LLM call: ConnectionManagerRequestService (when a generation profile is
  │     configured) or direct streaming POST to /api/backends/chat-completions/generate,
  │     auto-retried (max 2, linear backoff) on transient errors
  ├── Parse + validate JSON (strip fences, extract object, schema-check; the tier
  │     shapes the beats: scene beats ordered with one active, milestones all active;
  │     estimatedLength clamped to the tier's band)
  ├── Retry once with stricter JSON instruction if parse fails
  ├── Re-plan only: mergeReplan(existing, generated) keeps the situation, replaces the road
  └── Normalize schema, assign defaults, save to chat_metadata.story_arc.arcs
      (re-plan: updateArc on the existing id instead)
       |
       v
Prompt Injection  (lib/injection/)
  ├── On GENERATION_STARTED: read active arcs from storage
  ├── Calculate current phase for each arc (beat ratio × message ratio, take minimum)
  ├── Build TWO arc injections:
  │     story_arc_plan (IN_PROMPT) — token-budgeted plan text, one section per arc
  │       chosen by (tier, focus) — see "Tiers and Focus" below and lib/injection/builder.js:
  │       Episode, normal/spotlight — premise, tone, the ACTIVE beat's pressure only,
  │                          secrets, foreshadowing, triggers, pacing directives, anti-patterns
  │       Act/saga, normal — premise + every unfulfilled milestone's pressure as
  │                          STANDING PRESSURES, then gated secrets, triggers, foreshadowing
  │       Act/saga, spotlight — same section, pressures under BRING TO A HEAD + one
  │                          trailer sentence; ordered first
  │       Paused (any tier) — one line: premise + "pending, not being pursued right now"
  │     story_arc_signals (IN_CHAT, depth 0) — ARC PACING brake for the pacing clock;
  │       continuation guard + confidentiality clause always (whatever autoTrack says);
  │       with autoTrack on the PLANT CHECK, and only while the knowledge tracker is
  │       off the BEAT CHECK listing every active beat of every non-paused arc
  │       (ADR-0008). Placed as the last message before generation (models ignore
  │       it anywhere else)
  ├── Both are set to '' when no arcs are active or the extension is disabled
  ├── Third injection, independent of the arcs — story_arc_knowledge (IN_CHAT, depth 1,
  │     system): the knowledge block, "who knows what" for the characters present and
  │     talked about (lib/knowledge/ledger.js, see "Knowledge Tracker" below); set on
  │     every GENERATION_STARTED, '' while the extension or the knowledge tracker is off
  ├── Fourth injection, set right after the third under the same gate — story_arc_names
  │     (IN_CHAT, depth 1, system): the taken-names block, every name the ledger's
  │     characters use (lib/knowledge/names.js, see "Knowledge Tracker" below)
  └── On CHAT_COMPLETION_PROMPT_READY: stamp each user message in the OUTGOING
        prompt array with "[Arc: message N of ~M]", N derived from that message's
        own chat index. Old positions never change bytes, so the provider's
        prefix cache survives. Stored chat and the UI are untouched.
       |
       v
Beat Recognition and Progress Tracking  (lib/injection/signals.js,
                                        lib/planning/beat-completion.js)
  ├── On MESSAGE_RECEIVED: scan AI message for [ARC_SIGNAL:arcId:itemId:VERB]
  │     (emitted HTML-comment-wrapped; bare form still parsed for old messages);
  │     COMPLETE markers are asked for only while the knowledge tracker is off
  ├── completeBeats (both recognition paths): mark the named beats completed
  │     (active only; at most one per arc per message); stamp arc.lastFulfilledAt
  │     with the fulfilling message's chat index; unlock gated beats whose
  │     unlockAfter prerequisites are all complete; complete the arc when all
  │     non-optional beats are done; record the completion on the beat
  │     (beat.completion) so a rollback can reopen it
  ├── Queue PLANTED (clue) and FIRED (trigger) marks; apply the queue when a beat
  │     completed (in this message, or in the extraction's answer) or the oldest
  │     mark waited MARK_FLUSH_WINDOW (20) messages, so marks cost no miss of their
  │     own when a beat completes, and at most one per 20 messages otherwise
  ├── Strip signal tokens (and their leftover blank lines) from the message
  ├── Scrub leaked plan identifiers (beat/arc ids, all arcs) from the message
  ├── Save updated arc state to chat_metadata, refresh progress UI
  ├── Knowledge tracker on: every N replies, one extraction call (not awaited) reads
  │     the messages since the ledger's last update, records who learned what, and
  │     reports the beats the messages fulfilled, which go through completeBeats.
  │     Deleting, swiping or editing a message, or loading a branch, takes back what
  │     the ledger learned from it (lib/knowledge/ledger.js)
  └── Deleting or swiping a message, or loading a branch that ends before it, reopens
        the beats it completed (reopenCompletionsFrom, both paths); an edit reopens
        them before the re-extraction reads the message again (reopenCompletionsAt,
        tracker on)
       |
       v
Beat Promotion  (lib/injection/signals.js — promoteNextBeats)
  ├── On USER_MESSAGE_RENDERED: for every active episode without an active beat,
  │     promote its first pending beat to active and persist; for every act or
  │     saga, activate every pending milestone (all milestones stand at once)
  └── Between completion and promotion an episode lingers: the plan section carries a
        "develop the consequences" directive instead of a pressure, and no beat
        is offered for recognition. The player always reacts before the model learns
        what comes next; the next user message always ends the linger
       |
       v
UI Display  (lib/ui/)
  ├── Settings panel in ST extension drawer (setup rows only)
  ├── Wand-menu entry + popup (Plan / Manage / progress cards) — the everyday route
  ├── Planning wizard popup (context preview → tier + direction → generation progress);
  │     the same popup in revise mode re-plans an existing arc
  ├── Arc manager popup (list arcs, focus paused/background/normal/spotlight, re-plan, delete)
  ├── Knowledge popup (tracker on; from the Arc Manager and the wand popup): the
  │     knowledge ledger behind closed spoiler drawers, corrected by hand
  └── Compact progress widget in ST sidebar (beat/milestone count, phase, "~N msgs to
        next phase", and the stall nudge "May have drifted — re-plan?")
```

## Module Responsibilities

### lib/core/

Shared constants, settings management, and per-chat state initialization.

- `constants.js` — `MODULE_NAME`, `INJECTION_HEADER` (first line of the plan block; doubles as the marker that tells the stamping pass "this is the real chat prompt"), `defaultSettings`, `defaultPerChatSettings`, `ARC_PHASES` (five phases with 0–1 percentage ranges), `PHASE_ORDER`, `PACING_DIRECTIVES` (one directive string per phase), `TIER_TABLE` (episode/act/saga: `label`, `beatKind`, `beatCount`, `lengthBand` — design spec 2026-09-16 §1; read by the generator's tier block, the validator's clamp, the milestone section header and the UI badges, so prompt and validator cannot drift apart), `ARC_FOCUS`, `createDefaultArc()` factory. For the knowledge tracker (ADR-0007): `defaultKnowledgeTrackerSettings` (`{ enabled: false, updateInterval: 1 }`, nested in `defaultSettings.knowledgeTracker`), `KNOWLEDGE_PROMPT_KEY` (`'story_arc_knowledge'`), `HOLDER_HOW` (the four holder values `witnessed`, `told`, `user`, `plan`, used instead of string literals) and `createEmptyKnowledgeLedger()`, whose JSDoc is the ledger's schema of record
- `settings.js` — `loadSettings()` / `getSettings()` / `isEnabled()` for global extension settings; `ensureChatState()` initializes `chat_metadata.story_arc` on demand and runs `migrateArc()` over every stored arc; `getChatSettings()` returns per-chat settings with defaults merged. `arcTier(arc)` and `arcMessageStart(arc)` state the two fallbacks every reader uses: an arc without a tier is an episode (the migration rule), an arc without `messageStart` counts from chat index 0; tests pin both. `getArcs()` and `getChatSettings()` carry a comment at the `ensureChatState()` call saying that the read may migrate and save. Knowledge tracker: `loadSettings()` merges the stored `knowledgeTracker` group over its defaults key by key (so a stored group missing `updateInterval` gets 1); `getKnowledgeTrackerSettings()` returns that stored group, `isKnowledgeTrackerEnabled()` reads its switch; `ensureChatState()` creates an empty ledger in a chat that has none (every chat from before the tracker), and `getKnowledgeLedger()` returns `chat_metadata.story_arc.knowledge` after it; `secretHolders(secret)` reads a secret's holder names, `[]` for a secret planned before holders existed
  - **Migration (2026-09-16, ADR-0001).** An arc without `tier` was planned before tiers existed. It becomes `tier: 'episode'` (its beats are ordered scene beats, so no other tier fits); `focus: 'foreground'` → `'normal'`, `'background'` → `'paused'` with `pausedAt = chat.length` at migration. Nothing else on the arc changes. `ensureChatState()` runs on every `getArcs()`, so the migration happens before the first injection is built; `saveMetadata()` is called once when anything migrated. The guard is `arc.tier` being set, not a version number. The old words survive in exactly one place: the episode section's header line still reads `=== FOREGROUNDED: "<title>" ===`, kept byte-for-byte so existing chats' cached prompt prefixes do not change (158358d). Outside `migrateArc()` itself and this note, nothing uses "foreground" any more. "background" came back on 2026-10-25 as a focus value with a different meaning (an act or saga kept off-screen, ADR-0001 amendment); the migration only touches arcs without a tier, so a pre-tier `background` still becomes `paused` and a tiered `background` arc is never migrated (`tests/test-background.js`).

No other module depends on more than `core/`. Core has no circular dependencies.

### lib/context/

Harvests story state from all available ST data sources.

- `harvester.js` — `harvestContext()` gathers every source and returns a `HarvestedContext` object with fields: `character`, `persona`, `lorebook` (split into `constants` / `arcSummaries` / `recent`), `chatHistory`, `existingArcs`, `cast`, `estimatedTokens`. `cast` (issue #44) is the knowledge ledger's characters as `{ name, aliases }`, in ledger order, read through `getKnowledgeLedger()` in `core/settings.js`, while Story Arc and the knowledge tracker are on (`isEnabled()`, `isKnowledgeTrackerEnabled()`); with the tracker off it is `[]` (ADR-0007). Its names and aliases count in `estimatedTokens`. The planner gets it in Phase 2 (`formatCastBlock`, under `generator.js`). `chatHistory` holds story messages only: `selectStoryMessages` drops any message that names an id of a stored arc of any status (`arcInternalIds` from `signals.js`), quotes `INJECTION_HEADER` or holds `ARC_SIGNAL` (2026-10-30). A narrator's OOC analysis that printed a secret beside its id had been read by the planner as story, and the secret came back as a milestone pressure. Other OOC messages stay, because the user's own direction belongs in the planner's input
  - Lorebook: `fetchLorebookEntries()` reads World Info entries, `filterAndSort()` and `categorizeEntries()` classify them by comment/tag into three buckets (all three exported for tests)
  - Character: the private `getCharacterData()` pulls character name, description, personality, scenario; the private `getPersonaData()` reads the active user persona
- `chat-history.js` — extracts recent chat messages up to a token budget; exports `estimateTokens()` (character-count heuristic: chars / 4)

### lib/planning/

Arc generation, validation, storage, and prompt template management.

- `generator.js` — `generateArc(context, userDirection, callbacks, { tier, reviseArc, genre })` runs the two-phase LLM pipeline and stamps `tier`, `direction`, `genre` (only when non-empty), `messageStart` and `lastFulfilledAt` (= `messageStart`) on the validated arc. The tier travels three ways: `{{TIER_BLOCK}}` in Phase 2 (`buildTierBlock`, below), `validateArcPlan(parsed, { tier })` so the wizard's choice wins over whatever `tier` the model echoed (4246cf1), and the stamp on the result. Phase 1's `formatExistingArcs(arcs, reviseArcId)` marks the arc being re-planned `[BEING RE-PLANNED]` (`analyze-context.txt` explains the mark); Phase 2's existing-arcs list *omits* that arc — it is presented in the `{{ARC_SO_FAR}}` block (`buildArcSoFar`, below) instead, and listing it under "do not duplicate these" would tell the model not to cover its own ground (e3b81d8). The genre (ADR-0004) travels as `{{GENRE_BLOCK}}` in both phases, rendered by the exported `formatGenreBlock(genre, 'analysis' | 'outline')`: Phase 1 reads the story through it and reports material that leans another way as an imbalance, Phase 2 gets it as `== GENRE (binding) ==` above the creative direction. An empty genre renders no block. The genre is set from the wizard after validation, never from the model. **The cast in Phase 2 (issue #44).** The harvested `cast` travels as `{{CAST_BLOCK}}`, right after `{{GENRE_BLOCK}}`, rendered by the exported `formatCastBlock(cast, 'outline')`: `== CAST (characters already in the story) ==`, one line per character with its aliases, the taken names (`printTakenNames` from `knowledge/names.js`, the derivation of #39, sorted as the narrator's block lists them) and two rules: existing characters are named exactly as listed, everywhere in the plan, holders included; a new character gets none of the taken names as a first name or surname, unless the plan makes them related to the character who has it and says so. The FINAL CHECKLIST line on existing characters' names ends in `{{CAST_CHECKLIST}}`, `formatCastBlock(cast, 'checklist')`, which points it to the cast block. An empty cast renders `''` in both slots, so with the tracker off the outline prompt is byte-identical to the one before. Phase 1 gets no cast, and no call is added: a plan still costs three. Holders spelled as the ledger names them let the extraction link a revealed secret to them. When `reviseArc` is set, the validated plan is passed through `mergeReplan(reviseArc, arc)` (`replan.js`, ADR-0003) *inside* `generateArc`, so the wizard's review step shows the merged arc and Regenerate re-merges. Phase 3 is the plan check (2026-10-30, ADR-0006): `runPlanCheck(arc, story, revealableSecretIds, callbacks)` runs on the validated arc, on re-plan after the merge, so it sees every secret with its `disclosed` state and the ids the plan will be stored with. `buildPlanCheckVariables` fills `prompts/check-plan.txt` with the premise (on a re-plan the proposed premise, `proposedPremise`, since the road was planned around it; the check never rewrites the premise) and the direction (passed as public, so carrying them out is never a give-away), every secret by id with phase and disclosure, the unfired triggers, and the pressures and the fulfillments (`{{FULFILLMENTS}}`, the `intention`) of beats not yet completed; a completed beat's fulfillment is never passed, because it has already been recognised as written; a re-plan also gets the Phase 1 analysis and the last 10 harvested messages (`PLAN_CHECK_RECENT_MESSAGES`). The model answers `{ revealed, rewrites: [{ kind, id, text }], links: [{ trigger, secret }] }`, and the exported pure `applyPlanCheck(arc, answer, revealableSecretIds)` applies it to a copy: rewrites only the `action` of unfired triggers and the `pressure` and `intention` of open beats (a trigger rewrite that echoes the `IF … →` line is cut to the action), sets `disclosed` only for secrets of the arc being re-planned, and for those the `revealed` list decides both ways: a secret it leaves out goes back to `disclosed: false` (2026-10-31; a re-plan made while a leaked message was in the chat kept stating the leak after the user regenerated that message). On a re-plan the old `disclosed` mark is not shown to the check, so it judges from the story alone. A secret marked done by hand in the Arc Manager can therefore be un-marked by a re-plan, and fills a trigger's `secret` link only when it is empty or unknown. Unknown ids, empty texts and wrong shapes are ignored. **Fulfillment rewrites (2026-11-04, ADR-0006 amendment).** The check's task 3 finds every fulfillment that is a tally of many scenes ("has completed her first patrols") or a chain of separate events joined by "and", and rewrites it as the one on-screen moment at which the development shows; it answers each as a rewrite with `kind: "fulfillment"`. Recognition judges a message or two at a time (ADR-0008), and a sum over scenes never shows in one: a tally stayed open for 439 messages in the Paragon chat. `applyPlanCheck` applies such a rewrite only to a beat not yet completed; a fulfillment rewrite for an unknown or completed beat, or with an empty text, is ignored and logged, since it leaves a beat that may never be recognised. A failed or unreadable check keeps the plan as generated and says so through `onProgress('retry', …)`. Live run on the re-planned Paragon act (after the premise/direction block was added): both revealed secrets found, the three give-aways rewritten, the other five items left alone; the run before it had rewritten two items that carried out the author's direction. The old detail-pass draft `prompts/detail-pass.txt` remains, and the template loader does not accept it; its allow-list (`VALID_TEMPLATES`) holds `analyze-context.txt`, `generate-arc.txt`, `check-plan.txt` and the knowledge tracker's `extract-knowledge.txt`. `callLlm` is exported because the knowledge extraction (`lib/knowledge/ledger.js`) sends its call through the same transport, profile and retry loop. Phase 2 asks for each secret's `holders`, the characters who know it when the arc starts (`generate-arc.txt`, schema line and a guideline: leave out everyone who learns it on-screen later, and the people the secret is aimed at). Phase 2 also asks for every `intention` as ONE on-screen moment at which the development shows, which may come in many forms, never a tally of many scenes or a chain of separate events joined by "and", for scene beats and milestones alike (`generate-arc.txt`: the two-faces text, the schema line and a FINAL CHECKLIST line; `detail-pass.txt` carries the same rule; 2026-11-04). `generateArc` includes retry logic for JSON parse failures; supports progress callbacks (`onProgress`, `onChunk`, `isCancelled`). Both phases go through `callLlm()`, which builds a system+user message pair (large prompt as system message, short user trigger) and wraps the call in a retry loop (max 2 retries, linear backoff `2000 * (attempt + 1)` — 42bce4a, d064dc3; 42bce4a's message says "exponential", the code is linear). Whether an error is retried is decided by the exported `isRetryableError(detail)`, which matches `502|503|504|timeout|gateway|ETIMEDOUT|empty response` against `err.message` plus `err.cause?.message`. `empty response` is in that list because reasoning models (glm-5.2:thinking) sometimes emit only reasoning deltas and no content, which the routes below turn into `Empty response from API` — a per-call accident worth retrying. Auth, quota and model errors are deliberately not retryable: they fail identically every time and retrying only costs the user minutes. Each retry is reported through `onProgress('retry', …)` so the wizard shows it. The call itself takes one of two routes (e65449d):
  - **Profile route** — when `defaultConnectionProfile` is set, `callViaProfile()` streams through `ConnectionManagerRequestService.sendRequest(profileId, messages, undefined, { stream: true })`. `maxTokens` is deliberately `undefined`: ST deletes undefined payload keys before merging the profile preset, so the preset's response length wins — this is the owner-intended replacement for the old hardcoded `max_tokens: 4096` (INTENT of 2026-08-28 implemented in e65449d).
  - **Fallback route** — no profile configured: `callBackendDirectly()` POSTs a minimal body to ST's `/api/backends/chat-completions/generate` with `stream: true` and assembles the SSE deltas (a14ae32, a257d92). The body runs through ST's `EventSourceStream` (`/scripts/sse-stream.js`), which buffers until an event is complete, so an event split across two network chunks arrives whole; a complete event that is not JSON fails the call rather than being skipped. Each event's text is read by ST's `getStreamingReply(parsed, state, { chatCompletionSource })` from `/scripts/openai.js`, which knows every source's event shape (OpenAI `choices[0].delta.content`, Google `candidates[0].content.parts`, Claude `delta.text`); thoughts stay out of the text. Before 2026-10-26 the route read only the OpenAI shape and returned "Empty response from API" for Google and Claude. Model comes from `getChatCompletionModel(oai_settings)`, temperature from `oai_settings.temp_openai`, `max_tokens` from `oai_settings.openai_max_tokens` (the current API's response-length setting, 4096 only as last-resort default).

  Both routes report streaming progress by calling `onChunk(charsReceived)` per chunk. On the profile route `chunk.text` is cumulative and content-only (reasoning deltas live in `chunk.state.reasoning` and never reach `text`), so the count is `text.length`; the fallback route appends each event's delta and counts the assembled `fullText` after every event. Phase 2 can run two minutes, and without this the wizard has nothing to show.
  - **Templates** — `loadTemplate(name)` fetches a `.txt` file from `prompts/`; `fillTemplate(template, vars)` does `{{KEY}}` substitution
  - **Tier block** — `buildTierBlock(tier)` renders the `== TIER: … ==` block for `generate-arc.txt` from `TIER_TABLE`: beat count, "scene beat" vs "milestone" wording, length band; for act/saga also that milestones have no `unlockAfter`, that a fulfillment names the on-screen moment at which the story shows it has reached a *state*, any scene may show it, and it is never a specific scene, a tally of many scenes or a chain of separate events (2026-11-04), and that `revealPhase` means a stretch of the whole arc. One template with three blocks, because separate templates would drift (77dbf33). The block also asks the model to echo `"tier"` into the JSON — a fallback only, since the generator passes the tier to validation directly.
  - **Arc so far** — `buildArcSoFar(arc)` renders the `== ARC SO FAR ==` block for re-planning: the current premise with the instruction to write a premise for the arc as it stands now, keeping what is still true (ADR-0003 amendment; the old "Keep the premise as given" is gone), established secrets (add-only instruction), escalation, and every fulfilled beat's fulfillment text under "already happened". Returns `''` for `null`, so the plan-new prompt stays byte-identical (e3b81d8).
- `validation.js` — `parseLlmJson()` strips markdown fences and extracts the first JSON object; `validateArcPlan(raw, { tier })` checks required fields (non-blank `title` and `premise`, non-empty `beats`), then that every beat is an object with a non-blank `intention` and that beat ids are unique after missing ones are filled in positionally — the content rules the Arc Manager's `applyArcEdit` applies too (its JSDoc lists where the two differ on purpose); it normalizes optional fields via helper functions, returns `{ valid, arc, errors }`. The tier decides the beat shape (77dbf33): `normalizeTier` defaults unknown or missing values to `episode`; for a milestone tier (`TIER_TABLE[tier].beatKind === 'milestone'`) every beat is stored `active` with `unlockAfter: []`, for episodes the first beat is `active`, the rest `pending`, `unlockAfter` kept; `estimatedLength` is clamped into `TIER_TABLE[tier].lengthBand` (a model asking for 40 on an episode gets 20). Stored arcs are never re-validated, so the clamp touches new arcs only. One more rule for milestone tiers (7ed5b1e): every milestone must carry a non-empty `pressure`, or validation fails with `Milestone "<id>" has no pressure` per beat — see "Milestones" below. `normalizeTrigger` keeps the trigger's optional `secret` link (the id of the secret it touches, `''` for none; 2026-10-30). `normalizeSecretHolders` gives every secret a `holders` list of trimmed, non-blank name strings; a missing or malformed list becomes `[]`, and non-strings are dropped.
- `storage.js` — CRUD on `chat_metadata.story_arc.arcs[]`: `getArcs()`, `getActiveArcs()`, `getArcById()`, `saveArc()`, `updateArc()`, `replaceArc(storedArc, arc)` (the Arc Manager's JSON editor: replace in place, so a field deleted in the editor is gone), `deleteArc()`; each write calls `saveMetadata()`. `latestGenre(arcs)` returns the genre of the last arc in storage order that has one — the wizard's default for a new arc
- `replan.js` — `mergeReplan(existing, generated)` implements the spec §3 merge table; see "Re-plan" below (e3b81d8, b864ac1). Kept secrets keep their `holders`; a generated secret that restates a kept one is dropped with its holders, so the kept holders win. A kept completed beat keeps its completion record without `unlocked` and `arcCompleted` (`withoutRoadInRecord`). `applyReplan(merged, chatLength)` turns the checked merged arc into the arc the wizard's "Apply re-plan" stores: a deep copy that carries the chat length at apply as `replannedAt`, where the stall count restarts (#41).
- `beat-completion.js` — beat completion by recognition, and its rollback (2026-11-04, ADR-0008); see "Beat Completion" below. `completeBeats(completions, arcs)` holds the rules both recognition paths share: `processSignalResults` (the in-prompt marker) and the knowledge extraction (`ledger.js`) both call it. `reopenCompletionsFrom(firstGoneIndex)` reopens every recorded completion whose message is gone (delete, swipe, branch load; called from `index.js`), `reopenCompletionsAt(messageIndex)` those at one edited message (called from `updateKnowledgeAfterEdit`). `removeRulingsFrom(firstGoneIndex)` and `removeRulingsAt(messageIndex)` do the same for the arcs' rulings (delete and branch load from `index.js`, edit from `updateKnowledgeAfterEdit`; #45). Private: `completionRecord`, `reopenCompletion`, `restoreLastFulfilledAt`.
- `arc-edit.js` — the Arc Manager's hand edits (see `arc-manager.js` under `lib/ui/`). `completeBeat(beats, beatId)` completes one beat and unlocks the beats that waited for it; `completeBeats` uses it for a recognised completion too. It drops any `completion` record from the beat it completes, so a completion by hand is never reopened by a rollback.
- `arc-preset.js` — the "Create arc preset" button behind the settings panel, plus the standing directives it stores.
  - `createArcPreset(baseProfileId, confirmOverwrite)` creates a barebones chat-completion preset named `Story Arc Generation` — not derived from any base preset — and clones the currently selected generation profile into a profile of the same name that pins it. Connection details (API, model, secret) come from the profile at request time, so the preset carries only generation parameters: the wire-verified combination (`reasoning_effort: 'high'`, `openai_max_tokens: 20000`, `temperature: 0.8`, `top_p: 0.95`, `stream_openai: true`) plus neutral pins for every other sampler/behavior key (`ARC_PRESET_SETTINGS`), because `presetToGeneratePayload` starts from a clone of the *live* chat settings and only overlays keys the preset defines — a dropped key silently falls back to the roleplay session.
  - **Standing directives** — adult content and genre live as ordinary prompt entries (`storyArcAdultContent`, `storyArcGenre`) inside the arc preset (whose prompt list carries *only* these entries — safe because ST's `PromptManager.checkForMissingPrompts` re-adds its mandatory system prompts on load), so the user edits and toggles them in SillyTavern's own prompt manager instead of in an extension panel. Nothing in ST reads them: Story Arc's calls never use a preset's prompt list, so the list is free storage. `readActiveArcDirectives()` resolves the preset pinned by the active generation profile, `collectArcDirectives(preset)` returns the enabled entries' text, and `generator.js` renders them into Phase 2 as a `== STANDING CONSTRAINTS ==` section via `{{ARC_DIRECTIVES}}`. Nothing enabled means no section at all. They are read from the *stored* preset, so a toggle counts only once the user saves the preset — ST's prompt manager writes toggles to the live settings, not to the preset file. Re-creating carries edited text and toggle states over from the preset it replaces, so a hand-written genre survives.

### lib/injection/

Builds and delivers prompt injections; tracks progress via AI-emitted signals.

- `builder.js` — `buildInjection(arcs)` is a dispatcher: `buildArcSection(arc)` picks one private section builder by focus and tier (`paused` → `buildPausedSection`; `background` → `buildBackgroundSection`; `spotlight` → `buildSpotlightSection`; episode/normal → `buildEpisodeSection`; act or saga/normal → `buildMilestoneSection`), orders sections spotlight first, then normal episodes, then the rest (storage order within each group), and trims an over-budget body by **whole list items** (`trimToBudget`): only the items under `SECRETS`, `TRIGGERS` and `FORESHADOWING TO PLANT` are dropped, from the last one in the body backwards, so the spotlit arc's items (ordered first) go last and no guardrail line (pacing rules, DO NOT, directives) of any section is ever cut — never a mid-sentence cut either. A header goes with its last item. If the body is still over budget once every list item is gone, it is sent over budget and the warning says so. Until 2026-10-26 the trim popped lines off the tail of the whole body, which with a spotlit act or saga plus a normal episode dropped the episode's guardrails before any of the act's list items; the naive tail-slice before that fired on every generation of a big arc and deleted exactly the guardrail sections while keeping the content blobs (found live 2026-08-29); `buildSignalInjection(arcs)` builds the in-chat injection as a *separate* injection (empty only when there are no arcs) — the signal directive (`buildSignalDirective`) was moved out of the plan text because the tail-slice budget trim used to cut it off first on any realistic plan (27c3d17), and it now also carries the `ARC PACING:` phase brake (see below), one line for the pacing clock only (issue #5): the brake's "arc message N" is the number the stamps carry, and the stamps count one episode, so a line for any other episode would point at a counter the model never sees.
  - **Section builders (2026-09-16; separate files under `sections/` until they were folded into `builder.js` on 2026-10-26).** The secrets, triggers and foreshadowing blocks are rendered once, by `pushPlanLists(lines, arc, phase)`, which the spotlit milestone section calls (2026-10-26). While the knowledge tracker is on, each `SECRETS` line ends with `holderSuffix(secret)`: ` (known only to: Julian, Brody)` for a secret with holders, nothing for one without (every arc planned before holders). With the tracker off the line is exactly as before, which `tests/test-knowledge-secrets.js` pins against a literal section. The `TRIGGERS` header adds that a trigger changes how characters act and never discloses a SECRET (2026-10-30): a generated trigger action in the Paragon chat restated a guarded secret, and the model narrated it as a confession the moment the condition was near. The header does not protect plans generated before the rule: with the old action re-armed, the next message that pressed the character leaked the secret again (#2023, 2026-10-30), because a general rule loses to the specific action next to it. The fix is in the plan text: `generate-arc.txt` forbids trigger actions that state a secret or a payoff ("creating an opening to …"), and pressures that state a secret, each with a FINAL CHECKLIST line. Plans already stored keep their text until re-planned (ADR-0003 rewrites unfired triggers) or edited in the Arc Manager. A post-generation word-overlap check was tried on the Paragon plans and rejected: a harmless pressure ("Fletchette is still holding the … SD card of Dice's bare chest", 4 shared words with its secret) scored like the two leaks (5 each), and 150 of the chat's item–secret pairs shared 4 or more words. The `PLANT CHECK` line still quotes each unfired trigger's action verbatim. Both places now leave out a trigger tied to a secret until that secret is shown (`isTriggerShown`: no link or an unknown id → shown; linked secret disclosed → shown; else `shouldShowSecret(revealPhase, phase)`; 2026-10-30): a re-planned act carried a climax-secret trigger into the prompt at escalation while the secret itself was held back. The plant check computes the phase with `calculatePhase`, the same phase that gates secrets in the plan, so its line set changes only when the plan text does and no extra cache miss appears. The plan check (Phase 3, ADR-0006) fills the link for plans whose generator left it empty. A link means the trigger belongs to the moment its secret comes out, not merely that a secret explains it (2026-10-31): with the broader "concerns a secret" wording, 3 of 4 triggers of a fresh act were tied to its climax secret and would have stayed hidden all act, although their actions were harmless reactions. `buildEpisodeSection` is the pre-tier full section, byte-for-byte including its header word (see the migration note under `lib/core/`), kept so existing chats' prompts do not change. `buildBackgroundSection` (2026-10-25) is the title under `=== BACKGROUND:` plus one sentence: "Runs off-screen. Leave it out of scenes — no hints, sounds or clues — unless the user's character goes to it or brings it up." No premise (a premise is a paragraph of the thread's pitch), no genre, no pressures, no lists; the arc's milestones stay recognisable (in the beat check with the tracker off, in the extraction's developments with it on), and `showsPlanLists` already returns false for it, so it gets no plant-check lines. `buildPausedSection` (issue #3) is one line under `=== PAUSED:` — premise plus "pending, not being pursued right now"; the old "distant tension" wording is gone. `buildMilestoneSection` (act/saga, normal) renders `=== ACT: "<title>" ===` (or `SAGA`, from `TIER_TABLE.label`), a `GENRE:` line when the arc has a genre (ADR-0004; `buildEpisodeSection` prints it after its phase line), premise, every unfulfilled milestone's pressure under `STANDING PRESSURES` (its header lets a pressure colour scenes as a mood or a detail and become an event only when the user's character goes toward it or brings it up, 2026-11-01: "let them colour scenes" alone had a pressure's people barge into the moment the user was steering), and nothing else: no secrets, triggers or foreshadowing (2026-10-19). Those lists ask for a hint or a check every message, and a normal-focus saga carrying them pulled a superhero chat into its spy-thriller secrets. No `CURRENT PRESSURE`, no `PACING RULES`, no phase line, no `tone`/`directives`/`antiPatterns`: acts colour episodes, they do not carry their own guardrail block, and omitting the phase line keeps the section byte-identical between messages (77dbf33). `buildSpotlightSection` renders a spotlit episode as the plain episode section (spotlight changes nothing in the section; it only makes the arc the clock and orders it first) and a spotlit act/saga as the milestone section with the pressures block swapped for `BRING TO A HEAD:` + one trailer sentence ("Let these pressures intensify over the coming scenes, and let the world act on its own interests."), followed by the secrets under the shared `shouldShowSecret()` phase gating, triggers and foreshadowing. `buildMilestoneSection(arc, pressures, { withLists })` takes that block as an optional `{header, trailer}` and adds the lists only with `withLists: true`. No milestone is ever named as a target (ADR-0002).
- `clock.js` — `selectPacingClock(arcs)` returns the one episode whose count drives the stamps and the `ARC PACING` brake: the spotlit episode if any, else the first `normal` episode in storage order; paused episodes and all acts/sagas never qualify. `pauseArc(id)` / `resumeArc(id, focus)` / `spotlightArc(id)` are the arc manager's focus writers. `spotlightArc` keeps one arc in the spotlight: it resumes every other active spotlit arc into `normal`, then resumes the arc into `spotlight` (2026-10-25). Pause records `pausedAt = chat.length` (an already paused arc keeps its original freeze point). Resume adds `chat.length - pausedAt` to `messageStart`, to `lastFulfilledAt` (left absent on migrated arcs that never had it) and to `replannedAt` (left absent on arcs never re-planned) and clears `pausedAt`, so the stamp number and the phase continue where they stopped; on an arc with `pausedAt == null` (never paused, or already resumed) it only writes `focus` — the arc manager routes normal ↔ spotlight changes through it too.
  - **No injected text may change per message — anywhere, including the tail.** `story_arc_plan` goes in at `IN_PROMPT`, ahead of the chat history and therefore inside the prefix an LLM provider caches. The plan text used to carry `Messages into arc: N` and `Do not advance … for at least N more messages`, both derived from `chat.length`, so every generation was a full cache write and zero cache read (found live 2026-08-30: `cache_read_input_tokens: 0`, 111,738 tokens rewritten per turn). Moving those counters past ST's Claude breakpoint (`cachingAtDepthForClaude` in `src/prompt-converters.js`) into the `IN_CHAT` depth-0 block did **not** fix it: measured again post-`85f469b` inside the 1h TTL, a chat with Story Arc active still read `cache_read_input_tokens: 0` while an identical chat without it cached normally. With this provider (nanogpt → `claude-opus-4-5-20251101:thinking`), Anthropic's documented 20-block lookback does not rescue a changing tail; every byte that occupied a position last turn must be identical this turn. So `buildPacingBlock()` no longer counts at all — it states the phase brake as a fixed arc-relative boundary (`phaseBoundaryMessage()`), which moves only when the phase does. The current count reaches the model through per-message stamps instead (see `stamping.js` below). The pacing block, the continuation guard and the confidentiality clause are emitted regardless of `autoTrack`; only the BEAT CHECK and the PLANT CHECK are gated on it, and the BEAT CHECK on the knowledge tracker being off as well. The in-chat block is appended to the existing injection rather than added as a second one because the Claude converter counts system messages toward the depth, so each extra low-depth message pushes the breakpoint one real message further back.
- `stamping.js` — **how the exact counter survives the cache.** The model still needs "how far into this arc are we" on every generation, and one counter line anywhere is exactly the shape that breaks the prefix. The fix is to give every message its own counter: `buildStamp(arc, chatIndex)` returns `[Arc: message N of ~M]` where `N = chatIndex - arc.messageStart + 1` and `M = arc.estimatedLength` — a pure function of the index and fixed arc metadata, so message 67 reads "message 67 of ~80" this turn and every later turn. Old positions keep their bytes, only the appended tail is new, and the newest message carries the current number. `stampPromptMessages()` prepends the stamps on `CHAT_COMPLETION_PROMPT_READY`, mutating ST's outgoing messages array in place; stored chat (`chat[i].mes`) and the rendered UI are never touched. Details that matter:
  - **Only user messages are stamped** — half the tokens for the same pacing signal, and stamping the model's own past replies invites it to imitate the format and write `[Arc: message …]` into its prose. The cost is that the newest stamp lags on generations that follow an assistant message (Continue, or generating without typing): the model then reads the last *user* message's number, which can be a few behind. Accepted deliberately; the phase brake, not the exact count, is what enforces pacing.
  - **`focus` changes count as a lifecycle change.** The stamp comes from the pacing clock (`clock.js`), and `focus` defaults to `normal` for every new arc, so pausing or spotlighting an arc in the Arc Manager can hand every historical position a different arc's numbering. Same one-time cache miss as activating or deleting an arc, but a user hits this one far more often.
  - **Prompt entries are matched to chat indices by content suffix, not by position.** ST filters `is_system` messages out of `coreChat` (`public/script.js:4496`), `doChatInject` splices entries in, and other extensions add their own, so positions do not line up. An entry that matches nothing is skipped *without* consuming a chat index, so a foreign entry cannot shift every later number. If a regex script rewrote message text for the prompt, nothing matches and nothing is stamped — a no-op, never a wrong count.
  - **Arc lifecycle changes cost one cache miss.** Activating, completing or deleting an arc, or re-estimating its length, changes historical stamps. That is a few times per arc, and accepted.
  - **Other extensions' `generateRaw` calls fire the same event** (`public/script.js:4037`). The pass runs only on prompts containing `INJECTION_HEADER`, which only the real chat prompt carries.
  - **The plan section shows one beat and no ids.** The episode section carries a `CURRENT PRESSURE:` block holding the active beat's `pressure` text (falling back to `intention` for arcs planned before the field existed). Pending and locked beats are omitted entirely — no ids, no intentions, no teaser. Beat ids appear nowhere in the plan text at all. The old `CURRENT BEATS` list with `(NOW)`/`(upcoming)` markers turned the plan into a visible task list: live testing burned 7 of 10 non-optional beats in ~8 exchanges on an arc planned for 40 messages.
  - **Linger.** When an arc has no active beat (the gap between a completion and the next user message), the pressure block is replaced by a directive to develop consequences and introduce no new major developments.
  - `buildSignalDirective` always emits the continuation guard (never restart the scene, even when the last message is not the user's — RP presets like Celia wrap "the latest turn" at fixed depths, which mislabels the anchor when the user generates without input) and the confidentiality clause declaring the plan invisible scaffolding whose internals must not appear in any journal/summary/state-tracking block the preset requests. Both must survive linger, so neither is gated on having an active beat, and neither depends on `autoTrack` (until 2026-11-04 `autoTrack` off dropped the whole directive, guard and clause included). `autoTrack` switches automatic recognition only, and the knowledge tracker decides where beats are recognised (ADR-0008):

    | `autoTrack` | Knowledge tracker | In the signal directive | Beats recognised by |
    |---|---|---|---|
    | off | either | guard + clause | not recognised; only the Arc Manager's hand toggle completes them (the extraction lists no developments) |
    | on | off | guard + clause, BEAT CHECK, PLANT CHECK | the narrator's `COMPLETE` marker (`processSignalResults`) |
    | on | on | guard + clause, PLANT CHECK | the knowledge extraction (`fulfilled`, see "Beat Completion") |

    Both are settings, not per-message values, so the block stays byte-identical from message to message within a phase. With the tracker on the narrator never sees a fulfillment: the BEAT CHECK printed every active beat's `intention` into the prompt, and the narrator read it as a goal despite "do not steer the scene toward them" (Paragon chat, 2026-11-04: the model quoted a milestone's fulfillment as one of the "standing pressures" it was pursuing, and 7 of the prompt's 10 beat-check lines came from arcs in background focus). The BEAT CHECK block and its marker lines are gated: they appear only while a beat is active, and each line is phrased as recognition of the past (`If the story has already brought this about — "<intention>" — output exactly: …`) with an explicit "these are not instructions, do not steer toward them". Earlier phrasings were read as objectives; a bare `:COMPLETE` token was read as status and forced the active beat into every reply
- `pacing.js` — `calculatePhase(arc)` computes beat-completion ratio and message-count ratio against `estimatedLength`, takes the minimum to get a conservative phase; `getPacingDirective(phase)` returns the directive string; `selectNonOptionalBeats(beats)` is the beat filter that phase, progress card and arc completion count; `shouldShowSecret(revealPhase, phase)` is the secret gate shared by the episode section and the spotlit milestone section (moved here from the episode section in 77dbf33 so both gate identically); `phaseBoundaryMessage(arc, phase)` returns the arc-relative message number where the phase ends — it does not read `chat.length`, which is what makes it safe to put in the prompt; `messagesUntilNextPhase(arc, phase)` turns the same boundary into a countdown for the progress card's "~N msgs to next phase" line, and is UI-only now. Both return `0` — not `NaN` — when the boundary cannot be computed, which is the case for arcs planned before `estimatedLength` and `messageStart` existed (e1bc69a)
- **Clue and trigger marks (2026-10-19).** Before this, nothing ever set `planted`, `fired` or `disclosed`: a 980-message chat showed 0 of each across 6 arcs, so every clue was sent as "TO PLANT" in every message and the model kept planting it. `buildSignalDirective` now adds a `PLANT CHECK:` block with one recognition line per unplanted clue (`:PLANTED`) and unfired trigger (`:FIRED`, quoting the trigger's action) of every arc whose section shows them (`showsPlanLists`: episodes not paused, acts and sagas in spotlight — the dispatch in `builder.js`). Secrets get no line, because it would have to state the secret right before the reply; they are marked by hand in the Arc Manager. Marks are **queued** in `chat_metadata.story_arc.pendingMarks`, not applied: a marked item leaves the plan and the plant check, and any changed byte is a full cache miss (rule above). `flushPendingMarks(messageIndex, promptChangesAnyway)` runs on every received message and applies the queue when a beat completed in that message (the prompt changes anyway) or when the oldest mark has waited `MARK_FLUSH_WINDOW` = 20 messages. With the knowledge tracker on no beat completes inside the reply, so `onMessageReceived` passes `false` and only the window applies there; the extraction's apply calls `flushPendingMarks(messageIndex, true)` itself after it completed a beat (`completeFulfilledBeats` in `ledger.js`), so ADR-0005's rule holds on both paths. Until then the item stays visible and a repeated marker for it is ignored (the queue is deduplicated). A queued mark dies with its reply (2026-10-31): `index.js` listens to `MESSAGE_DELETED` (ST passes the new chat length; regenerating the last reply deletes it first) and `MESSAGE_SWIPED` (the swiped message's index), and `dropPendingMarksFrom(firstGoneIndex)` drops every mark with `at >= firstGoneIndex`, then saves. A new swipe queues its own marks through `MESSAGE_RECEIVED`. Deleting a message in the middle shifts later indices and leaves their marks queued, as before. Before this a mark from a swiped-away reply closed its trigger later anyway (Paragon chat). Any number of items may be marked per message; the one-beat-per-arc rule applies to beats only.
- `signals.js` — `parseSignals(text)` finds all `[ARC_SIGNAL:arcId:itemId:COMPLETE|PLANTED|FIRED]` tokens (the verb is returned as `verb`) anywhere in the message, bare or HTML-comment-wrapped (the directive asks for the comment form — ST's renderer hides it completely, even mid-stream; verified against `messageFormatting`: a custom tag leaves an empty `<p>`, an open/close tag leaks its inner text, a comment leaves nothing); `processSignalResults(signals, activeArcs, messageIndex)` queues the PLANTED and FIRED marks and hands every `COMPLETE` marker to `completeBeats` (`planning/beat-completion.js`) as `{ arcId, beatId, at: messageIndex }`, `at` being the index `MESSAGE_RECEIVED` delivered, not `chat.length - 1` (see Gotchas; 23649df, 9c3e980). Until 2026-11-04 the completion rules lived here; they moved so the knowledge extraction applies the same ones (see "Beat Completion"). It deliberately does **not** promote the next beat; `promoteNextBeats(arcs)` does that on `USER_MESSAGE_RENDERED`: for an episode it activates the first pending beat when none is active; for an act or saga it activates *every* pending milestone at once — validation already stores milestones `active`, so this only repairs an arc that arrived with pending ones (a re-plan merge, an old build) (77dbf33). Recording stays liberal in one direction on purpose: a completion signal is never refused for being too fast, because the signal arrives *after* the scene was written and refusing it would make the tracker disagree with the visible story. The brake is what the model can see, not what the bookkeeping accepts; `stripSignalsFromMessage()` removes tokens from both `chat[]` and the rendered DOM and trims the blank lines the marker leaves at message start; `scrubArcInternals(messageIndex, arcs)` mechanically removes leaked beat/arc ids from the saved message after marker parsing — the confidentiality clause steers the model, only the scrub guarantees it (RP presets with state-tracking blocks, e.g. Celia's `[Main-line]`, otherwise persist beat ids and next-beat agendas into history, where they steer later generations). Called with *all* arcs, not just active — past arcs' ids linger in journal recaps. Only underscore-containing ids are scrubbed; a plain-word id is indistinguishable from prose and harmless. The id list comes from the exported `arcInternalIds(arcs)` — arc ids plus beat, secret, clue and trigger ids; secret ids since 2026-10-30, after a narrator's OOC analysis printed one beside the secret's content — and the harvester uses the same list to keep such messages out of the planner's input

### lib/knowledge/

The knowledge tracker's whole process (ADR-0007), one file under the house rule "one process, one file", plus the message ids it shares with the beat completions and the taken-names derivation it shares with the reused-name flag and the planner. See "Knowledge Tracker" below for the ledger, the block and the events.

- `ledger.js` — six sections, in the order the process runs, each helper right after its first caller (AGENTS.md "One Process, One File"). Every ledger operation changes the stored ledger **in place** and returns whether it changed; callers save only then. The three update functions (`updateKnowledgeAfterReply`, `updateKnowledgeAfterSwipe`, `updateKnowledgeAfterEdit`) return a `KnowledgeUpdateResult`, `{ ledgerChanged, beatsChanged }` (`NOTHING_CHANGED` when they did nothing): `index.js` refreshes the status line on the first and the progress display on the second. `beatsChanged` is also true when the update stored a ruling, so the card shows it even when no beat changed.
  1. **Update after a reply** — `updateKnowledgeAfterReply(replyIndex)`, see "Knowledge Tracker"; then `completeFulfilledBeats(fulfilled, messageIndex)`, which runs after the apply, so the covered messages carry their message ids when `completeBeats` records the completions, and flushes the queued marks (`flushPendingMarks(messageIndex, true)`) when a beat completed; then `storeRulings(rulings)` (see "Rulings" in "Knowledge Tracker"), also after the apply and before the save; then the helpers `repliesSince` and `latestExchangeStart`.
  2. **Extraction** — `extractKnowledge(ledger, chatMessages, fromIndex, personaName)` loads `prompts/extract-knowledge.txt`, fills it from `buildKnowledgeExtractionVariables(...)` (`{{PERSONA}}`, `{{CHARACTERS}}` with aliases, `{{FACTS}}` by id with holders or "public", `{{SECRETS}}` by ref with planned holders, `{{MESSAGES}}` from `fromIndex` on, each with its index; hidden `is_system` messages left out), sends it through the generator's `callLlm`, and returns the parsed answer or `null` on a failed call or an unreadable answer. `listShownSecrets(arcs)` lists the active arcs' secrets the current phase shows (`shouldShowSecret`, the SECRETS block's gate), disclosed ones included, each under a `ref` unique in the call (`id`, then `id_2`, … because secret ids are unique only within an arc). `parseKnowledgeExtractionAnswer(text)` takes the answer whole or not at all: unreadable JSON, a missing key or one wrongly typed item gives `null`; a missing `revealedSecrets` or `retracted` reads as `[]`, each retracted item needs a `factId` and an integer `at`, and each revealed item needs its `secretId`, its heard `text`, `heardBy` and an integer `at`. `resolveRevealedSecrets` turns each revealed ref back into its arc, secret id and planned holders, keeps the answer's heard `text` and `at`, and drops refs the input did not list. The secret's own `content` goes into the extraction's input only, never into the resolved item. Beats (2026-11-04, ADR-0008): with the chat's `autoTrack` on, `listRecognisableBeats(arcs)` lists, per active arc that is not paused and has an active beat, its active beats under the id `<first 8 characters of the arc id>:<beat id>` (the marker's arc id) and its completed beats' fulfillments under `done`, without ids; with `autoTrack` off the list is empty. `buildKnowledgeExtractionVariables` renders it as `{{DEVELOPMENTS}}`, one `Arc "<title>":` block per arc. `parseKnowledgeExtractionAnswer` reads the answer's `fulfilled: [{ developmentId, at }]` as the one exception to all or nothing: a missing list or one of the wrong type reads as `[]`, and an unreadable item is dropped, so a broken beat report never costs the knowledge update. `resolveFulfilledDevelopments(fulfilled, developments, fromIndex, lastReadIndex)` turns each item into `{ arcId, beatId, at }` for `completeBeats`, and drops an id the input did not list as an active beat and an `at` outside the messages the call read; `lastReadIndex` is taken before the call, so a message sent during it is never a fulfilling one. Rulings (2026-11-04, #40; ADR-0008 amendment): `listArcPlans(arcs)` lists every active arc that is not paused, whether or not it has an active beat and whatever `autoTrack` says, with its short arc id, title, premise and the `pressure` of every beat not completed (a beat without a pressure adds none); `buildKnowledgeExtractionVariables` renders it as `{{PLANS}}`. The answer's `rulings: [{ arcs, quote, at }]` is read as tolerantly as `fulfilled`. `resolveRulings(rulings, arcPlans, chatMessages, fromIndex, lastReadIndex)` drops, with a warning, an `at` outside the read messages, a message there that is hidden or not the player's, a quote not in that message (`findQuoteInText`: ignoring case, whitespace collapsed; it returns the span as it stands in the message, so the stored text is the player's own) and a ruling with no listed arc id left; it returns `{ arcIds, text, at }` with full arc ids.
  3. **Apply an extraction answer** — `applyExtractionAnswer(ledger, answer, fromIndex, messageIndex)` covers the messages `fromIndex…messageIndex`. New characters first (ids `c<n>`), then the learned items: a known fact id adds holders; a text joins the fact with the same text (`findFactWithSameText`: equal ignoring case, runs of whitespace and a trailing full stop; facts in the ledger and those created earlier in the same answer) and creates a fact (`f<n>`) only for new text; names match case-insensitively against names and aliases, and unknown names and fact ids are ignored. The teller (`toldBy`) of a `told` item becomes a `witnessed` holder of the fact at the same `at`, unless they hold it already: the prompt leaves out characters who already know, and without this a talked-about teller printed "Does not know" next to "Has told only Ellie". An item's `at` outside `fromIndex…messageIndex` falls back to `messageIndex` (`atInsideCoveredMessages`), so a regeneration, a delete or the next edit of that message always takes it back. A revealed secret creates or extends the fact linked to it (`fact.secret = { arcId, secretId }`), worded with the heard `text` (a later reveal adds holders and keeps the first wording), with the characters who heard it as `witnessed` holders and its planned holders as `plan` holders, all at the reveal's own `at`. Then the retracted ids: a known fact without a user-entered holder moves to `retractedFacts` with the correction's `at` (see "Knowledge Tracker"). `present` replaces the scene; the scene it replaces goes into `sceneHistory` (`keepSceneInHistory`: only a scene from an earlier message, never the empty one before the first update; the newest `KNOWLEDGE_SCENE_HISTORY_CAP` = 10 are kept), and `lastUpdatedAt` becomes `messageIndex`. Helpers: `findCharacterId`, `nextLedgerId(prefix, entries)` (one above the highest number in use; exported for the popup), `findCharacterIds` (names to unique ids), `findFactWithSameText` with `normalisedFactText`, `addHolderUnlessHeld`. Given the chat as a fifth argument (both update paths pass it), `assignCoveredMessageIds` gives the covered messages a message id, and every holder entry at a covered index (in retracted facts too), a retraction, the scene and `lastUpdatedAt` get that id as `messageId` / `lastUpdatedMessageId`.
  4. **Roll back after a delete, a swipe, an edit or a branch load** — `rollBackKnowledgeFrom(firstGoneIndex)` first calls `followMessagesById(ledger, chat)` (entries with a message id, retractions and retracted facts' holders included, move to their message's new index or go with it; a retraction whose correcting message is gone gives its fact back; `messageIdOf`, `latestMessageWithId`), then `dropKnowledgeFrom(ledger, firstGoneIndex)`, the index rule for entries without one: holder entries with `at >= N` go, a fact left without holders goes, `at: null` entries stay; a scene from a dropped message goes back to the latest scene in `sceneHistory` before message N, and becomes `{ at: null, present: [] }` only when there is none (a ledger stored before the history has none); history entries at N or later go; and `lastUpdatedAt` goes back to `N - 1` (`null` for N = 0). It only rolls back data. The prompts are rebuilt by `onMessageDeleted` in `index.js`, which calls `injectStoryArcPrompts()` (plan, signal and knowledge injections) after its drops and rollbacks: a regenerate fires GENERATION_STARTED, where the prompts are first built, while the old reply is still in the chat, and deletes it only afterwards. ## Phase System

Five phases, each with a 0–1 percentage range applied to both beat-completion ratio and message-count ratio. The current phase is whichever of the two ratios is lower (conservative — do not rush ahead).

| Phase | Range | Pacing Directive |
|-------|-------|-----------------|
| Setup | 0–20% | Plant seeds. Build atmosphere. No revelations. No confrontations. |
| Development | 20–50% | Tensions grow. Complications deepen. Hints become patterns. |
| Escalation | 50–75% | Stakes rise sharply. Confrontations can begin. Secrets start surfacing. |
| Climax | 75–90% | Major beats resolve. Secrets revealed. Decisive moments. |
| Resolution | 90–100% | Aftermath. Emotional processing. Seeds for the next arc. |

## Signal Protocol

When `autoTrack` is enabled, a dedicated injection (`story_arc_signals`, IN_CHAT depth 0 — the last message the model sees before generating) instructs the AI to emit markers: `PLANTED` and `FIRED` for clues and triggers (the PLANT CHECK), and, only while the knowledge tracker is off, `COMPLETE` for beats (the BEAT CHECK):

```
<!-- [ARC_SIGNAL:<arcId-prefix>:<beatId>:COMPLETE] -->
```

With the tracker on, beats are recognised by the knowledge extraction instead, and the narrator never sees a fulfillment (ADR-0008; see "Beat Completion"). The marker parsing below runs on every reply whatever the switches, so a `COMPLETE` marker the narrator writes without being asked is still applied to an active beat.

The HTML-comment wrapper makes the marker invisible in ST's renderer even while it streams in; the bare form (without the wrapper) is still parsed for messages written before the change. Only the first 8 characters of the arc UUID are used in the signal to keep it compact. The model is told to put the marker on the **first** line of its reply, not the last — end-of-message markers get eaten whenever the response hits the token cap. On `MESSAGE_RECEIVED`, `parseSignals()` scans the whole message, `processSignalResults()` resolves the full arc by prefix match (for a `COMPLETE` marker through `completeBeats`), `stripSignalsFromMessage()` removes the tokens (and their leftover blank lines) before the user sees them, and `scrubArcInternals()` deletes any beat/arc ids the model leaked elsewhere in the message — journals and state-tracking blocks from RP presets otherwise carry plan internals (spoilers, next-beat agendas) into saved history.

Directive placement is the load-bearing detail (27c3d17): with the directive in the system prompt (or even one message back from the end), GLM 5.2 reasoned about beats in its chain-of-thought and still never emitted a marker. Depth 0 produced compliance. Emission remains stochastic per message — acceptable over a 40-message arc, since beats only need to complete eventually.

## Beat Completion

A beat completes when the story is recognised to have fulfilled it (2026-11-04, ADR-0008). There are two recognition paths, chosen by the knowledge tracker's switch (`autoTrack` off turns both off; see the table under `buildSignalDirective`):

| | Tracker off | Tracker on |
|---|---|---|
| Who recognises | the narrator, in the reply it writes | the knowledge extraction, after the reply |
| What it sees | the BEAT CHECK: each active beat's `intention` in the narration prompt | `{{DEVELOPMENTS}}` in `extract-knowledge.txt`: each active beat's `intention` by id `<arc8>:<beatId>`, the arc's completed beats under `done` |
| What it reports | `<!-- [ARC_SIGNAL:<arc8>:<beatId>:COMPLETE] -->` on the reply's first line | `fulfilled: [{ developmentId, at }]` (task 6, FULFILLED: only what happens on screen, OOC lines fulfil nothing, when in doubt leave it out) |
| Caller | `processSignalResults` (`signals.js`), `at` = the reply's index | `completeFulfilledBeats` (`ledger.js`), `at` = the message the answer names, inside the messages the call read |
| When | in `onMessageReceived`, before the next generation | a few seconds after the reply, or up to `updateInterval` replies later; also after a swipe switch or an edit (the single-message re-extraction) |

Both paths call `completeBeats(completions, arcs)` in `lib/planning/beat-completion.js`, so the rules are the same:

- the arc must be found and `active`, the beat must exist and be `active`; a pending, locked or unknown beat is a hallucinated id or a stale report and is ignored (logged);
- one completion per arc per message (`at`), the first in the list wins; independent arcs may each advance in the same message;
- `lastFulfilledAt` becomes `at`, unless a later completion set it already (an edited earlier message completed again); locked beats whose prerequisites are now all completed become pending (`completeBeat` in `arc-edit.js`, the Arc Manager's toggle uses the same function); an arc with no non-optional beat left completes;
- no promotion: the next scene beat waits for the next user message (`promoteNextBeats`).

**Fulfillments are one on-screen moment.** The extraction reads only the messages since its last update, usually one user message and one reply. A fulfillment that is a tally of many scenes ("has completed her first patrols") or a chain of separate events joined by "and" never shows in such a window; the narrator did not recognise one either (`rookie_beats_and_sidekick_drills` stayed active for 439 messages in the Paragon chat with the whole chat in context). The generator asks for one moment (`generate-arc.txt`, `buildTierBlock`, `detail-pass.txt`) and the plan check rewrites tallies and chains (see `generator.js` above). Existing arcs get one-moment fulfillments when they are re-planned; there is no migration. Marking beats complete by hand is not a recognition path; the Arc Manager's toggle stays an override.

**The completion record.** A completion with an `at` stores `beat.completion = { at, messageId?, unlocked, arcCompleted, lastFulfilledBefore }` (`completionRecord`): the message by index and, when it carries one, by Story Arc message id (the id the knowledge ledger uses, `lib/knowledge/message-ids.js`), and what reopening the beat has to undo. The id is only read, never given: the ledger relies on only the messages an update read carrying one (`followMessagesById`). With the tracker on, the extraction gave the message its id before its completions are applied. With the tracker off, or for a hidden message, the record names its message by index only.

**Rollback.** Before 2026-11-04 a completed beat was never reopened: a swiped-away reply that completed a beat kept it completed. Now:

| Event | Call | What happens |
|---|---|---|
| `MESSAGE_DELETED(newChatLength)` (also the last reply before a regeneration) | `reopenCompletionsFrom(newChatLength)` in `index.js`, then `updateProgress()` and a save when it changed anything | a record with a message id follows its message: it moves to the message's new index while the message is in the chat, and is reopened when the message is gone; then every record at `newChatLength` or later is reopened |
| `MESSAGE_SWIPED(mesId)` | `reopenCompletionsFrom(mesId)`, before the knowledge rollback (which strips the swiped message's id) | the swiped message's completions are reopened. ST awaits the handler before it generates a new swipe, so the new reply's prompt shows the reopened beat and may complete it again. Switching to an existing swipe re-extracts it (tracker on); its markers were stripped when it arrived, so the in-prompt path does not complete its beats again |
| `MESSAGE_EDITED(id)` | `reopenCompletionsAt(id)` inside `updateKnowledgeAfterEdit`, tracker and `autoTrack` on only | the completions at exactly that message are reopened, matched by message id when the message and the record carry one, else by index; the re-extraction completes them again if the edited text still fulfils them |
| `CHAT_CHANGED` | `reopenCompletionsFrom(chat.length)` before the ledger rollback | ST copies the chat metadata whole when it branches; a branch that ends before a completing message reopens its beat |

Next to each call, the arcs' rulings follow their message by the same rules (#45): `removeRulingsFrom` on delete and chat change, `removeRulingsAt` in `updateKnowledgeAfterEdit` (tracker on, whatever `autoTrack` says), none on a swipe; see "Rulings" in "Knowledge Tracker".

Delete, swipe and branch load reopen completions with the tracker off too. Reopening a beat (`reopenCompletion`) undoes what its completion did: the beat is `active` again; in an episode a later beat promoted meanwhile goes back to `pending` (one scene beat is active at a time); a beat it unlocked that is still `pending` is `locked` again, so an unlocked scene beat promoted meanwhile ends up locked too; an arc it completed is `active` again. Several completions of one arc are reopened latest first. Then `restoreLastFulfilledAt` sets the arc's `lastFulfilledAt` to the latest remaining recorded completion or to the earliest reopened record's `lastFulfilledBefore`, whichever is later; that value covers what has no record (`messageStart`, a completion by hand or from before the records), and a record without it (an arc from before `lastFulfilledAt`) falls back to `messageStart`. A completion without a record is never touched. The reopen functions are synchronous and do not save; the caller saves when they return true.

**Limits.** A record without a message id has only the index rule: a deletion in the middle of the chat before the completing message leaves `at` one off, and deleting the completing message itself in the middle of the chat does not reopen the beat. With the tracker off, an edit reopens nothing (nothing would complete the beat again). An unreadable extraction answer loses both the knowledge update and the completions for that window; the next update reads the same messages again. A user message sent while the extraction runs is built with the beat still active, so its pressure stays one message longer. The extraction judges messages it did not write and does not see the plan, so it may recognise a single-event beat more strictly than the narrator did. An arc that is never re-planned keeps its old tally and chain fulfillments, which the extraction will not recognise.

## Pacing Enforcement

Prompt-side pacing ("do not advance for N more messages") was demonstrably ignored, so the brakes are mechanical and sit on what the model can *see*:

1. **Information hiding** — the plan text shows one beat, as a pressure, with no id. A model cannot race toward objectives it was never given.
2. **Pressure/fulfillment split** — the plan shows the beat as weather (`pressure`, no completion state). The fulfillment condition (`intention`) reaches the narrator only through the BEAT CHECK, phrased as recognition of the past, and only while the knowledge tracker is off; with it on, only the extraction sees it (ADR-0008). An outcome-phrased beat is a solvable, and models are trained to solve visible goals in one scene and then parrot the solution into dialogue. The recognition phrasing was not enough: the narrator still read beat-check fulfillments as goals (Paragon chat, 2026-11-04).
3. **Active-only, one per arc per message** — the backstop in `completeBeats` against one eager scene burning several beats.
4. **Promotion on the next user turn** — after a completion the arc is left with no active beat until `USER_MESSAGE_RENDERED`. The AI's own aftermath prose and empty-input continues cannot chain into the next objective; the player reacts to a development before the model learns what follows.

Promotion is reactive, not clocked. A message-budget hold was considered and rejected: scenes must react to the roleplay, not to a round counter, and a clock detaches the plan from an unforeseen story direction. The accepted consequence is that an arc "planned for 40 messages" can finish sooner if the model keeps fulfilling beats and the player plays along — `estimatedLength` feeds only the advisory phase wording, and the real pace is set by the player's turns.

## Tiers and Focus

Multiple arcs can be active simultaneously. Tier owns an arc's shape, focus owns its prominence (ADR-0001, `CONTEXT.md`). The tier is chosen in the wizard at generation and only grown by re-plan (episode → act → saga, never smaller); the focus is set by hand in the Arc Manager at any time.

### Injection matrix — what `buildArcSection(arc)` picks

`builder.js` looks at focus first, then tier (`arc.tier || 'episode'`, so an arc without a tier is an episode):

| | Episode | Act / Saga |
|---|---|---|
| `paused` | `paused.js`: one line under `=== PAUSED:` — premise + "pending, not being pursued right now". No beat check line; clock frozen | same one line; no beat check |
| `background` | not offered (ADR-0001 amendment); re-plan never shrinks an act or saga into an episode (ADR-0003 amendment) | `background.js`: `=== BACKGROUND:` title + "Runs off-screen…" sentence. No premise, pressures or lists; milestones stay recognisable (beat check or extraction); clock runs |
| `normal` | `episode.js`: full section (`CURRENT PRESSURE` of the one active beat, pacing rules, DO NOT, directives, gated secrets, triggers, foreshadowing). Pacing-clock candidate | `milestone.js`: `=== ACT:`/`SAGA:` header, premise, every unfulfilled milestone's pressure under `STANDING PRESSURES`. No secrets, triggers or foreshadowing, no brake, no clock, no phase line |
| `spotlight` | `spotlight.js` → the same full section, byte-identical; the arc **is** the pacing clock and is ordered first | `spotlight.js` → the milestone section with the pressures under `BRING TO A HEAD:` + one trailer sentence, then gated secrets, triggers, foreshadowing; ordered first so budget trimming never drops it. No milestone is named as a target (ADR-0002) |

Section order (`sectionRank`): spotlight first, then normal episodes, then everything else (normal acts and sagas, background, paused) — storage order within each group. The in-chat block is the same for every tier: `ARC PACING` names only the pacing clock; the recognition set (the BEAT CHECK with the tracker off, the extraction's `{{DEVELOPMENTS}}` with it on) is every `active` beat of every non-paused arc, which for an act or saga means every unfulfilled milestone. The phase (`calculatePhase`) feeds the brake boundary, secret gating and the progress card on an episode (the stamps do not depend on it); on an act or saga it feeds secret gating (spotlight only) and the progress card (phase label and the "~N msgs to next phase" line) only — `calculatePhase` itself is tier-blind.

### Milestones — activation and recognition

A milestone is an act's or saga's beat: unordered, all standing at once. `validateArcPlan` stores every milestone `active` with `unlockAfter: []`, so recognition can fire for any of them in any message from the first one on; `promoteNextBeats` keeps that invariant after a re-plan merge. The cap of one completion per arc per message still holds. A milestone is never shown to the model as its fulfillment (7ed5b1e, issue #13): the milestone and spotlight sections print only `pressure` and skip a milestone without one rather than substituting its intention, and `validateArcPlan` rejects an act or saga whose milestone lacks a `pressure` — one error per beat naming its id, through the same errors path the wizard already shows with Regenerate. The `pressure || intention` fallback inherited from pre-2026-08-29 episodes was removed here because it could print a past-tense fulfillment as a standing pressure, which under `BRING TO A HEAD` is exactly the named target ADR-0002 forbids. The episode fallback stays. The generator's tier block tells the model that a milestone's fulfillment names the on-screen moment at which the story shows it has reached a *state*, not a specific scene, a tally of scenes or a chain of events, so it can be recognised whatever route the story took and from the one or two messages the extraction reads (2026-11-04).

### Pause — the clock freezes and shifts

`pauseArc(id)` writes `focus: 'paused'` and `pausedAt = chat.length` (an already paused arc keeps its original freeze point, so the span it sat out is never shortened). `resumeArc(id, focus)` on a paused arc adds `chat.length - pausedAt` to `messageStart`, to `lastFulfilledAt` and to `replannedAt` (when present) and clears `pausedAt`, so the stamp number and the phase continue where they stopped: paused at chat length 100 on "message 12 of ~20", resumed at 115, the next user message still stamps "message 12" (pinned by `tests/test-clock.js`). On an arc with `pausedAt == null` it only writes `focus` — the Arc Manager routes every normal ↔ spotlight change through it too (b7bde8a). Shifting `messageStart` re-numbers every historical stamp: one prefix-cache miss, the same class as any focus change.

### Spotlight — the world moves, nothing is named

Spotlighting an episode changes nothing in its section; it makes that episode the pacing clock and orders it first. Spotlighting an act or saga moves its unfulfilled milestone pressures into the main block under `BRING TO A HEAD:` with the trailer "Let these pressures intensify over the coming scenes, and let the world act on its own interests." The obvious wording — "choose one of these and steer toward it" — is the goal instruction the 2026-08-29 pacing work found to be poison, so no milestone is ever named (ADR-0002). If live play shows spotlight is too soft, the next step is a tempo phrase ("within the next few scenes"), not a target; the trailer is a standalone sentence rather than a header parenthetical so that phrase is a one-line change (fcc104f).

## Re-plan

Re-plan regenerates the unfulfilled part of an active arc from the story's current state, keeping its identity, its secrets and its fulfilled beats (ADR-0003, spec §3). Entry points: the Arc Manager's Re-plan button (closes the manager, then `showWizard(arcId)` — nested ST popups stack badly) and the stall nudge on the progress card (`showWizard(arcId)` directly, no popup to close).

| Step | What happens | Where |
|---|---|---|
| Wizard step 2 | tier pre-set, direction pre-filled, title and premise editable; untouched values kept verbatim; the hint says a new premise is proposed for review | `wizard.js` revise mode |
| Phase 1 | existing-arcs list marks the arc `[BEING RE-PLANNED]`; the analyst is told not to report its unfulfilled beats as open threads | `generator.js` `formatExistingArcs`, `analyze-context.txt` |
| Phase 2 | `{{ARC_SO_FAR}}` block (current premise with the instruction to write a premise for the arc as it stands now, established secrets add-only, escalation, fulfilled beats as "already happened"); the arc is omitted from the existing-arcs list. The output contract's premise line says the premise is shown in plain view, so it states no secret and no planned development (new arcs too) | `generator.js` `buildArcSoFar`, `generate-arc.txt` |
| Validate | as plan-new, with the tier chosen in the dialog | `validation.js` |
| Merge | `mergeReplan(reviseArc, generated)` inside `generateArc`, so step 3 reviews the merged arc and Regenerate re-merges; the model's premise rides along as the transient `proposedPremise`, and the plan check reads it as `PREMISE` (the road was planned around it) | `replan.js`, `generator.js` `buildPlanCheckVariables` |
| Review | step 3 of a re-plan shows a Premise block in plain view, outside every spoiler: current and proposed premise, a choice (current pre-selected; reset on Regenerate) and a text area holding the chosen text. A new arc's premise stays behind its spoiler | `wizard.js` `buildPremiseChoice` |

The message reference and `lastFulfilledBefore` stay, so a rollback still reopens the beat itself and sets `lastFulfilledAt` back. ## Stall Nudge

A stall is the measurable sign of divergence: an arc going roughly three times its expected per-beat length without a fulfillment (GLOSSARY "Stall"). `isStalled(arc, chatLength)` in `progress.js`, for every tier (#41, 2026-11-04): not while paused or in background focus, `chat.length - max(messageStart, lastFulfilledAt, replannedAt) > 3 × estimatedLength / nonOptionalBeatCount`; an act's or saga's non-optional beats are its milestones. An arc without a non-optional beat or without `estimatedLength` never stalls. `lastFulfilledAt` is the chat index of the fulfilling message, so after N further messages the difference is N + 1: a 20-message episode with six non-optional beats nudges at N = 10 and not at N = 9 (pinned by `tests/test-stall.js`). A missing or `0` `lastFulfilledAt` counts from `messageStart` (`Math.max`), so a migrated episode is not nudged the moment it loads. An act of length 90 with four milestones, last fulfilled at 2225, is not stalled at chat length 2292 and stalled at 2293 (67.5 allowed). `applyReplan` stamps `replannedAt`, so a freshly re-planned arc shows no nudge; it is a field of its own because the rollback below sets `lastFulfilledAt` back before the re-plan, and the stamp cannot be moved by it. A chat shortened by deletions below the stamp counts negative: nothing lights until it grows past it again. Pausing does not count: resume shifts `lastFulfilledAt` and `replannedAt` by the paused span. A background arc's clock runs, so an arc brought back to normal focus may light at once. `completeBeats` sets it, and reopening a completion sets it back (`restoreLastFulfilledAt`), so a swiped-away fulfillment no longer resets the stall count.

When it holds, the progress card shows "May have drifted — re-plan?" as a button that opens the wizard in revise mode for that arc. Nothing is injected — the nudge is player-facing only; the model is never told the arc stalled (23649df). With automatic recognition off, acts and sagas show the nudge once their allowance runs out; that is accepted (#41).

An arc with an open ruling (no `answeredAt`) shows a ruling line instead (`renderRulingLine` in `progress.js`, 2026-11-04, #40): the newest open ruling (latest `at`) quoted, "and N earlier" when there are more, the full quote in the tooltip, clamped to two lines, and "You overruled the plan — re-plan?" as a button with the stall button's class, so the same settings-panel handler opens the re-plan wizard. When the stall line would also show, only the ruling line shows. The card shows only the player's words and the count, never plan text, and neither the plan block nor the signal directive reads `rulings`.

## Knowledge Tracker

Story Arc keeps a knowledge ledger per chat: which character knows which fact, and how they learned it (ADR-0007, spec issue #2). A short block close to the bottom of the prompt tells the narrator what everyone knows and what the characters in the scene, and the characters the scene talks about, know. It never says what a character does not know. It exists because a rule against omniscience names no fact and loses to the scene; a concrete "Gabriel has told only Ellie" leaves the narrator no reason to invent an off-screen phone call. The process lives in `lib/knowledge/ledger.js`.

**Rulings (2026-11-04, #40, ADR-0008 amendment).** The extraction also gets the plans of the active, non-paused arcs (`== PLANS OF THE STORY ARCS ==`: short arc id, title, premise, open pressures, no genre, no ids on pressures) and task 7, OVERRULED: an out-of-character line of the player that says the story must differ from a listed premise or pressure is reported with the arc ids, the exact quote and the player's message index. Scene-level requests and new direction that contradict nothing listed are not rulings. A checked ruling (`resolveRulings`) is stored by `storeRulings` on each arc it names, after the ledger apply and before the save, in the update after a reply and in the re-extractions after a swipe switch and an edit. A ruling whose text matches an open ruling of the arc is skipped, and so is one the arc holds already from the same message with the same text. The update log records `answer.rulings` (resolved) and `rulingsStored`, never the text. Only while the tracker is on; rulings do not follow `autoTrack`. A ruling follows its message like a completion record (2026-11-04, #45; `removeRulingsFrom`, `removeRulingsAt` in `beat-completion.js`): open and answered rulings go when their message is deleted (by message id when the ruling has one, and a ruling whose message is still in the chat moves to its new index; otherwise by the index rule), when a branch is loaded that ends before it, and when the message is edited, before the edit's re-extraction reads it again, so a ruling the edited text still states is stored again by the normal rules, as an open ruling (an answered one comes back open), and one the player edited out is gone. The edit removal runs only where the edit re-extracts (tracker on, message read), whatever `autoTrack` says. A swipe removes no ruling: it replaces the narrator's reply, not the player's message before it. The progress card refreshes after a removal. The bare pick after the narrator's options is not built yet (spec #30).

**Optional, off by default.** `extension_settings.story_arc.knowledgeTracker = { enabled: false, updateInterval: 1 }`. While the switch (or Story Arc itself) is off there is no extraction call, the knowledge block and the taken-names block are `''`, the SECRETS lines carry no holders, and the Knowledge buttons are not shown, so the injection is byte-for-byte what it was before the tracker, the beat check included (pinned by `tests/test-knowledge-secrets.js` and `tests/test-knowledge-inject.js`). Rollbacks still run while it is off (below), so knowledge from text that is gone does not come back when it is switched on.

**The ledger** lives at `chat_metadata.story_arc.knowledge`, next to the arcs, so branches, exports and backups carry it (a side file was rejected in ADR-0007). Shape of record: `createEmptyKnowledgeLedger()` in `constants.js`.

```javascript
knowledge: {
    characters: [{ id, name, aliases: [name] }],          // ids c1, c2, …
    facts: [{
        id, text,                                         // ids f1, f2, …
        public: boolean,                                  // known to everyone; never printed
        secret?: { arcId, secretId },                     // only on a fact an arc's secret became when revealed
        holders: [{ characterId,
                    how: 'witnessed' | 'told' | 'user' | 'plan',     // HOLDER_HOW
                    toldBy: characterId | null,           // for how 'told'
                    at: messageIndex | null,              // null = entered by the user, survives every rollback
                    messageId? }],                        // the message's Story Arc stamp (below)
    }],
    scene: { at: messageIndex | null, messageId?, present: [characterId] },   // from the last extraction
    sceneHistory: [{ at: messageIndex, messageId?, present: [characterId] }], // earlier scenes, oldest first,
                                                          // newest 10; missing in older ledgers = empty
    retractedFacts: [{ at: messageIndex, messageId?, fact }], // facts an OOC correction at `at` took back, whole;
                                                          // missing until the first retraction = empty
    lastUpdatedAt: messageIndex | null,                   // last message the ledger covers
    lastUpdatedMessageId?,                                // that message's stamp
    updateLog: [record],                                  // newest 20, oldest first; missing until the
                                                          // first record = empty (below)
}
```

The ledger stores only who knows, and the block states only who knows (issue #21). Holder entries record the message, not the swipe: a swipe takes the message's knowledge back and the shown text is extracted again. The extraction writes `witnessed`, `told` and (for a revealed secret's planned holders) `plan`; the popup writes `user` (the values are `HOLDER_HOW` in `constants.js`). A public fact is a flag on the fact, not a holder value. The teller of a `told` item is a `witnessed` holder too (whoever tells a fact knows it). So is the actor: the extraction prompt has a character who did, caused or planned what a fact describes listed among its holders (`witnessed`), even when absent. Only for the deed as they did it: a routine act they would not remember does not count, and what others found out about them is a fact they do not hold (2026-11-01: Diana became a holder of "Vera knows Diana from her signature on Lucas's file", and the block told the narrator she knew it). In the 2026-11-01 live check the player told Amy that Mara rewrote her diagnostic logs; Mara was left out, and the block printed "MARA (talked about, not present)" with "Does not know" for her own deed. The prompt also asks for fact text that states the fact itself, not who else knows it (a live fact ended "…, and nobody else knows except Ellie."). In the second live check one answer wrote "Mara from the night shift rewrote Amy's diagnostic logs." twice, as the actor's own item and as the item of those Steve told; two facts with one text printed both "Knows" and "Does not know" for Mara. Applying the answer now joins learned items with the same text into one fact, and the prompt asks for a ledger fact's id over new text when the same knowledge is meant and for each fact once. The same check got 9 facts from one reply, mostly sensations ("Amy can feel the vibration of Steve's phone in her throat like a heartbeat"); the prompt now records only knowledge a character could act on or wrongly reveal (secrets, plans, identities, who did what, private information, things told in confidence), not small talk, sensations, descriptions, moods or what anyone in the scene can plainly see. One fact holds one piece of knowledge (issue #23): the extraction once joined "Ellie Masters is sitting on over a million dollars and intends to bring Vera Lin onto Lucky Strike's payroll" into one fact; Vera later learned only the second half and could not become its holder. The prompt now puts knowledge that different characters can learn at different times into separate facts. Every `at` the extraction writes lies inside the messages its call covered.

**Extraction after a reply.** `onMessageReceived` calls `updateKnowledgeAfterReply(replyIndex)` after signal processing, so the extraction reads the reply without its markers, and does not await it: ST awaits its listeners, and the extraction must not hold up the next generation. A prompt built while it runs uses the ledger as it is. The update runs when at least `updateInterval` AI replies (hidden messages not counted) arrived since `lastUpdatedAt`, and reads every message from `lastUpdatedAt + 1` to the reply. A ledger never updated (`lastUpdatedAt: null`) reads only the latest exchange, the reply and the user message before it: a long chat's history is not backfilled. One extraction at a time (`knowledgeUpdateRunning`); a reply arriving meanwhile starts none, and the next update covers its messages. When the answer is back it is dropped if the chat changed (`chat_metadata.story_arc` is another object), the reply's text changed (a swipe) or `lastUpdatedAt` moved (a rollback); otherwise it is applied to the ledger re-read after the call, so popup edits made during the call survive. A failed call or an unreadable answer changes nothing but the update log and leaves `lastUpdatedAt`, so the next update reads the missed messages again. The call goes through the arc generation connection profile (`callLlm`, the plan check's transport), so it can run on a cheaper model than the chat.

**Beat recognition (2026-11-04, ADR-0008; ADR-0007 amendment).** With the chat's `autoTrack` on, the same call also recognises beats; no call is added. Its input gets `== DEVELOPMENTS OF THE STORY ARCS ==` (`listRecognisableBeats`: the active beats of every active arc that is not paused, by id, and each arc's completed beats under `done` as context that is never reported), and its answer a `fulfilled` list (task 6). After the answer is applied to the ledger, `completeFulfilledBeats` hands the resolved items to `completeBeats` and flushes the queued marks when a beat completed. The narration prompt then carries no BEAT CHECK. The rules, the completion record and the rollback are under "Beat Completion"; the single-message re-extraction after a swipe switch or an edit completes beats the same way. With `autoTrack` off the developments list is empty, so nothing is reported.

**Out-of-character corrections retract facts** (issue #18). The extraction can take knowledge back, not only add it. Live case, test chat 2121–2129: a character stated a yearly stipend the narrator had made up, the extraction recorded it for two characters, the player objected out of character ("There was never anything on the page regarding financial compensation…"), the narrator admitted "I invented that detail on the spot", and the fact kept reaching the narrator through the block. The prompt now says that out-of-character lines (marked OOC, in square brackets, or the narrator stepping out of the story) teach characters nothing and are corrections; when one calls a ledger fact wrong, invented or not canon, the answer lists it under `retracted: [{ factId, at }]`, `at` being the message of the correction (inside the covered messages, like every `at`). A correction that states the right version is no fact until a later in-story message shows a character learning it. `parseKnowledgeExtractionAnswer` reads a missing `retracted` as `[]`; a non-list or an item without `factId` or integer `at` rejects the answer. Applying the answer handles retractions last (the correction is the later word): the fact leaves `facts` with all its holders and goes to `retractedFacts` as `{ at, fact }`. A fact with any user-entered holder stays (a hand correction wins), and an unknown id changes nothing. The rollback is the normal drop path: `keepOnlyHolders` judges each retraction with the same predicate as the holder entries, so deleting, swiping, regenerating or editing the correcting message (and loading a branch that ends before it) puts the fact back, with only its holders from before the rollback point; a fact entered meanwhile under its id gives the returning fact a fresh id (`nextLedgerId`).

**Message ids (issue #19).** Applying an answer gives every message the call read Story Arc's own message id, `message.extra.story_arc_message_id` (a `uuidv4`; a message that carries one keeps it), and each holder entry, the scene and `lastUpdatedAt` store it as `messageId` / `lastUpdatedMessageId` next to the index. The message id is Story Arc protocol data on the message, the same exception GOALS.md makes for scrubbing plan internals; `saveMetadata` saves the whole chat, so it persists with the messages. Ids are never borrowed from other extensions. Only messages an update read carry a message id: a swipe removes it from the shown swipe and from every swipe's `swipe_info[i].extra`, and the extraction that reads the swipe gives it a new one. ST's `syncMesToSwipe` copies `extra` into the swipe it swipes away from, and a branch from a chosen swipe (`createBranch` → `getBranchChatSnapshot` → `syncSwipeToMes`) brings that swipe's `extra` back without a `MESSAGE_SWIPED`; without the cleanup, a swipe whose knowledge an earlier swipe took back would count as read in the branch and never be read again.

**Rollback** — what text that is gone taught the characters is taken back, and the scene goes back to the latest one recorded before the dropped message (`sceneHistory`). Without that history a swipe of reply 44 in the test chat emptied the scene, and the regenerated reply's block printed Ellie and Amy, both in the scene, as "(talked about, not present)". A new swipe needs nothing more: it arrives through `MESSAGE_RECEIVED` and its update reads it. An existing swipe whose message an update had read is extracted again on its own (tracker on only); otherwise the next update reads it |
| `MESSAGE_EDITED(id)` — fires once the new text is saved in the chat | `updateKnowledgeAfterEdit(id)` (not awaited) | tracker on and the message already read: drop only the entries learned at that message (`dropKnowledgeLearnedAt`) and extract that message again, so later knowledge stays. Tracker off, or a message no update has read: nothing |
| `CHAT_CHANGED` — fires after the chat's messages are printed, so `chat.length` is the loaded chat's | `rollBackKnowledgeFrom(chat.length)`, then `updateKnowledgeStatus()` | ST copies the chat metadata whole when it branches; a branch made at message 2078 would otherwise carry knowledge from 2079 on |

The single-message re-extraction (`reextractKnowledgeOfMessage`) passes the chat cut after the message, so the call reads that message only. Its answer is dropped when the chat changed, the message's text changed, or the ledger's coverage moved over the message during the call (an update that was before it now reaches past it, or one that reached past it now ends before it). When the ledger already reaches past the message, `lastUpdatedAt`, the scene and the scene history stay as they are. Deleting a message in the middle of the chat is handled by the message ids (above). Entries without a message id, learned before #19, still go by index, so a deletion in the middle among them shifts later indices uncorrected, the limitation the pending marks keep. Message ids and ledger reach disk in the same chat save, so one is not saved without the other. Live check of a middle deletion is pending (issue #19).

**Update log (issue #26).** In the Paragon chat the updates for replies 2165, 2167 and 2169 wrote their scene but no facts, although four replays of the same extraction all returned facts; the only trace was the browser console, gone after a reload. So the ledger keeps its own short history in `updateLog`, saved with the chat: the newest `KNOWLEDGE_UPDATE_LOG_CAP` = 20 records, oldest first (`recordKnowledgeUpdate`). Nothing reads it — not the block, not the extraction prompt, not the popup (whose save writes only `characters` and `facts`). No timestamps; indices and message ids place each record. Records (shape at `createEmptyKnowledgeLedger`):

- `{ kind: 'update' | 'reextract', from, to, messageId, answer: { present, newCharacters, learned, retracted, revealedSecrets, fulfilled }, factsCreated, holdersAdded, factsRetracted, beatsCompleted }` — an applied answer: the messages read, the message id of `to` (`null` when it has none), the lengths of the answer's lists (`fulfilled` after resolving), and what the apply did (fact ids created and retracted, holder entries added, the teller's entry included, the number of beats completed). Beats go in as counts only, never their ids or texts: the plan is spoiler-protected. An update whose answer learned nothing is an `update` with zero counts.
- `{ kind: 'skipped', from, to, reason }` — a call whose answer was not applied: `'no answer'` (the call failed or the answer was unreadable), `'chat changed'` (the reply's or message's text changed), `'ledger moved'` (a rollback or update moved `lastUpdatedAt` during the call). Saved, unlike before. A skip by the tracker switch, the update interval or an update already running is not recorded, nor is a skip when another chat was loaded during the call (the record would land in that chat).
- `{ kind: 'rollback', from: firstGoneIndex, factsDropped, holdersDropped, factsRestored }` — written by `dropKnowledgeFrom` when the rollback changed anything. In `rollBackKnowledgeFrom` it also counts what `followMessagesById` took back with deleted messages. The edit's `dropKnowledgeLearnedAt` writes none; the re-extraction after it writes its `reextract` record.

What a step did is found by object identity (`knowledgeHoldings` before and after, `holdingsChange`), so a restored fact that took a fresh id is reported under that id.

**The knowledge block** — `story_arc_knowledge`, in-chat at depth 1, system role, set by `injectKnowledgeBlock()` from `injectStoryArcPrompts()` (called by `onGenerationStarted` and `onMessageDeleted`) next to the plan and signal injections. Depth 1 sits right above the newest message; this placement took a hand-written card from 3 of 3 leaking replies to 0 of 3 in the 2026-11-01 experiment (spec issue #2, Further Notes). `buildKnowledgeBlock(ledger, chat)` covers:

- **present** — the characters in `scene.present` from the last extraction;
- **talked about** — characters whose name or an alias appears as a whole word (case-insensitive, Unicode-aware) in the story text of the latest user message or the latest reply, hidden messages skipped, minus those present. Story text is the message with every tagged element (`<tag>…</tag>`, nested ones included) taken out (`withoutTaggedElements`, issue #22): presets append status blocks such as `<svt>…</svt>` and `<trk>…</trk>` to every reply, and at message 2133 of the Paragon chat three bystanders got a talked-about section only because a `<bg>` line named them. HTML formatting tags in the story text (`<i>Steve</i>`) are taken out too. The extraction input keeps the tags.

```
[WHO KNOWS WHAT — characters in this scene and characters being talked about. Each character knows only their own list, what everyone knows, and what happened in front of them on-screen. A private fact reaches nobody off-screen: not through rumors, teammates, news reports, logs, records or their own deduction. A character not listed here knows only what everyone knows, plus any secret the SECRETS section names them for.]

EVERYONE KNOWS
- Steve's team won the Best Live Demo award

STEVE (present)
- Knows: Steve is quitting next month (shared only with Amy)
- Knows: The demo ran on a scripted fallback (shared only with Lena and Amy)

AMY (present)
- Knows (told by Steve): Steve is quitting next month (shared only with Steve)
- Knows: The demo ran on a scripted fallback (shared only with Lena and Steve)

LENA (talked about, not present)
- Knows: The demo ran on a scripted fallback (shared only with Steve and Amy)
```

`EVERYONE KNOWS` lists the public facts as `- <fact>`, newest first by their newest holder entry (facts without holders after the dated ones, in ledger order), at most `KNOWLEDGE_LIST_CAP` lines; it is printed only when there are public facts, right after the header. Per character: `- Knows: <fact>` (or `- Knows (told by <name>): <fact>`), followed by ` (shared only with <names>)` listing the fact's other holders in holder order, or ` (known only to them)` when the character is its only holder; and, for a character talked about only, `- Has told only <names>: <fact>` from the `toldBy` entries. Each list holds at most `KNOWLEDGE_LIST_CAP` = 5 lines, newest first; an entry made by the user counts as newest, so a correction reaches the narrator first. A character with no lines gets no section; with no public fact and no section the block is `''`. A `plan` holder entry never prints a line of its own but is named in "shared only with" (owner ruling D22: otherwise the line says the character alone knows it, and the header's last sentence points planned holders to the SECRETS block), and a fact held only through the plan is printed nowhere: a secret's text stays in the SECRETS block, which gates it by phase. Once a secret is revealed on-screen it is a fact with `witnessed` holders and is printed like any other; its planned holders get no line for it.

There are no "Does not know" lines (issue #21, owner ruling D20 a, D18 a). Until 2026-11-01 each covered character got `- Does not know: <fact>` for a fact another covered character held. Every such line printed the private fact's full text: in the Paragon party scene at message 2169 the block was ~4,600 tokens in 11 sections, 48 of its 68 lines were "Does not know" lines, and the two private Jumbotron facts appeared 24 times. The narrator gave one of them to a background character who was listed as not knowing it, laundered as "My team leader said …". Naming a secret once per bystander puts it in front of the model ("white bear"), and a character without a list had no limit at all. Now a private fact's text appears only in its holders' sections, the header says what a character may draw on (own list, public facts, what happened in front of them) and that rumor and hearsay carry nothing new, and the public facts are printed so bystanders have material they may use. The extraction prompt records as public what a crowd watched happen and what was broadcast or reported.

**The taken-names block** (issue #39, spec #34) — `story_arc_names` (`NAMES_PROMPT_KEY`), in-chat at depth 1, system role, set by `injectKnowledgeBlock()` right after the knowledge block, under the same gate: Story Arc on and the tracker on, `''` otherwise and `''` when the ledger has no character. It works without any active arc. ST joins the extension prompts of one position, depth and role in the sorted order of their keys, so it lands right after `story_arc_knowledge`, in the same system message. It tells the narrator every first name, surname and codename the story already uses, because Summaryception compacts long chats and the narrator then reuses names it cannot see (Julian Vance and Julian Sterling). One header sentence with the rule, then the names on one line:

```
[NAMES ALREADY IN THIS STORY — first names, surnames and codenames of characters who have appeared. A new character gets none of these names, as a first name or as a surname, unless the new character is related to the character who has it. Characters already in the story keep their names.]
Aegis, Bishop, Chen, Marcus, Sterling, Vance
```

The derivation is code in `lib/knowledge/names.js`, no LLM call, and reads only the ledger: every character's name and each of its aliases. `nameWords(name)` splits a name at whitespace and removes enclosing punctuation; it drops words without a letter, lowercase particles (`de`, `van`, `al-`; a capitalised `Van` or `Al` stays) and leading articles (`The`), and drops leading titles while more than one word is left, so the last word always stays. A title is a word ending in a period or a word of `TITLE_WORDS` (honorifics, ranks, offices and kinship words such as Mr, Dr, Judge, Commissioner, Señora, Staff, Sergeant, Uncle, Auntie; never a common given name such as Don). No word is classified as a first name or a surname. `listTakenNames(ledger)` returns a `Map` from the folded form (`foldName`: lowercase, diacritics removed, locale-independent) to the spelling of the first record in ledger order that has it; a hyphenated word is in it whole and by each part. `buildTakenNamesBlock(ledger)` prints only the parts, sorted by the folded form in code-unit order. **Byte stability:** the text depends only on the set of names, so the order of the records, the facts, the holders and the scene never change it; a new character, a rename or an alias with a new word does. The reused-name flag (#35) and the planner with its plan check (#36) reuse `listTakenNames` and `foldName`; the module is its own file because the generator cannot import `ledger.js` without a cycle. A character added or renamed in the Knowledge popup counts from the next generation on. The extraction prompt and the ledger's shape are unchanged.

**Secrets and holders.** The planner names each secret's holders (`generate-arc.txt`, `normalizeSecretHolders` in validation, `[]` for arcs planned before). A re-plan keeps the holders of kept secrets. While the tracker is on the SECRETS block appends ` (known only to: …)` to a secret with holders (`holderSuffix` in `builder.js`). The extraction sees the shown secrets with their planned holders and reports a secret that comes out plainly on-screen under `revealedSecrets`, with what the characters heard (`text`, one sentence) and the message it came out in (`at`); applying the answer turns that sentence into a ledger fact linked to the secret. The secret's own `content` never goes into a fact and so never into the knowledge block: it may hold parts that have not come out yet (owner ruling D10 a, 2026-11-01). The secret's own `disclosed` state in the arc stays with the plan check and the Arc Manager.

**The Knowledge popup** (`lib/ui/knowledge-popup.js`), reachable while the tracker is on from the Arc Manager header and the wand popup. It lists characters (add, rename, aliases) and facts with their holders (add, edit text, delete, add or remove a holder, mark public), behind two spoiler groups that start closed, because the ledger shows who holds the arcs' secrets. Names and aliases are unique across characters, ignoring case, because the block and the extraction find characters by any of them. Hand edits are `how: 'user'`, `at: null`: no regeneration, swipe or deletion removes them. The popup is the correction path for an extraction that recorded a leak as a fact.

**Status line.** The settings drawer shows at which message the ledger was last updated (`updateKnowledgeStatus()`), so the player sees whether it is behind.

**Live verification pending (K13).** None of the tracker has run in the browser yet: in the disposable test chat, switch on, a few replies (the status line moves), a swipe to a new and to an existing reply, a regeneration, an edit, a hand-entered fact in the popup, the `(known only to: …)` suffix in the outgoing prompt, then switch off and confirm the prompt equals the one before the tracker. `prompts/extract-knowledge.txt` has never run against a live model.

| Outgoing prompt | in-place mutation of `eventData.chat` on `CHAT_COMPLETION_PROMPT_READY` | Stamp per-message arc counters (see `stamping.js`) |
| LLM calls | `ConnectionManagerRequestService.sendRequest()` (profile set) or direct `fetch()` to `/api/backends/chat-completions/generate` (fallback) | Run multi-phase generation (not `generateRaw()` — see Gotchas, a14ae32) |
| Per-chat persistence | `chat_metadata` + `saveMetadata()` | Store arc plans |

Key events used:

| Event | Handler |
|-------|---------|
| `GENERATION_STARTED` | Build and inject arc guidance (or clear it when no arcs / disabled); set the knowledge block (`''` while the tracker is off) |
| `MESSAGE_RECEIVED` | Parse signals, complete beats named by `COMPLETE` markers, flush queued marks, scrub leaked ids, refresh progress; then start the knowledge update (not awaited), which with the tracker on also completes the beats it reports and refreshes progress when it did |
| `USER_MESSAGE_RENDERED` | Promote the next beat in arcs left without an active one |
| `MESSAGE_DELETED` | Drop queued marks and reopen completions from the new chat length on; ledger knowledge and completion records follow their messages by message id (index rule for those without one) |
| `MESSAGE_SWIPED` | Drop queued marks, reopen completions and drop ledger knowledge from the swiped message on; re-extract a switched-to existing swipe |
| `MESSAGE_EDITED` | Reopen the beats completed at the edited message (`autoTrack` on) and re-extract its knowledge (tracker on) |
| `CHAT_CHANGED` | Re-initialize per-chat state, reopen completions past the chat's end, refresh UI, drop ledger knowledge past the chat's end, refresh the knowledge status line |

`MESSAGE_RECEIVED` fires only for AI messages; user messages fire `USER_MESSAGE_RENDERED` (the same event Story Mode counts rounds on). The split is what makes the promotion gap a *user* turn rather than any turn.

**Emission order matters here.** `Generate()` emits `GENERATION_STARTED` at its top (`public/script.js:4299`) and only calls `sendMessageAsUser()` — which emits `MESSAGE_SENT` and then `USER_MESSAGE_RENDERED` — about 150 lines later (`:4453`, emitting at `:5912`/`:5919`). The injection for the message the user just typed is therefore built *before* promotion runs, so a freshly promoted beat's pressure first reaches the model on the generation after that. The resulting sequence, per completed beat:

1. AI message completes a beat; the arc is left with no active beat.
2. The player types a reaction. Its generation still sees the linger directive → the AI writes one consequences/breather message with no beat check.
3. The player types again. This generation carries the newly promoted beat's pressure.

One AI message of breathing room per beat, which is the intent. With the knowledge tracker on, step 1 is the extraction's answer instead, a few seconds after the reply (or up to `updateInterval` replies later); promotion still waits for the first user message after the completion is applied, and a user message sent while the extraction runs is built with the beat still active. This cannot be shortened by choosing a different event: every user-message event fires after `GENERATION_STARTED` inside the same `Generate()` call. Promoting in `onGenerationStarted` instead would restore exactly the chaining the design removes, because empty-input continues also go through `Generate()`.

## Gotchas

- **Arc generation deliberately does not go through `generateRaw()`.** It adds fields (`include_reasoning`, `reasoning_effort`, `type`, `stop`, `logit_bias`, …) that make some providers answer 502. The profile route goes through `ConnectionManagerRequestService` (a controlled payload via `ChatCompletionService.processRequest`, not the `generateRaw` path); the no-profile fallback `callBackendDirectly()` sends the minimal body SillyTavern-MemoryBooks uses — `messages`, `model`, `temperature`, `max_tokens`, `chat_completion_source`, plus `custom_url` when set. Pinned by a14ae32, e65449d.
- **`maxTokens: undefined` is how the profile preset's response length wins.** `ChatCompletionService.createRequestData` deletes undefined payload keys *before* `presetToGeneratePayload` merges the preset, so an undefined `max_tokens` lets the preset's value through. Passing a number would override the preset on every call. Pinned by e65449d.
- **The signal directive must never live inside the budget-trimmed plan text.** The trim slices from the tail, the directive was the last section — so on any plan larger than the budget the model never saw the signal protocol at all. This was the primary reason tracking never worked. It now injects separately (`story_arc_signals`). Pinned by 27c3d17.
- **The signal directive only works at IN_CHAT depth 0.** In the system prompt or even one message from the end, GLM 5.2 demonstrably reasoned about the beats in its chain-of-thought and still skipped the marker; as the final message before generation it complied. Marker goes on the reply's *first* line — end-of-message markers are eaten by response-token-cap truncation. Pinned by 27c3d17.
- **Beat progression needs explicit promotion.** Completing a beat does not make the next one `active` by itself; without a promotion step the arc has no active beat after the first completion, the directive lists no markers, and tracking silently dies. Promotion now lives in `promoteNextBeats` on `USER_MESSAGE_RENDERED` — deliberately one user turn later than the completion, never in `completeBeats`. Pinned by 27c3d17 (the step) and this change (its placement).
- **A visible plan is a task list.** Listing pending beats with ids and intentions made GLM 5.2 drive at them: 7 of 10 non-optional beats in ~8 exchanges on a 40-message arc, with beat intentions parroted into dialogue. The plan text now shows one beat, as a pressure, without ids. This is the primary pacing brake; the prompt-side "do not advance for N more messages" rule was ignored every time.
- **Never refuse a completion for being too fast.** The signal arrives after the scene is already on screen, so refusing it makes the tracker disagree with the visible story and re-arms the same marker instruction next message — a loop. Bookkeeping stays liberal; the pace is controlled by what the model is shown, not by what the recorder accepts.
- **Do not migrate stored arcs to add `pressure`.** Arcs planned before 2026-08-29 have beats without the field; `buildEpisodeSection` (`builder.js`) falls back to `intention` and they keep working. A live arc in the owner's test chat depends on this.
- **`setExtensionPrompt` takes `(key, value, position, depth, scan, role, filter)`.** The original call passed seven positional args (an extra `0` before `scan`), shifting `role` into `scan` and the role constant into `filter` — it only worked because everything coerced to the intended values. Pinned by 27c3d17.
- **`generateQuietPrompt()` is not the alternative.** It routes through the full chat pipeline, which re-enters Story Arc's own `GENERATION_STARTED` / `MESSAGE_RECEIVED` handlers while a plan is being generated. Tried in 8787fea, reverted in a700465.
- **Non-streaming requests time out on large prompts.** The arc prompt arrives as one 24K+ char message and exceeds nano-gpt's ~38s non-streaming ceiling; normal chat escapes this only because its prompt is spread over many small messages. The request therefore sets `stream: true` and reassembles the SSE `data:` events, stopping at `[DONE]`. Pinned by a257d92.
- **The model name must come from `getChatCompletionModel(oai_settings)`.** `oai_settings.openai_model` is only correct for the OpenAI source — nanogpt keeps its model in `oai_settings.nanogpt_model`, so reading the field directly sent "gpt-5" to a backend that does not serve it. Pinned by ca2dfb8.
- **A 200 OK can still be an error.** Some backends return `{ error: … }` in a 200 body, and errors also turn up inside individual SSE chunks. Both paths throw instead of handing the body to the arc JSON parser, which otherwise reports it as a parse failure. Pinned by 3a14aa3.
- **The settings drawer needs ST's exact markup.** The header div must carry `inline-drawer-toggle` — ST binds its click handler to that class, not to `inline-drawer-header` — and without it the drawer silently never opens. Pinned by 1310dc7. Leave the styling to ST too: wrapper padding and a header border misalign the panel in the drawer list (a09887b).
- **Assistant-last histories make RP presets restart the scene.** Celia injects `<latest_turn_start>`/`<latest_turn_end>` wrappers at fixed IN_CHAT depths 1/0; when the user generates without typing (a normal way to advance the story), the wrappers label the model's *own last reply* as "the latest turn to answer", and GLM re-answered the last user message from scratch — three parallel takes of the same scene. The signal directive's continuation guard counters this at depth 0. Pinned by 8dbfdb1.
- **Every popup must unbind its click namespace when it resolves.** The handlers are delegated on `document`, so they outlive the popup's DOM. The wizard's `click.storyArcWizard` stayed bound after the wizard closed, and one click in the arc manager then fired both modules' `.story-arc-spoiler-toggle` handlers — the spoiler toggled twice and looked like nothing happened. The manager leaked the same way in reverse. Each popup now calls `$(document).off('click.<namespace>')` after `await popupPromise`. Pinned by 7945e3a; `wand-menu.js` follows the same pattern for `click.storyArcWandPopup`, and needs it more than the others because the popup is reopened in a loop.
- **`MESSAGE_RECEIVED`'s index is not always `chat.length - 1`.** `/sys at=N` emits the event with the index of the inserted message (`public/scripts/slash-commands.js:6006`); every other emission site (`script.js:6691,6716,6738,6781`, `group-chats.js:300`) does use the last index. `processSignalResults` therefore takes `messageIndex` from the handler instead of re-deriving it, so `lastFulfilledAt` points at the message that actually carried the marker. Pinned by 9c3e980.
- **Stored arcs are never re-validated.** The tier band clamp (episode 8–20) and the milestone rules apply at generation only; an existing episode with `estimatedLength: 40` keeps it, and re-plan replaces `estimatedLength` from the fresh generation. Reading the clamp as "no arc can have 40" is wrong for every arc planned before 2026-09-16 (77dbf33).
- **Never re-list the re-planned arc in Phase 2's existing arcs.** It sits in the `ARC SO FAR` block; the existing-arcs list carries "do not duplicate these", so listing it there too tells the model not to cover the arc's own ground. Phase 1 gets the `[BEING RE-PLANNED]` mark instead (e3b81d8).
- **Prompt clauses steer; only post-processing guarantees.** GLM pastes beat ids and next-beat agendas into Celia's `[Main-line]`/journal blocks even when told not to; because those blocks re-enter the prompt as history, the model ends up pacing the arc off its own agenda instead of the pacing rules. `scrubArcInternals` deletes the ids mechanically after every AI message — the confidentiality clause reduces the leakage, the scrub makes the identifiers unable to persist.

## Design Principles

1. **Context-first** — arc quality is bounded by context quality. Lorebook classification, chat trimming, and character harvesting are all weighted toward signal over noise.
2. **Narrative-first schema** — beats express *intention*, not script. Secrets, foreshadowing, and triggers give the AI creative latitude while keeping the arc on track.
3. **Conservative pacing** — phase advancement requires both beat completion and message count to exceed the threshold. The AI is explicitly told not to rush.
4. **Non-destructive** — read-only access to lorebook, chat history, and character data. Only `chat_metadata.story_arc` is written.
5. **Lean** — no bundler, no library, no file storage beyond `chat_metadata`. One module per responsibility. No features outside the core loop: harvest → plan → inject → track. One exception, by decision (ADR-0007): the optional knowledge tracker keeps the one kind of memory the plan's secrets need, who knows what; Story Arc still does not summarize or manage lorebooks.
6. **Graceful degradation** — any single context source (lorebook, chat, character) is sufficient for generation. Empty sources produce placeholder text rather than errors.
